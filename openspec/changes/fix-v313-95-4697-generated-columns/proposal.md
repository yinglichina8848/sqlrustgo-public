## Why

Issue #4697: `CREATE TABLE t(c INT GENERATED ALWAYS AS (a + b) STORED)` fails
with `Parse error: Expected SELECT after AS`. The CREATE TABLE column-definition
path doesn't recognise the SQL-standard GENERATED keyword and treats
`AS (expr)` as a CTE/subquery construct, so the parser falls into a branch
expecting `SELECT`.

Generated columns (also called "computed columns" in MySQL or "virtual
generated columns" in SQLite) are required by:

- SQL:2003 / SQL:2008 standard `GENERATED ALWAYS AS (expr) STORED|VIRTUAL`
- MySQL 5.7+ `GENERATED ALWAYS AS (expr) STORED|VIRTUAL`
- PostgreSQL 12+ `GENERATED ALWAYS AS IDENTITY` (covered by existing test
  `test_parse_generated_column_identity`)
- SQLite 3.31+ `GENERATED ALWAYS AS (expr) STORED|VIRTUAL`

This PR lands parser-level acceptance. Executor/storage evaluation of the
generated expression on read/write is **out of scope** (deferred to v3.13 or
later); the parser records the intent so a future engine-side implementation
can pick it up without another grammar change.

## Fix

Extend `parse_column_definition` in `crates/parser/src/parser.rs` so the
post-data-type constraint loop accepts a `GENERATED ALWAYS AS (expr)
[STORED|VIRTUAL]` clause and records it on the `ColumnDefinition` AST node.

Three concrete changes:

1. New `GeneratedColumn { expression: String, stored: bool }` struct.
2. New `ColumnDefinition.generated: Option<GeneratedColumn>` field (with
   `#[serde(default)]` for backward-compatible deserialization).
3. New arm in the `parse_column_definition` constraint loop matching
   `Identifier("GENERATED")`, which consumes:
   `GENERATED ALWAYS AS (<expr>) [STORED|VIRTUAL]`.
   - `ALWAYS` and `AS` are required keywords.
   - `<expr>` is parsed via the existing `parse_expression()`.
   - `STORED` / `VIRTUAL` are optional; absent means `VIRTUAL` (SQL default).

`ColumnDefinition` gains a `Default` impl so all ~20 existing construction
sites continue to work without per-site migration; the new parser-only
construction site uses `..Default::default()` for the auxiliary fields.

## Capabilities

### New Capabilities

- `parser-generated-column`: `CREATE TABLE t(c INT GENERATED ALWAYS AS
  (expr) [STORED|VIRTUAL])` parses successfully and the generated-column
  definition is recorded on `ColumnDefinition.generated`.

### Modified Capabilities

- `parser-column-definition`: `ColumnDefinition` gains a `generated`
  field. Round-trip JSON/serde persistence is preserved (field is
  `Option` with `#[serde(default)]`).

## Out of Scope

- Executor-side evaluation of the generated expression on INSERT/UPDATE
  (no physical storage of the computed value, no on-read computation).
  Tracked separately as a v3.13 executor/storage item.
- `GENERATED ALWAYS AS IDENTITY` for auto-increment sequence integration —
  already covered by existing parser test
  `test_parse_generated_column_identity`; deeper planner/storage work is
  a separate issue.
- `GENERATED BY DEFAULT AS (expr) STORED|VIRTUAL` — the `BY DEFAULT`
  variant is deferred (the `ALWAYS` form is the SQL standard).
