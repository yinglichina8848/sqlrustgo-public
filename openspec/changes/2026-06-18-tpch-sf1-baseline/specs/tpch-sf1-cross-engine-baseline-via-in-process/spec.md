# tpch-sf1-cross-engine-baseline-via-in-process

## Purpose

A 22-query TPC-H baseline on the SF=1.0 fixture SHALL be runnable
end-to-end and SHALL produce a single Markdown report at
`docs/releases/v3.10.0/perf/SF1_BASELINE_REPORT.md` with row
counts and per-engine wall-clock timings for sqlrustgo, MariaDB
(when available on `localhost:3306`), and SQLite
(`/tmp/tpch-sf1/sqlite.db`). The baseline MUST be runnable
without depending on a working external mysql client connection
to sqlrustgo, because the external-client path is tracked
separately in issue #3474.

## ADDED Requirements

### Requirement: SF=1.0 fixture generation is dbgen-backed

The SF=1.0 fixture used by the baseline SHALL be produced by the
official TPC-H dbgen tool (the binary at
`/home/openclaw/tpch-dbgen-master/dbgen`) or by the project's
`scripts/generate_tpch_data.sh --sf 1 --backend dbgen` wrapper.
The fixture MUST be a `.tbl` file set in the TPC-H standard
pipe-delimited format with the canonical SF=1 row counts:

- region: 5
- nation: 25
- supplier: 10,000
- customer: 150,000
- part: 200,000
- partsupp: 800,000
- orders: 1,500,000
- lineitem: 6,000,000

The fixture SHALL NOT be generated by
`crates/bench/examples/tpch_data_gen.rs` (which has a documented
100x-scale bug per its own source code).

#### Scenario: SF=1.0 fixture row counts match TPC-H spec

- GIVEN `scripts/generate_tpch_data.sh --sf 1 --output
  /tmp/tpch-sf1 --backend dbgen` has been run
- WHEN `wc -l /tmp/tpch-sf1/*.tbl` is executed
- THEN each table's row count SHALL match the TPC-H spec counts
  above (or be within ±1 of them, depending on the dbgen build's
  exactness)

### Requirement: 22 queries are run on the in-process surface

The baseline SHALL run all 22 TPC-H queries (Q1..Q22) on the
SF=1.0 fixture using the existing in-process test surface
(`MySqlTestClient` against `start_ephemeral` +
`FileStorage` + `WalStorage`). The query SQL is the canonical
TPC-H SQL in `queries/q{1..22}.sql`, unchanged from the
existing SF=0.01 test.

For each query, the baseline SHALL record:
- the row count returned by sqlrustgo (via `MySqlTestClient::query_rows`)
- the wall-clock time for the sqlrustgo round-trip, measured at
  the `MySqlTestClient` boundary
- when MariaDB is reachable on `localhost:3306`: the row count
  and wall-clock time for the same query on MariaDB
- when SQLite is on PATH: the row count and wall-clock time for
  the same query on SQLite

#### Scenario: 22 entries in the baseline report

- GIVEN a fresh `bash scripts/tpch_sf1_baseline.sh` run
- WHEN the resulting report is read
- THEN it SHALL contain exactly 22 query entries (Q1..Q22) with
  non-empty row counts and per-engine timing columns

### Requirement: report file location and format

The baseline report SHALL be written to
`docs/releases/v3.10.0/perf/SF1_BASELINE_REPORT.md`. The report
SHALL be a Markdown document with the following sections in this
order:

1. **Header** — issue #3423, branch / commit hash, timestamp, host
   CPU / RAM / disk free
2. **Setup** — fixture path, generation tool, row counts, file
   sizes
3. **Per-query results** — a table with one row per query and
   the columns: `Q | sqlrustgo rows | sqlrustgo ms | mariadb rows
   | mariadb ms | sqlite rows | sqlite ms | notes`
4. **Summary** — totals, the slowest query per engine, the
   queries where row counts diverge between engines (with `OK`
   or `DIVERGENT` annotations), and a pointer to issue #3474 for
   the external-client follow-up
5. **Limitations** — explicit list of what the baseline does NOT
   cover (e.g. external-client path, prepared-statement binary
   protocol, multi-result-set)

#### Scenario: report file exists and has the required sections

- GIVEN a completed `bash scripts/tpch_sf1_baseline.sh` run
- WHEN the report file is opened
- THEN it SHALL contain a `# SF=1.0 baseline` header and SHALL
  contain the five sections listed above (in order)

### Requirement: divergence between engines is annotated

When sqlrustgo's row count for a query differs from MariaDB's
(or SQLite's) row count for the same query, the report SHALL
mark that query as `DIVERGENT` in the `notes` column and SHALL
include the two counts in the notes. The baseline does not
attempt to root-cause the divergence; it only records it.

#### Scenario: row-count divergence is recorded

- GIVEN Q14 returns 1 row from sqlrustgo and 1 row from MariaDB
  (no divergence) and Q19 returns 1 row from sqlrustgo and 0
  rows from MariaDB (divergence)
- WHEN the report is generated
- THEN Q14 SHALL have no `DIVERGENT` annotation
- AND Q19 SHALL have a `DIVERGENT` annotation in the `notes`
  column, with both row counts visible

## ADDED Test Surface

### Requirement: tpch_sf1_22_vs_3engines_test is the regression

`tests/tpch_sf1_22_vs_3engines_test.rs` SHALL contain at least
one integration test that runs the 22 TPC-H queries against the
in-process server and asserts that all 22 return at least one
row (Q1, Q6, Q14, Q15, Q19, Q22 are known to return small
result sets; the others return multi-row result sets). The test
SHALL mark itself `#[ignore]` if the SF=1.0 fixture is not
present at the expected path, with a clear `eprintln!` message
telling the operator to run the fixture-generation step.

#### Scenario: in-process regression passes when fixture is present

- GIVEN `/tmp/tpch-sf1/lineitem.tbl` exists and has 6,000,000
  lines
- WHEN `cargo test --test tpch_sf1_22_vs_3engines_test
  -- --include-ignored` is run
- THEN the test SHALL pass within 10 minutes wall-clock

#### Scenario: in-process regression is skipped when fixture is absent

- GIVEN `/tmp/tpch-sf1/lineitem.tbl` does not exist
- WHEN `cargo test --test tpch_sf1_22_vs_3engines_test` is run
- THEN the test SHALL be reported as ignored (yellow / ok in
  the test summary) and SHALL NOT consume the 10-minute budget
