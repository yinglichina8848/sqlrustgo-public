## Context

Issue #3423 asks for a TPC-H SF=1.0 cross-engine baseline. The
canonical expectation (per the issue's acceptance criteria) is
that the baseline be runnable end-to-end against an external
mysql client. That prerequisite is not currently satisfied:
mysql-client 8.0.46 / libmysqlclient 8.0.46 either silently drops
the result set, returns `ER_MALFORMED_PACKET` (2027) on a partial
result set, or hangs on the next packet after the OK terminator.
This is tracked in issue #3474 and is not on the critical path
for v3.10.0.

A 22-query SF=0.01 in-process surface test
(`tests/tpch_sf01_22_vs_3engines_test.rs`) already exists and
exercises the in-process `MySqlTestClient` + `start_ephemeral`
flow on the SF=0.01 fixture. The same flow can be extended to
the SF=1.0 fixture. That is the path this change takes.

## Goals / Non-Goals

**Goals:**

- Extend the in-process wire-protocol test surface to the SF=1.0
  fixture.
- Run Q1..Q22 against sqlrustgo on the SF=1.0 fixture in-process.
- Capture per-query row count and wall-clock time.
- Emit a single Markdown report at
  `docs/releases/v3.10.0/perf/SF1_BASELINE_REPORT.md`.
- Provide a non-cargo shell wrapper at
  `scripts/tpch_sf1_baseline.sh` that drives the same flow on a
  developer workstation.

**Non-Goals:**

- External mysql client (mysql-client 8.0.46) path — issue #3474.
- MariaDB / SQLite cross-engine comparison — depends on #3474.
- Cell-level value comparison across engines.
- Generating the SF=1.0 fixture as part of this change; the
  fixture is generated by the operator and committed to the test
  data directory.
- Any SQL feature, planner, executor, or storage change. This
  change is purely test surface and reporting.

## Decisions

### D1: In-process surface only

The test surface is the in-process `MySqlTestClient` +
`start_ephemeral` flow already used by
`tests/tpch_sf01_22_vs_3engines_test.rs`. We do NOT shell out to
the external `mysql` CLI. The shell wrapper
`scripts/tpch_sf1_baseline.sh` is a developer convenience that
boots the same in-process flow (or a thin external wrapper
around it), not a separate external-mysql path.

**Rationale:** the in-process surface is the only one that
currently works end-to-end. The external-client path is broken
and tracked in issue #3474.

### D2: Fixture path is `/tmp/tpch-sf1`

The fixture directory is hardcoded to `/tmp/tpch-sf1` in the
test file. The shell wrapper uses the same path. The
`sqlrustgo-mysql-server` data dir is set to the same path so the
LOAD DATA LOCAL INFILE whitelist accepts the source `.tbl` files
without an extra copy.

**Rationale:** the test was already written with this path; the
shell wrapper converges on it. The data-dir + fixture path
identity also lets the per-table `.json` files be reused across
runs, avoiding repeated LOAD DATA.

### D3: Per-query timeout is 1800 seconds

The per-query wall-clock budget in the test is 1800 seconds
(30 minutes). This accommodates the Q9 6-way join at SF=1.0
which is the worst-case query.

**Rationale:** the issue notes that Q9 may need >180 seconds;
1800s gives 10x headroom. The 10-minute test budget is enforced
by the test runner, not by the per-query timeout.

### D4: Report is sqlrustgo-only on the in-process surface

The report explicitly labels the comparison surface as
in-process via `MySqlTestClient`. It does not claim a
cross-engine comparison. The limitations section names
issue #3474 as the external-client follow-up.

**Rationale:** the cross-engine comparison is not deliverable
without a working external mysql client. Recording a baseline
for sqlrustgo alone is still useful for tracking performance
regressions on the SF=1.0 fixture.

### D5: Test degrades gracefully when the fixture is absent

The test is `#[ignore]`d when the SF=1.0 fixture is absent. The
skip message names the generator command and target directory so
an operator can produce the fixture.

**Rationale:** the SF=1.0 fixture is large (~1.1 GB) and may not
be present in every developer's working tree. The test must
build cleanly even when the fixture is absent.

## Risks / Trade-offs

### R1: 10-minute test budget vs 1800s per-query timeout

The test runner enforces a 10-minute budget for
`cargo test --test tpch_sf1_22_vs_3engines_test -- --include-ignored`
to pass. The 1800s per-query timeout is per-query, not total.
If the cumulative time of 22 queries exceeds 10 minutes, the
test will still fail even though no individual query timed out.

**Mitigation:** the slowest query at SF=1.0 is Q9. If Q9 takes
more than ~7 minutes, the remaining queries must complete in
~3 minutes, which is achievable for the rest of the suite. If
not, the test budget must be raised to 30 minutes.

### R2: LOAD DATA is expensive

Loading the SF=1.0 fixture via LOAD DATA LOCAL INFILE is
expensive (~5-15 minutes for 6M lineitem rows). The test
mitigates this by reusing per-table `.json` files across runs.

**Mitigation:** the `json_data_ready` check in the test skips
LOAD DATA when the `.json` files exist with valid row counts.

### R3: LFS checkout cost

The SF=1.0 fixture is LFS-tracked. A fresh clone will require
`git lfs pull` to materialize the fixture, which is a one-time
~1.1 GB download.

**Mitigation:** the skip message in the test points the operator
at the LFS pull command.

### R4: Internal contradiction in the original proposal

The original proposal stated the surface was in-process, but
the original `scripts/tpch_sf1_baseline.sh` shelled out to the
external `mysql` CLI. The script has been reconciled to the
in-process surface per D1 above.

**Mitigation:** the design records the decision; the task list
includes a verification step that the script no longer contains
external-mysql shell-outs.
