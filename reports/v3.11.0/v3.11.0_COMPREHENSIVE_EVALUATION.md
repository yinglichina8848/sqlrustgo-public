## 1. 性能评估

### 1.1 SOAK 测试结果 (Batch Mode)

**测试时间**: 2026-07-18 (运行时长: 21h+)
**配置**: 150 线程, batch-size 100, OLTP:OLAP = 3:7
**WAL 模式**: `--wal-sync=batch:10000`

#### OPS 趋势

| 时间 | 运行时长 | OPS | WAL | 数据库 | 状态 |
|------|----------|-----|-----|--------|------|
| 06:52 | 0h | 24,678 | 6.6MB | 7.5MB | ✅ |
| 07:45 | 10h21m | 19,375 | 9.8MB | 13MB | ✅ |

**观察**:

- 可能原因: 数据库数据量增长、缓存命中率变化
- 下降趋势放缓，趋于稳定

**结论**: 线性扩展性良好，256 线程达到峰值

### 1.2 性能提升路径

```
v3.10.0 基础:
  TPS: ~9 OPS (mysql CLI per-query 模式)

v3.11.0 优化:
  ├─ Batch Transaction Mode: 9 → 371 OPS (41x)
  ├─ WAL Sync Mode (batch:10000): 371 → 400 OPS
  └─ Batch Mode bench_client: 400 → 32,805 OPS (82x)

总计: 9 → 32,805 OPS (3,644x 提升)
```

### 1.3 瓶颈分析

**旧瓶颈 (v3.10.0)**:
- mysql CLI 每次查询 ~264ms (进程创建 + TCP 握手)
- 单线程串行执行
- JSON 序列化开销

**新优化 (v3.11.0)**:
- Batch 模式: 100 查询/次 mysql 调用
- ParallelWalStorage: 表级并行 flush
- WAL batch sync: 每 10000 次事务 sync 一次

## 3. 架构评估

### 3.1 ParallelWalStorage 架构

```
ParallelWalStorage (WAL serial, tables parallel):
  commit():
    1. WAL write (serial)        ← 确保持久化顺序
    2. Sync WAL                 ← batch:10000 模式
    3. flush_parallel()         ← 并行表写入
       └─ std::thread::scope()  ← 3+ 脏表时启用
```

### 3.2 Batch Mode bench_client

```rust
// 架构: 持久 mysql 进程 per 线程
Command::new("mysql")
    .stdin(Stdio::piped())    // 写入查询
    .stdout(Stdio::piped())   // 读取结果
    .output()

// 批量执行
let input = queries.join(";");  // 100 查询/批次
```

### 3.3 关键改进

| 组件 | v3.10.0 | v3.11.0 |
|------|---------|---------|
| Storage | FileStorage | **ParallelWalStorage** |
| WAL Sync | every | **batch:10000** |
| Table Flush | serial | **parallel (3+ tables)** |
| bench_client | per-query | **batch mode** |
| Thread Model | 16 threads | **150+ threads** |
