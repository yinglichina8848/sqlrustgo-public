# 写路径 O(log N) 设计评估（#5188）

> **版本**: v4.1.0（设计稿）
> **日期**: 2026-10-10
> **状态**: 设计评估，**不含实现**。按本 issue 约定，实现排在 #5167（正确性）之后。
> **关联**: #5181（部分修复已合入：`Vec::retain` 去掉二次分配）、#5177（读路径 WHERE 全扫描，已修复）

---

## 0. 现状与代价模型（代码事实）

- 热点：`WriteState::remove_matching`（`crates/storage/src/file_storage.rs:167-197`）。
  对 `tables` 与 `insert_buffer` 两份行向量逐行执行谓词判定 + 原地压缩。
  #5181 已把「取走整个向量 → 重建新向量」改为 `mem::take` + `Vec::retain`，
  去掉了 20000 元素向量的二次分配，但**遍历本身仍是 O(rows)**。
- 行定位基础设施已存在：PK/二级索引的 B+Tree 以
  `row_id: u32` 为值，而 `row_id` 就是行在 `Vec<Record>` 里的下标
  （`file_storage.rs:2208-2211`：`rows.iter().enumerate()` 后
  `index.insert(key, row_id)`）。`BPlusTree::search / search_all`
  （`crates/storage/src/bplus_tree/mod.rs:106,114`）返回 `Option<u32> / Vec<u32>`；
  #5213 之后一个 key 对应多个 `row_id`（非唯一索引）。
- Undo：`UndoOp::{UpdateRow,DeleteRow}` 记录 `row_idx` + 原值
  （`file_storage.rs:373-388`），ROLLBACK 按 LIFO 在**同一 index** 回放
  （`:369` 注释：reverse insertion order, last-in / first-out）。
  `remove_matching` 的 doc（`:161-166`）明确：**顺序保持是承重墙** ——
  多行删除后按 index 回放若用「remove 后重放旧 index」不能恢复原表，
  已由回归测试钉死（`crates/storage/tests/write_path_scaling_5181.rs::rollback_after_multi_row_delete_restores_order`）。
- 实测（#5181/#5188 引文，20000 行单行 delete+insert）：
  合计 **0.472ms** = 删除 **0.344ms** + 插入 **0.002ms**。
  即：谓词遍历 + 压缩是全部代价，插入本身可忽略。
- 系统级：sysbench @10000 行 1242~1367 QPS（#5183 测量污染更正后）。

**结论**：要让单行 DELETE/UPDATE 达到 O(log N)，唯一要改的是
「找到哪一行」这一步 —— 从全表谓词遍历改成索引定位。删除动作本身
（`Vec` 内挖洞）的代价决定两个候选方案的差异。

## 1. 方案 A：位置前置解析（resolve-then-apply）

### 机制

1. 谓词是纯 PK 等值时（`WHERE id = v`，形状判别复用 #5177 的
   `try_extract_pk_eq_with_col` / 保守回退规则），先用 PK B+Tree
   `search(key)` 拿 `row_id`（O(log N)，**不持有写锁**，取完即放）。
2. 拿 `write_state` 写锁，**在临界区内复核**：
   `rows[row_id]` 存在且其 PK 列仍等于 `v`。
   - 复核通过 → 只对该行执行删除/更新（`Vec::remove(row_id)` 或原地改值），
     跳过全表谓词遍历。
   - 复核失败（位置已失效）→ **回退现行全表路径**（`remove_matching` 现状），
     语义与今天完全一致。
3. `insert_buffer` 仍按现状小扫描（事务内未提交插入，O(事务大小)≈O(1)；
   索引在 #5210 后覆盖 buffer 行，但「索引查不到 buffer 行」与
   「索引查到」两种情形都必须正确 —— 最简做法：索引查到且复核通过则
   buffer 扫描可跳过，否则照常扫。实现时以复核结果为准，不做投机。）
4. 非 PK 等值 / 复合谓词 / 无 PK：一律现状路径（与 #5177 读路径同构的回退纪律）。

### Q1：并发写 + 位置失效下如何保正确（本方案核心）

**位置何时会失效**：索引解析与写临界区之间，同一表的并发
INSERT / DELETE / UPDATE / ROLLBACK 都会改变 `row_id`↔行 的对应
（追加、压缩移位、LIFO 重插）。失效是常态而非例外，因此正确性不靠
「假设没人并发写」，而靠**临界区内复核 + 回退**：

- 复核 = 一次存在性检查 + 一次 PK 列比较（O(1)）。
- 复核失败的语义与「索引不存在」完全相同：走全表路径，
  该路径今天就是正确实现 —— 回退不引入新语义面。
- 复核在写锁内完成，因此不存在 TOCTOU：进入临界区后位置不会再变。
- **锁序规范（防死锁）**：索引 B+Tree 锁与 `write_state` 锁**永不嵌套**。
  方案 A 的取数路径是「取索引锁 → 解析 → 放索引锁 → 取写锁 → 复核」。
  复核只用写锁内的数据，不需要再回索引。实现 PR 必须带一条
  「索引锁内不取写锁、写锁内不取索引锁」的不变量注释 + 回归测试
  （两个连接并发 point-DELETE/INSERT 压同一表，断言无死锁且结果一致）。

### 残留代价

`Vec::remove(row_id)` 仍移动尾部所有行（O(rows) 的指针搬移，
20000 行 ≈ 160KB memcpy ≈ 10~20µs 量级），但**不再是谓词逐行求值**
（0.344ms 的主体）。预计单行 delete+insert @20k 从 0.472ms 降到
**~30-50µs** 量级（≈10~15×）。

### 风险面（A）

| 风险 | 缓解 |
|---|---|
| 复核-回退路径双实现漂移 | 回退就是现状函数，不新增第二份删除逻辑；测试覆盖「失效必回退」 |
| 锁序违反 → 死锁 | 上述不变量 + 并发回归测试 |
| `row_id: u32` 与 `usize` 下标转换 | 现有索引路径已有该转换惯例（`:2297` 等）；复核处断言越界即回退 |
| 多 `row_id`（#5213 后 `search_all`）| PK 等值定位只用 `search`（唯一索引单值）；非唯一索引形状本就走回退 |

## 2. 方案 B：行槽间接层（row slot indirection）

### 机制

`Vec<Record>` → `Vec<Option<Record>>`（槽位层）。删除 = 槽置 `None`
+ 记录空闲槽号（O(1)，**无搬移**）。`row_id` = 槽号，从此**稳定**：

- 索引里的 `row_id` 永不因其它行的增删而失效 → 方案 A 的
  「复核 + 回退」整套机制可以删除，索引定位天然正确。
- **Undo 简化**：`UndoOp::DeleteRow { row_idx }` 的 `row_idx` 变成槽号，
  ROLLBACK 直接把原值写回该槽 —— 「多行删除后 index 移位导致回放错位」
  这一承重墙问题从根上消失（现行 `write_path_scaling_5181.rs` 钉的
  正是这个脆弱性）。LIFO 顺序仍然保留（值层面 last-in/first-out），
  但不再有「哪个 index」的问题。
- 插入 = 追加新槽（新 `row_id`）或复用空闲槽（`row_id` 复用，见下）。
- 迭代/flush/快照：一律「按槽号序遍历、跳过 `None`」——
  **默认结果顺序（无 ORDER BY 的返回序）与今天逐字节一致**，
  flush 落盘顺序也不变。

### Q2：row_id 语义变化波及哪些测试/不变量

| 面 | 影响 |
|---|---|
| 所有 `rows.iter().enumerate()` 假设 row_id=下标 | 语义不变（槽号=下标），但「下标处必有行」的假设失效 → 全仓审计 `enumerate()`/`rows[i]` 直取点 |
| 迭代/SELECT 结果序 | 槽序=插入序（跳过洞）→ 不变；#5099 系列 undo/MVCC/trigger 接线测试是主爆炸半径 |
| flush / 快照 | `flush_buffer`（`:4642`）/`flush`（`:1858`）写非空槽；快照若按行快照需补「快照含洞」语义 |
| MVCC 墓碑 | #5099 系列引入的 tombstone 若以 row_id 为键 → 槽稳定反而使其更正确；若以「第 N 行」为语义 → 需改 |
| `row_id` 单调性 | 空闲槽复用会破坏「row_id 随时间单调增」。若任何代码/外部依赖该性质，改为只追加不复用（代价：洞永久占内存，需 flush 压实 + 重发 row_id —— 又回到搬移问题；**建议：不复用，flush 时压实并整体重发索引**，与今天 flush 重写索引同构） |
| 内存 | `Option<Record>` 与 `Record` 等大（Record 远大于 niche 位），无额外代价 |

### 风险面（B）

改动面 = 整个行存储层（增删改查/flush/快照/undo/索引重发），
是 A 的 5~10 倍工作量与回归面；但换来「row_id 永久稳定 + undo 简化」
的结构性正确性，且把 A 的锁序/复核机制变成不必要的复杂度。

## 3. Q3：第三条路

| 路径 | 结论 |
|---|---|
| `HashMap<PK, row>` 分片存储 | **否决**。默认结果序 = 行向量序是承重语义，HashMap 丢序；保序需旁路顺序结构 → 双份账本 + 双份 undo，复杂度 ≥ B 而无 B 的稳定性收益 |
| 只优化 insert_buffer 路径 | **否决**。buffer 是事务局部，O(事务大小)≈O(1)；0.472ms 的 0.344ms 全部在 `tables` 侧。收益≈0 |
| （备注）append-only 墓碑：删 = 打洞不搬移，flush 时压实 | 本质是 B 的无槽复用变体，归入 B 的决策 |

**推荐：A 先行，B 作文档化后续。**
A 是单函数改动面（`remove_matching` 调用点 + 复核 + 回退），可独立验证、
可独立回滚；A 落地后重测，若搬移成本（~10-20µs @20k）仍显著
（表规模上去之后必然），B 的动机就变成「消灭搬移」而非「消灭遍历」，
决策更干净。B 不做「顺手」，只按本节风险表立项做。

## 4. Q4：量化预期（成本模型，非承诺）

- 单行 delete+insert @20k：0.472ms → 模型 **~30-50µs**（O(log N) 定位
  + O(rows) 指针搬移），≈ **10~15×**（删除半 0.344ms → ~15µs）。
- sysbench @10k（1242~1367 QPS，~740µs/tx）：写路径遍历是 tx 内
  两个 delete+insert + 一个 index update 的主体；模型预期 **1.8~2.3×**
  （~1500-2200 QPS 量级）。**这是模型值**：
  - 必须用 #5183 更正后的干净测量法复测（防 client 侧污染）；
  - 锁、WAL、JSON 序列化等固定成本会吃掉一部分增益；
  - 验收建议钉「@10k 单行 delete+insert ≤ 100µs」与「@100→10000
    删除代价增长 < 3×」两条可复现断言（照 #5209 的验收测试写法）。
- 值得做吗：**A 值得**（改动面有界、回滚干净、10~15× 单操作收益）；
  B 等 A 的复测数据说话。

## 5. 风险清单（合并视图）

1. **顺序承重墙**：默认结果序 + undo index 回放依赖行向量序 —— A 不动它；
   B 用「槽序遍历」保它，需全仓审计直取下标点。
2. **锁序**：A 引入「索引锁 →（放）→ 写锁」序列，必须钉死不嵌套（死锁风险）。
3. **row_id 稳定性假设扩散**：B 落地前，任何新代码不得假设
   「row_id 查出来永远有效」（现状即不保证）；B 落地后此假设才成立，
   届时可删 A 的复核 —— **A 的复核代码带 `// superseded by #5188-B` 标注**。
4. **u32 溢出**：`row_id: u32`，槽/行规模 > 4.29e9 才溢出（现状同限，非新增）。
5. **测量可信度**：Q4 全部数字须用更正后方法复测（#5183 教训）。
6. **实现时机**：#5167（正确性）未落地前不动写路径 ——
   正确性缺陷未闭环时性能改动的回归成本不对称。
