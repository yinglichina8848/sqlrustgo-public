## 概述

本轮迭代修的是 `scripts/sync/5remotes_sync.sh` 的挂死。修的过程中暴露了 4 条教训，
前两条指向同一个方法论错误：**把「症状」当成了「根因」**，
后两条指向**检测器自身也会骗人**。

## Lesson-01: 「不可达」与「挂起」是两种完全不同的故障

### Observation

同步脚本挂死 900s。上一轮会话据此在 lessons 里写下结论：
**「github / gitee / gitcode 三个远端在本机 SSH 不可达」**。

本轮实测：三个远端 **全部认证成功**。上一轮的结论是错的。

### Root Cause

「挂起」和「不可达」在日志里长得一模一样——都是「没有输出」。

但它们的成因完全相反：

| | 不可达 | 挂起 |
|---|---|---|
| TCP 22 | 拒绝 / 超时 | **连通** |
| SSH banner | 收不到 | **收得到** |
| 报错 | `Connection refused` / `Could not resolve` | **无任何输出** |
| 成因 | 网络 / 路由 / 防火墙 | 对端在等我们，等一个永远不来的应答 |

本例的挂起点是 **ssh-agent**：agent 已死但 socket 文件还在，
unix socket 的语义是「文件存在即认为可连」，于是 `connect()` 不失败，
ssh 阻塞在 agent 往返上。

### Impact

- 错误的结论被写进了 lessons 文档，会持续误导后续会话
- 更糟的是：这个错误结论让「修远端可达性」这个方向被彻底放弃，
  而真正的问题（工具自身不健壮）根本没被提上日程

### Mitigation

**「没有输出」不能证明「连不上」。** 判定顺序必须是：

1. `nc -z -G 5 <host> 22` —— TCP 通不通
2. `ssh -v` —— 有没有收到 `Remote protocol version` banner
3. 收到了 banner 但卡在 auth → **问题在本地认证状态**，不是网络
4. 认证方式逐项二分（`IdentityAgent=none` / `IdentitiesOnly=yes` / `BatchMode=yes`）

### Future Prevention

- 任何「某主机不可达」的结论，必须附带 **TCP 层证据**（`nc -z` / `ssh -v` 的 banner 行），
  缺证据就标注为「未验证」
- 会话结束前，回头核对上一轮写进 lessons 的**事实性断言**——
  lessons 是会被后续会话当既成事实引用的

## Lesson-02: 工具不能继承调用方的隐式环境状态

### Observation

同步脚本在自己机器上挂死，在别的机器上正常。

### Root Cause

脚本的 ssh 调用没有指定 `IdentityAgent=none`，于是继承调用方的 `SSH_AUTH_SOCK`。
而 `SSH_AUTH_SOCK` 的健康状态**不属于脚本能控制的范围**——它是用户会话级的隐式状态。

同一个道理适用于：`GIT_SSH_COMMAND`、`GIT_ASKPASS`、`SSH_AUTH_SOCK`、
`http_proxy`……凡是「调用方可能设了，也可能没设，而且设了会改变行为」的环境变量。

### Impact

- 脚本在 A 机器上能跑、在 B 机器上挂起，而两者之间**没有代码差异**
- 更糟的是这被误诊成了「远端有问题」，于是去改远端、改网络、改权限——
  全都不是问题所在

### Mitigation

**凡是会改变行为的隐式输入，工具要么显式接管，要么显式拒绝继承。**

本例的做法：脚本自己设 `GIT_SSH_COMMAND`（调用方已设则尊重调用方），
并在所有 ssh 调用上显式关掉 agent。

### Future Prevention

写自动化工具时列一张「隐式输入清单」：
`SSH_AUTH_SOCK` / `GIT_SSH_COMMAND` / `GIT_ASKPASS` / `GIT_CONFIG` /
`GIT_TERMINAL_PROMPT` / `http_proxy` / `HOME` / `XDG_CONFIG_HOME`……
每一条都要问：**这个变量被设成坏值时，我的工具会挂死吗？**

## Lesson-03: 检测器必须用「行为替身」，不能只匹配文本

### Observation

回归测试最初用一个 stub `ssh` 来验证「脚本不会挂起」。

### Root Cause

如果 stub 只是「记录参数然后返回 0」，那么测试只能证明**脚本文本里写了某个选项**，
不能证明**脚本在这个环境下不会挂**。两者在真实环境里可能分道扬镳。

本例中，只有当 stub **忠实模拟真 ssh 的阻塞条件**
（`SSH_AUTH_SOCK` 非空 且 参数缺 `IdentityAgent=none` → 阻塞），
测试才真正具有鉴别力。

### Impact

一个「检查脚本文本里有没有 `IdentityAgent=none`」的测试，
在有人把这一行删掉时可能依然通过——脚本在真实环境里立刻重新挂死。

### Mitigation

**替身要复现被测行为，不是复现被测实现的表面。**

具体做法：stub 的判定条件直接抄自真 ssh 的行为差异
（`SSH_AUTH_SOCK` 非空 + 缺 `IdentityAgent=none` → 阻塞），
而不是抄自「脚本应该长什么样」。

配套：再写一个**变异脚本**，逐个把关键结构改回去，要求每一种都必须被抓住。

### Future Prevention

- 任何「断言脚本文本」的测试，都要问：*删掉这行，真实系统会坏吗？*
  如果会，那测试必须换成行为替身
- 变异脚本进仓库，和测试一起跑

## Lesson-04: 变异存活先怀疑夹具，再怀疑实现

### Observation

MUT-3（删掉 `GIT_SSH_COMMAND` 的 export）**存活**了——测试仍然通过。

### Root Cause

静态检查写的是 `grep GIT_SSH_COMMAND`，命中的是**注释里提到该变量名的文字**。
删除真正的 `export` 语句，注释还在，检查照样通过。

同类问题还有两处：
- 扫描 1 的关键词匹配**区分大小写**（`TOKEN` vs `token`）→ 漏报了真实的 token 赋值
- 扫描 1 最初把 git commit SHA（纯 40 位十六进制）也当成凭据 → 大量误报

### Impact

一个「有鉴别力的测试」在第一版其实是**没有鉴别力的**——
它看起来在检查，实际什么都没检查。

误报同样有害：如果门禁一上来就报 50 条误报，人会开始习惯性地忽略它，
真正的泄露淹没在噪声里。

### Mitigation

**变异存活时，先怀疑测试自己。** 具体顺序：

1. 变异是不是真的被应用了？（看 diff）
2. 夹具/检测器是不是命中了**注释、占位符、其它合法内容**？
3. 匹配条件是不是**大小写敏感**、**长度不足**、**缺少上下文限定**？

收紧手段（本例）：
- 匹配**代码行**而不是全文（排除注释）
- 要求同行出现**凭据关键词**（排除 git SHA）
- 要求**至少 16 位十六进制且含非零字符**（排除全零占位符与短词）
- 大小写用 `-i` 覆盖（BSD grep 的 `-E` 不支持 `(?i)` 修饰符）

### Future Prevention

- 门禁脚本上线前，先**注入已知违规样本**验证它真的会红——空过的门禁比没有门禁更危险
- 门禁脚本**自身**要进变异验证清单
- 检测器里不要写任何被检测的字面量（否则检测器自己就成了新的泄露点）
