# ADR-011: v3.8.0+1 TX+WAL Repair Strategy

## Status

**Accepted** — v3.8.0+1 (target: 2026-08-30)

## Context

v3.8.0 GA 通过 ADR-006 defer 12 个 TX+WAL contract gap：
- 19/31 PASS / 12 FAIL
- 4 TX-Lifecycle (EEK v0 strict mode)
- 8 WAL Recovery (multi-tx ordering + partial-write)

ADR-007 (WAL architecture) 4 decisions 已 accepted (2026-06-03)：
- Decision-1: DDL 走 WAL
- Decision-2: `is_wal_enabled()` 公开
- Decision-3: DDL bypass 策略 (production 拒绝 / migration 允许)
- Decision-4: Read-only 模式 DML 返回 Err

ISSUE-2740 (Crash Recovery Empirical) 已 closed (PR #2780)。

**所有前置就绪**，需要规划 v3.8.0+1 实施。

## Decision

**v3.8.0+1 修复 12 gap，9 周时间表**：
- Phase A: TX-Lifecycle dual-mode（3 周）
- Phase B: WAL Recovery 严格 ordering（4 周）
- Phase C: Integration + GA（2 周）

### Decision-1: TX-Lifecycle dual-mode 设计

**默认（autocommit）**：保持当前行为，不破坏 19/19 PASS + 8/8 e2e。
**严格（`SQLRUSTGO_EEK_MODE=strict`）**：DML without active tx → `TransactionLifecycleErr`。

```rust
// crates/transaction/src/manager.rs
pub fn execute_dml(&mut self, stmt: &Statement) -> Result<...> {
    if self.read_only && is_dml_statement(stmt) {
        return Err(TransactionError::ReadOnly);
    }
    if is_hek_strict_mode() && !self.has_active_tx() && is_dml_statement(stmt) {
        return Err(TransactionError::Lifecycle);
    }
    // ... normal path
}
```

### Decision-2: WAL Replay Order 严格 LSN

**当前**：FIFO based on append order
**修复**：Strict LSN-based ordering + 二次 undo log

```rust
// crates/storage/src/wal_storage.rs
impl<S, T> WalStorage<S, T> {
    pub fn log_undo(&mut self, tx_id: TxId, lsn: Lsn) -> SqlResult<()> {
        // Write undo log entry with strict LSN order
    }
}

// crates/storage/src/recovery_engine.rs
impl RecoveryEngine {
    pub fn replay(&mut self) -> SqlResult<()> {
        // 1. Replay forward (LSN ascending)
        // 2. Replay undo for uncommitted tx (LSN ascending)
        // 3. Atomic partial-write recovery
    }
}
```

### Decision-3: 不退化保证

**3 层防御**：
1. **dual-mode**（TX-Lifecycle）— opt-in strict
2. **分步 PR**（WAL Recovery）— 每步独立 gate
3. **baseline 锁**（22 个现有 test 必须保持绿色）：
   - 19/31 contract test
   - 5/5 `exp_g_wal_contracts_verified`
   - 8/8 `e2e_trigger_wal_recovery`（含 T-001/002/003）
   - 22/22 RECOVERY-001~008（`tests/wal_integration_test.rs`）

### Decision-4: 时间表 + 风险预案

```
9 周（2026-07-01 ~ 2026-08-30）
├── Phase A (3w): TX-Lifecycle dual-mode
├── Phase B (4w): WAL Recovery
└── Phase C (2w): Integration + GA
```

**应急**：
- Phase B 延期到 v3.8.0+2：保留 Phase A 单独发布
- 部分 gap 暂留 KNOWN_GAP：诚实文档化（参考 ISSUE-2743）

### Decision-5: 与 v3.9 MVCC 关系

v3.8.0+1 不实现 MVCC。MVCC 推迟到 v3.9.0。
但 v3.8.0+1 的 undo semantics 为 MVCC 打基础：
- WAL undo log → v3.9 MVCC version chain
- Read-only mode → v3.9 snapshot isolation

## Consequences

### Positive

1. **31/31 contract tests PASS** — 完整 TX+WAL contract
2. **不破坏 22 个 baseline test** — 严格不退化
3. **MVCC 基础就绪** — v3.9 路径清晰
4. **诚实规划** — POST_GA_PLAN.md 完整

### Negative

1. **9 周时间** — 不算短
2. **WAL 改动风险大** — 分步 PR 缓解
3. **dual-mode 复杂度** — 2 套行为

### Risks

- **R-1**：Phase B WAL 改动可能引入崩溃恢复 bug
- **R-2**：dual-mode 增加配置复杂度
- **R-3**：22 baseline test 中某些可能因架构变化而 FAIL
