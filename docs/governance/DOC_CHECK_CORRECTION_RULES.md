# 文档检查与纠正规则

> **版本**: v1.0.0
> **日期**: 2026-05-30
> **适用范围**: SQLRustGo 所有版本发布文档、日常文档维护
> **维护人**: Hermes Agent
> **状态**: 强制执行

---

## 一、背景与目的

本规则旨在为文档检查与纠正工作建立**标准化、可追溯、可撤销**的工作流程。

防止以下问题：
- AI 事后编造文档内容（Type C 伪证据）
- 过度修改原始记录（违反最小修改原则）
- 修改后无复核造成错误扩散
- 工作记录缺失导致无法审计

---

## 二、核心原则

### 2.1 最小修改原则

修改文档时，只允许修改**事实性错误**：
- 版本号错误
- 日期错误
- 状态标记错误（Alpha/Beta/GA）
- 重复条目（同一 commit 出现两次）
- 缺少必要条目（版本历史表缺少自身版本）

**禁止**修改：
- commit 日志内容
- 功能描述
- 架构设计内容
- 任何实质性的技术内容

### 2.2 证据优先原则

任何状态声明必须有对应证据：
- 版本 GA 状态 → CHANGELOG.md 头部或 GA_GATE_REPORT.md
- 日期 → git log 或 release tag
- 文档存在性 → 文件系统验证

### 2.3 可撤销原则

所有修改必须满足：
- 修改前先 `git stash` 或确认当前修改已 `git add`
- 每一步修改都有 git diff 记录
- 新增文件使用 `git add` 暂存
- 可通过 `git checkout -- <file>` 恢复到修改前状态

---

## 三、工作流程（5 步标准流程）

### 步骤 1：发现问题

**操作**：
1. 读取目标文档（README.md、CHANGELOG.md 等）
2. 交叉验证版本号/日期/状态与相关文档的一致性
3. 列出所有发现的问题，注明行号和具体错误内容

**输出格式**：

| # | 文件 | 问题 | 位置 | 依据 |
|---|------|------|------|------|
| 1 | v3.7.0/CHANGELOG.md | 重复 commit | 第27-28行 | 同一 commit `b925f438` 出现两次 |

**工具**：
- `read` — 读取文档
- `grep` — 搜索版本号/状态标记
- `bash ls` — 验证文件存在性

---

### 步骤 2：编写文档改正计划和复核审查 Checklist

**操作**：
1. 撰写《文档改正计划》，包含：
   - 问题清单（步骤 1 的输出）
   - 修改原则说明
   - 每项修改的具体操作（oldString → newString）
   - 预期结果
2. 编写《复核审查 Checklist》，包含：
   - 每项修改的验证点
   - 无新增问题检查
   - 链接有效性检查

**输出格式**：

**《文档改正计划》**：

| # | 操作 | 文件 | 说明 |
|---|------|------|------|
| 1 | 删除重复行 | v3.7.0/CHANGELOG.md | 删除第28行重复的 `b925f438` |
| 2 | 添加版本表条目 | v3.7.0/CHANGELOG.md | 在 v3.6.0 前插入 v3.7.0 |

**《复核审查 Checklist》**：

- [ ] 问题 1 已修复：无重复 commit
- [ ] 问题 2 已修复：版本表包含 v3.7.0
- [ ] 修改量合理：无过度修改
- [ ] 链接有效：所有引用的 .md 文件存在
- [ ] git diff 干净：无非预期修改

---

### 步骤 3：执行文档改正计划

**操作**：
1. 每项修改使用 `edit` 工具执行
2. 每项修改后记录执行的 git diff
3. 如新增文件，编辑后立即 `git add` 暂存

**输出**：
- git diff 片段（每项修改后）
- 修改的文件清单

---

### 步骤 4：根据 Checklist 核查

**操作**：
1. 逐项执行 Checklist
2. 每项核查结果记录到工作记录
3. 如发现问题，标记并回退到上一步骤

**输出**：

| 检查项 | 结果 |
|--------|------|
| 问题 1 已修复 | ✅ 通过 |
| 问题 2 已修复 | ✅ 通过 |
| 无新增问题 | ✅ 通过 |

---

### 步骤 5：编写完整的文档检查和纠正工作报告

**操作**：
1. 整理所有工作记录
2. 输出《文档检查和纠正工作报告》

**《工作报告》必须包含**：

```markdown
# 文档检查和纠正工作报告

## 一、基本信息
- 工作时间：
- 执行人：
- 工作范围：

## 二、发现的问题

| # | 文件 | 问题 | 依据 |
|---|------|------|------|

## 三、执行的操作

| # | 文件 | 修改内容 | 依据 |
|---|------|----------|------|

## 四、复核检查结果

| 检查项 | 结果 |
|--------|------|

## 五、待提交文件状态

## 六、发现的问题（，如有）

## 七、结论
```

## 四、复核审查 Checklist（标准化模板）

### 4.1 修改正确性

- [ ] 问题 1 已修复
- [ ] 问题 2 已修复
- [ ] 问题 N 已修复

### 4.2 无过度修改

- [ ] commit 日志内容未被修改
- [ ] 功能描述未被修改
- [ ] 实质性技术内容未被修改

### 4.3 链接有效性

- [ ] 所有引用的 `.md` 文件已验证存在
- [ ] 所有引用的文件路径正确

### 4.4 git 状态

- [ ] git diff 无非预期修改
- [ ] 新增文件已 `git add`
- [ ] 修改文件已 `git add`

### 4.5 可撤销性

- [ ] 所有修改可通过 `git checkout -- <file>` 恢复
- [ ] 工作记录完整，可追溯每一步

---

## 五、证据链要求

### 5.1 必须保存的证据

1. **修改前状态**：`git stash` 或修改前的 `git diff`
2. **每步修改**：`git diff` 输出
3. **文件存在性**：`ls` 命令输出
4. **链接验证**：`ls <path>/<file>.md` 命令输出

### 5.2 禁止的行为

- 禁止无证据的状态声明（"测试通过"、"门禁通过"）
- 禁止无 provenance 的文档生成
- 禁止删除原始记录
- 禁止无 Checklist 核查的修改
