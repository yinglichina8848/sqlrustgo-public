# #4218 Phase 2 — FileStorage View Persistence + Connection Registry

**Status:** Approved (brainstorming → implementation)
**Date:** 2026-08-14
**Iteration:** 2026-08-14 (V312-35 follow-up)
**Issue:** #4218 (StorageEngine trait API surface drift)

## Background

Phase 1 (#4218 commit `fcc9858eb`) added trait method declarations and
Statement enum variants for:

- `StorageEngine::create_view / drop_view / list_views / get_view`
- `StorageEngine::set_cancel_flag / check_cancelled`
- `StorageEngine::kill_connection / list_processes + ProcessInfo struct`
- `Statement::KillConnection { conn_id, is_query }`
- `Statement::ShowProcesslist { full }`

All implementations are no-op defaults. `ExecutionEngine::execute_*`
already routes through the trait, but the trait does nothing for
non-memory engines, so FileStorage behaviour is unchanged (views lost
on restart, KILL not supported, SHOW PROCESSLIST returns empty).

This Phase 2 wires the trait into `FileStorage` with disk persistence
for views and a server-side connection registry for KILL/SHOW
PROCESSLIST. Removes the `ExecutionEngine::views` shadow copy now
that the trait is the single source of truth.

## Goals

1. Views survive server restart (disk persistence)
2. `KILL CONNECTION <id>` actually cancels a peer session
3. `SHOW [FULL] PROCESSLIST` returns real session metadata
4. `ExecutionEngine::views` shadow copy is gone (single source of truth)
5. Zero regression on existing view tests (`view_procedure_trigger_e2e_test`,
   `wire_smoke_mysql_cli`, etc.)

## Non-Goals

- Multi-tenant view isolation (per-database view directories)
- Replacing JSON with bincode (cosmetic; revisit if perf matters)
- Binary protocol wire format for `SHOW PROCESSLIST` (text protocol only)
- Session-level query-only cancel (`KILL QUERY`) — engine-level cancel
  for now, treat both as `kill_connection(conn_id)`

## Components

### 1. `crates/storage/src/file_storage.rs` — view persistence

```rust
fn views_dir(&self) -> PathBuf {
    self.data_dir.join("views")
}

fn view_path(&self, name: &str) -> PathBuf {
    self.views_dir().join(format!("{}.json", name))
}

fn atomic_write(path: &Path, bytes: &[u8]) -> io::Result<()> {
    let tmp = path.with_extension("json.tmp");
    fs::write(&tmp, bytes)?;
    fs::rename(&tmp, path)?;
    Ok(())
}

impl StorageEngine for FileStorage {
    fn create_view(&mut self, info: ViewInfo) -> SqlResult<()> {
        fs::create_dir_all(self.views_dir())?;
        let json = serde_json::to_vec(&info)
            .map_err(|e| SqlError::ExecutionError(format!("view encode: {}", e)))?;
        atomic_write(&view_path(&info.name), &json)
            .map_err(|e| SqlError::IoError(format!("create_view: {}", e)))?;
        Ok(())
    }

    fn drop_view(&mut self, name: &str) -> SqlResult<()> {
        let path = self.view_path(name);
        match fs::remove_file(&path) {
            Ok(()) => Ok(()),
            Err(e) if e.kind() == io::ErrorKind::NotFound => Ok(()),
            Err(e) => Err(SqlError::IoError(format!("drop_view: {}", e))),
        }
    }

    fn list_views(&self) -> Vec<String> {
        fs::read_dir(self.views_dir())
            .map(|entries| {
                entries
                    .filter_map(|e| e.ok())
                    .filter_map(|e| e.file_name().into_string().ok())
                    .filter(|n| n.ends_with(".json") && !n.ends_with(".tmp"))
                    .map(|n| n.trim_end_matches(".json").to_string())
                    .collect()
            })
            .unwrap_or_default()
    }

    fn get_view(&self, name: &str) -> Option<ViewInfo> {
        let path = self.view_path(name);
        fs::read(&path).ok().and_then(|bytes| {
            serde_json::from_slice::<ViewInfo>(&bytes).ok()
        })
    }
}
```

### 2. ConnectionRegistry (server-side)

`crates/mysql-server/src/registry.rs` (new file):

```rust
use std::sync::atomic::AtomicU64;
use std::sync::{Arc, Mutex, Weak};
use sqlrustgo_storage::engine::ProcessInfo;

pub trait Session: Send + Sync {
    fn cancel(&self);
    fn info(&self) -> ProcessInfo;
}

#[derive(Default)]
pub struct ConnectionRegistry {
    inner: Mutex<HashMap<u64, Weak<dyn Session>>>,
    next_id: AtomicU64,
}

impl ConnectionRegistry {
    pub fn register(&self, session: Arc<dyn Session>) -> u64 {
        let id = self.next_id.fetch_add(1, Ordering::Relaxed) + 1;
        self.inner.lock().unwrap().insert(id, Arc::downgrade(&session));
        id
    }
    pub fn unregister(&self, id: u64) {
        self.inner.lock().unwrap().remove(&id);
    }
    pub fn cancel(&self, id: u64) -> SqlResult<()> {
        let session = self.inner.lock().unwrap()
            .get(&id).and_then(|w| w.upgrade())
            .ok_or_else(|| SqlError::ExecutionError(
                format!("Unknown connection id: {}", id)
            ))?;
        session.cancel();
        Ok(())
    }
    pub fn snapshot(&self) -> Vec<ProcessInfo> {
        self.inner.lock().unwrap()
            .values()
            .filter_map(|w| w.upgrade())
            .map(|s| s.info())
            .collect()
    }
}
```

`FileStorage::new` accepts an `Arc<ConnectionRegistry>` so it can forward
kill/list. `kill_connection` / `list_processes` call into it.

## Data Flow

### CREATE VIEW

```
parser → Statement::CreateView(view)
  ↓
ExecutionEngine::execute_create_view(view)
  ↓
storage.create_view(ViewInfo { name, columns, definition })
  ↓
FileStorage: atomic_write(<data_dir>/views/<name>.json)
```

### KILL CONNECTION

```
COM_KILL dispatch (lib.rs)
  ↓
ExecutionEngine::execute_kill_connection(conn_id, is_query)
  ↓
storage.kill_connection(conn_id)
  ↓
FileStorage: registry.cancel(conn_id)
  ↓
Session.cancel() → engine.set_cancel_flag(true)
  ↓
next execute_*() checks check_cancelled() → Err if true
```

### SHOW PROCESSLIST

```
COM_QUERY dispatch
  ↓
ExecutionEngine::execute_show_processlist(full)
  ↓
storage.list_processes()
  ↓
FileStorage: registry.snapshot()
  ↓
Vec<ProcessInfo> → 7-8 column result set (Id, User, Host, db, Command,
                                  Time, State[, Info])
```

## Error Handling

| Scenario | Behaviour |
|----------|-----------|
| `create_view` write fails (disk full, EROFS) | `SqlError::IoError`, tx rollback |
| `drop_view` file missing + `IF EXISTS` | silent success (matches MySQL) |
| `drop_view` file missing without IF EXISTS | `SqlError::ExecutionError("View not found: <name>")` |
| `kill_connection` unknown id | `SqlError::ExecutionError("Unknown connection id: <id>")` |
| `kill_connection` on session whose Weak ptr expired (already dropped) | `SqlError::ExecutionError("Connection already closed: <id>")` |
| `list_processes` no active sessions | empty `Vec<ProcessInfo>` (SHOW returns 0 rows) |
| `create_view` file exists + replace semantics (CREATE OR REPLACE) | overwrite via atomic_write — already supported via the `replace` boolean in CreateViewStatement |

## Risks & Mitigations

1. **WAL replay interaction**: views are written outside WAL transactions
   (per-file, atomic rename). After crash, views from <data_dir>/views/
   are authoritative. WAL does not need view redo/undo logic.

2. **Concurrent CREATE OR REPLACE**: atomic_write via tmp + rename
   guarantees one writer wins; readers may briefly see ENOENT during
   the rename but `get_view` returns `Option<ViewInfo>` and falls
   through to "view not found" without crashing.

3. **ConnectionRegistry contention**: `Mutex<HashMap>` is fine for
   single-digit active connections (test scenario). For production
   server with hundreds of connections, consider `DashMap` in a
   follow-up — out of scope for v3.12.

4. **Phase 1 commit not pushed**: Gitea 252 was down when Phase 1
   finished. Phase 2 must wait for Phase 1 to land before merge to
   avoid trait-method-not-found errors on develop HEAD. Use `git
   log --oneline develop..HEAD` to verify before pushing Phase 2.

## Out of Scope

- View privileges (`GRANT SELECT ON view TO user`) — orthogonal to this issue
- Materialised views (no auto-refresh) — separate issue
- View column type validation against underlying tables — deferred
- `KILL QUERY` (cancel in-flight query only, leave connection alive) —
  current impl cancels whole connection; MySQL semantics say both
  variants exist but our engine-level cancel is session-wide.
