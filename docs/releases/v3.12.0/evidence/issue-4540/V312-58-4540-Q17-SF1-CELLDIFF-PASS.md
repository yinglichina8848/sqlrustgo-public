## Cell-diff comparison

The oracle reference value for TPC-H Q17 SF=1 is the canonical `249963.75857142857` (per `docs/releases/v3.9.0/perf/TPC_H_SHA256_BASELINE_20260612.md`).

| Field | Oracle | sqlrustgo | Delta |
|-------|--------|-----------|-------|
| Value (full precision) | `249963.75857142857` | `249963.75857142854` | 2.91e-11 |
| Relative error | — | — | 1.16e-16 |
| FLOAT_TOL threshold | 1e-3 | 1e-3 | — |

The 2.91e-11 delta is **FP64 representation noise** — the canonical reference value `...2857` and our result `...2854` differ by 3 ULP (units in last place) at the 14th decimal place. This is the well-known TPC-H float-rounding artifact that `q17_small_order_shortage_perf.rs` accounts for via `FLOAT_TOL = 1e-3`. Our diff is ~34 million times tighter than the tolerance.

| Hash format | sha256 |
|-------------|--------|
| Oracle (TPC-H canonical `%.20f`) | `a0ea4dbaf91831477f75479760e114684a89974ade4bd28243327f96a54b1ef4` |
| sqlrustgo (`.20f`) | `c2057f01178ff7fb46adc2c158e3e90dd3dff5c5ce9f7a81ef530c7ac0dc66d6` |
| Oracle `%.2f` | `ac31d6bc6d9d40ed5a93ed2932059122e6c08327c4b3433da39b240da52e125c` |
| sqlrustgo `%.2f` | `ac31d6bc6d9d40ed5a93ed2932059122e6c08327c4b3433da39b240da52e125c` |

Note: The `%.2f` hashes **match exactly** (`ac31d6bc...`). The full-precision hashes differ because the underlying values differ in the 14th decimal place — this is expected FP64 behavior, not a semantic difference. The regression test's `assert!((value - expected).abs() < FLOAT_TOL)` is the correct cell-diff check for this query class.

## Why this works (root cause + fix trace)

### Root cause (pre-fix, per `evidence/v312-58/issue-4379-sprint3-partial-closure.md`)

Q17's WHERE clause has a correlated scalar subquery:

```sql
... AND l_quantity < (SELECT 0.2 * AVG(l_quantity) FROM lineitem WHERE l_partkey = p_partkey)
```

Pre-fix executor detected the correlation but re-evaluated the subquery **per outer row** with no materialization — for SF=1's ~30K candidate parts × 6M lineitem scan, this is ~180B operations → >1800s TIMEOUT confirmed in `V312-58-Q17-VERIFICATION.md` (2026-08-23, commit `10d6f489d`).

### Fix pipeline (now shipped to develop/v3.12.0)

| Phase | Component | PR/Commit | Mechanism |
|-------|-----------|-----------|-----------|
| Phase 1 | Pattern detection `find_correlated_equalities` → `ScalarAggInWhere` | PR #4449 | Recognize `WHERE col CMP (SELECT agg FROM ... WHERE col=outer.col)` |
| Phase 2 | Materialization driver `build_scalar_agg_index` + `try_scalar_agg_index_lookup` | PR #4450 | Build per-partkey agg index, look up scalar literal per outer row |
| Phase 3 | HashSemiJoin wiring | commit `3b6634a7d0` | Replace correlated-equality with hash-join on the materialized index |
| Sprint 4 Step 1.5/1.6 | `residual_has_subquery` gate | PR #4453 | Detect when residual carries nested Subquery/Exists → fall through to slow path that DOES recurse via Subq-ARM |

### DIAG proof of fix engagement (from `q17_sf1_diag.log`)

```
try_scalar_agg_index_lookup calls=4800 hits=4800 pattern_fail=0 build=1
step15 entered=1 has_correlated=1
```

- `calls=4800 hits=4800`: scalar-agg index consulted 4800 times, 100% hit rate
- `pattern_fail=0`: pattern detector never bailed (vs prior 100K subset's known issue)
- `build=1`: exactly one scalar-agg index materialized (per-partkey AVG, single GROUP BY pass over 6M lineitem ≈ 24s)
- `step15 entered=1 has_correlated=1`: Sprint 4 routing gate fired and confirmed correlated path engaged

**Wall-clock decomposition** (from the diag log):

| Phase | Time |
|-------|------|
| part.tbl bulk load (200K rows) | 0.55s |
| lineitem.tbl bulk load (6M rows, 760 MB) | 23.93s |
| scalar-agg index build (single GROUP BY over 6M lineitem) | ~30s (estimated from elapsed − load − exec) |
| Q17 outer join + filter + projection | ~7s (estimated) |
| **Total Q17 elapsed** | **61.65s** |

The dominant cost is now the single full scan of `lineitem` to build the scalar-agg index (~24s load + ~30s groupby) instead of the original 30K × 6M correlated re-evaluation (~180B ops). The 61.6s is consistent with the **subquery-materialization** strategy described in §"Fix strategy (proposed)" of `V312-58-Q17-VERIFICATION.md` — except the implementation went through `ScalarAggInWhere` + `try_scalar_agg_index_lookup` rather than a derived-table rewrite.
