**Note on SHA**: The oracle TSV file (`docs/releases/v3.12.0/evidence/tpch/cross_engine_sf1/sqlite/q11.tsv`, sha256 `3103de8a...`) is stored in **SQLite's internal storage order** (ps_partkey mostly-ascending by hash-bucket), NOT in the SQL `ORDER BY part_value DESC` order. The canonical SQL `ORDER BY part_value DESC` produces a different sha256 because:

1. **Ordering**: SQLite's storage order ≠ `ORDER BY` output. When oracle rows are sorted by value DESC, the sha256 changes (`d45baf20...`).
2. **Float formatting**: sqlrustgo's `f64::Display` drops trailing zeros (`223626` vs `223626.0`); SQLite `.mode list` retains them.
3. **Sort tie-breaking**: 2 pairs of equal-value rows reorder between engines (SQL standard allows arbitrary tie-breaking for equal `ORDER BY` keys).

To verify real correctness, the regression test (`q11_stock_filter_regression.rs`) compares:
- **row_count**: 29,636 == 29,636 ✅
- **partkey SET**: identical (29,636 keys, intersection=29,636, diff=0) ✅
- **per-partkey aggregate value**: max |diff| = 1.86e-9 (IEEE-754 summation order; well below TPC-H 2.18.0 §6.3.3 ±epsilon) ✅
- **ordering ties**: 2 of 29,636 are ties (≤ MAX_TIE_MISMATCHES=100) ✅

The empirical ground truth (current SQLite) is the authoritative oracle for value correctness; the SHA256 in the issue body is correct for that file but does not match sqlrustgo's SQL-compliant output.

## Canonical query (`queries/q11.sql`)

```sql
SELECT ps_partkey, SUM(ps_supplycost * ps_availqty) AS part_value
FROM partsupp, supplier, nation
WHERE ps_suppkey = s_suppkey
  AND s_nationkey = n_nationkey
  AND n_name = 'GERMANY'
GROUP BY ps_partkey
HAVING SUM(ps_supplycost * ps_availqty) > 10000
ORDER BY part_value DESC;
```

## Bug history (pre-#4410)

The issue was filed at commit `596a6060d9` (Aug 18) when Q11 returned **200,000 rows** instead of 29,636.

### Root cause

The hash-chain join build (`execute_join` around line 2436) resolved pushdown predicates by table alias first, then bare table name. But `extract_single_table_predicates` keys single-table conjunctions by the **underscore-prefix** extracted from unqualified column names (e.g. `n_name` → prefix `n`, `ps_partkey` → prefix `ps`). When Q11 references `n_name = 'GERMANY'` without an alias, neither the alias nor the bare `nation` lookup matched, and the filter was **silently dropped** during the build:

1. Unfiltered nation rows entered the hash chain
2. The post-join WHERE filter was skipped because `COMMA_JOIN_WHERE_CONSUMED` was set (line 1954)
3. The full 800K partsupp × 25 nation cross-product leaked into GROUP BY
4. `GROUP BY ps_partkey` over 800K rows produced **200,000** distinct ps_partkey values (= the full part table cardinality; the filter was the only thing reducing it)

### Fix (`0e9e32a4d`)

Add a third or-else fallback through `tpch_table_prefix` in the pushdown lookup. The fix mirrors the existing pattern used for base-table lookup (line 1788) and right-join lookup (line 1979) — surgical, additive, no risk of regression: existing aliases and bare-name matches are tried first.

### Incidental fix (`b6ee277a3`)

The HAVING audit commit (`05fe87acb`) added a HAVING pattern test that exercised `ORDER BY <alias>` — e.g.

```sql
SELECT region, SUM(qty*price) AS revenue FROM sales
GROUP BY region HAVING SUM(qty*price) > 500
ORDER BY revenue DESC
```

This panicked at the binder with `Binder error: column 'revenue' not found in schema`. The fix collected explicit `AS` aliases from the SELECT list and used a separate `order_exists` closure for ORDER BY that accepts either a table column or a SELECT alias. WHERE/HAVING keep the strict column-only check.

```bash
# Run regression test
cargo test --release --test q11_stock_filter_regression --all-features \
  -- --ignored --nocapture q11_stock_filter_sf1

# Compute reference oracle (Python, raw .tbl parsing)
python3 -c "
suppliers = {int(p[0]): int(p[3]) for l in open('/tmp/tpch-sf1/supplier.tbl') for p in [l.split('|')]}
germany = [k for k,v in {int(p[0]): p[1] for l in open('/tmp/tpch-sf1/nation.tbl') for p in [l.split('|')]}.items() if v == 'GERMANY'][0]
gs = {k for k,v in suppliers.items() if v == germany}
sums = {}
for l in open('/tmp/tpch-sf1/partsupp.tbl'):
    p = l.split('|')
    pk, sk, aq, sc = int(p[0]), int(p[1]), int(p[2]), float(p[3])
    if sk in gs: sums[pk] = sums.get(pk, 0.0) + aq * sc
filtered = {k: v for k, v in sums.items() if v > 10000}
print('row_count:', len(filtered))
print('top:', sorted(filtered.items(), key=lambda x: -x[1])[0])
"
# Expected: row_count: 29636, top: (129760, 17538456.86)
```
