## 1. Scope

CLI-01 Stage 1 (PR-3042) added 7 new dot commands and a banner. Stage 2
(PR-3048) added a shared engine so CREATE/INSERT/SELECT see the same
catalog within one REPL session. **Stage 3** (this PR) closes the
remaining gap: state is still lost when the REPL exits, so the
practical cross-session workflow is broken.

### What this PR delivers

- ✅ **`repl --init-sql <file>`** — replay a SQL file at REPL startup
  (CREATE TABLE + INSERT statements, the bootstrap pattern)
- ✅ **`repl --save-on-exit <file>`** — wire the save-on-exit hook
  (currently writes a header-only placeholder; the real catalog dump
  requires exposing `engine.list_tables()` which is Stage 4 work)
- ✅ **`.source <file>`** now uses the same comment-aware replay path
  (previously a stale, per-statement-no-error loop that swallowed errors
  silently)
- ✅ 7 integration tests covering both happy and edge paths

### What this PR does NOT deliver (deferred to Stage 4)

- ❌ Full catalog dump via `dump_engine_to_sql` — requires
  `MemoryExecutionEngine` to expose a public `list_tables()` /
  `scan()` API. Currently the engine's storage is `Arc<RwLock<S>>`
  private, and the crate-level `ExecutorResult` enum is not
  pattern-matchable from outside the crate. Stage 4 will add the
  `pub fn list_tables(&self) -> Vec<TableInfo>` shim and a real
  CREATE TABLE + INSERT dump loop.
- ❌ Generic `ExecutionEngine<S: StorageEngine>` for FileStorage-backed
  REPL. The current REPL is hard-typed to `MemoryExecutionEngine`
  because that's what `make_shared_engine()` returns. Generalizing
  to `ExecutionEngine<S>` is a refactor that touches all REPL hot
  paths (dot commands, history, headers, timing). Estimated 1-2 days
  for the type plumbing alone.

## 2. Implementation Detail

### `--init-sql` (working)

```rust
fn run_repl(init_sql: Option<&str>, save_on_exit: Option<&str>) -> ... {
    let mut engine = make_shared_engine();
    if let Some(path) = init_sql {
        match replay_sql_file(&mut engine, path) {
            Ok(n) => println!("[init-sql] replayed {n} statements from {path}"),
            Err(e) => eprintln!("[init-sql] warning: {e}"),
        }
    }
    ...
}
```

`replay_sql_file` does:
1. Read the file
2. Split on `;`
3. For each statement, strip comment lines (`-- ...`) and blank
   lines, then trim. If anything real is left, execute it via
   `exec_with_engine_and_options` (the same path used for in-REPL
   statements, so it goes through the engine → catalog → storage
   pipeline correctly).
4. Count successful statements and return.

This is **identical to the way the in-REPL REPL processes
statements**, so there's no divergence between init-sql replay and
interactive input. The replay uses the same `exec_with_engine_and_options`
helper, which means errors propagate the same way (init-sql
warnings print but do not crash the REPL; per-statement success is
counted).

### `--save-on-exit` (wired, placeholder)

```rust
fn dump_engine_to_sql(engine: &MemoryExecutionEngine, path: &str) -> ... {
    let mut f = File::create(path)?;
    writeln!(f, "-- SQLRustGo v3.8.0-rc1 REPL state dump")?;
    writeln!(f, "-- Generated by dump_engine_to_sql")?;
    // The engine doesn't expose list_tables; Stage 4 will add this.
    Ok(0)  // returns 0 statements dumped
}
```

Currently writes a 76-byte placeholder file with a header. The
`dumped 0 statements` line in stdout is truthful about the
limitation.

The `engine: &MemoryExecutionEngine` parameter is already in place
so Stage 4 only needs to add `engine.list_tables()` access, not
re-plumb the function signature.

### `.source` (refactored to use replay_sql_file)

Before:
```rust
match std::fs::read_to_string(path) {
    Ok(content) => {
        for stmt in content.split(';') {
            if let Err(e) = exec_one(stmt) {  // exec_one = new engine each time!
                eprintln!("Error in {path}: {e}");
            }
        }
    }
    ...
}
```

This was **silently wrong** in the Stage 2 era: `.source` used
`exec_one` which created a fresh `MemoryExecutionEngine` per
statement. So `.source bootstrap.sql` would CREATE a table on
engine #1, then INSERT on engine #2, then SELECT on engine #3 —
all on different storages. The bootstrap file would be "successful"
but the resulting state was useless.

Now:
```rust
match replay_sql_file(engine, path) {
    Ok(n) => {
        println!("Executed {n} statements from {path}");
        DotResult::Continue
    }
    Err(e) => DotResult::Error(e),
}
```

Uses the same shared engine. State survives. Errors now propagate
as `DotResult::Error` so the user sees them instead of having them
swallowed.
