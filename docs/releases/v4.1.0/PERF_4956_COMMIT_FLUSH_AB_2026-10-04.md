1. 测量对象
--------------------------------------------------------------------------------
#4956 为修 #4946（autocommit INSERT 被确认后丢失），把

    if commit_lsn > 0 {
        self.inner_mut().flush()?;
    }

放进了 WalStorage::commit_transaction（crates/storage/src/wal_storage.rs:926），
使 flush 先于 WAL 截断。此前 flush 被推迟给调用方 / 后台清扫。

两侧二进制唯一差异就是这 3 行：
  after  = develop/v4.1.0 原样                          md5 b2a171b6740019f82b5ea54083b58791
  before = 同一棵树，删掉 `self.inner_mut().flush()?;`   md5 c54a560664803d4da4b3f06761d5a9aa

  编译: --release（lto=fat, codegen-units=1），同一 worktree 同一 toolchain
  补丁: evidence/PERF_4956_ab_patch.py（apply/revert 双向，逐字符匹配，匹配不唯一即拒绝）
  两二进制 md5 已确认不同；A/B 顺序按轮次交替（r1 after→before，r2 before→after，r3 after→before），
  以免单调的机器漂移被读成某一侧的效果。

--------------------------------------------------------------------------------
4. 结论
--------------------------------------------------------------------------------
1. **单行 OLTP 提交没有可测量的回归。** 这是本次最重要的结论，且与"flush 进了
   提交关键路径"的直觉相反。原因可从代码解释:FileStorage::flush 是增量的
   （drain_dirty_windowed 只快照 [last_saved..] 窗口，save_table_window 只写这一段），
   单行事务每次只有 1 行要落盘，固定开销吃掉了全部差异。
2. **批量事务确有 20~29% 的回归**，机制与上一点对称：1000 行事务每次都要做一次
   完整窗口快照 + 序列化 + 写盘；before 侧这些行能累积到更大的批次里一次写完。
   换言之，被推迟的 flush 成本并没有消失，只是被合并了。
3. 副作用是 after 侧的延迟分布尾部更厚（flush 造成周期性停顿），但在本测量
   的规模下其幅度与轮间噪声重叠，不构成可报告的回归。

--------------------------------------------------------------------------------
5. 本次测量的边界（不可省略）
--------------------------------------------------------------------------------
- before 侧不是可接受的替代方案。它就是 #4946 的缺陷本身:提交时既不落快照又先截断
  WAL，崩溃后两条路径皆丢。短跑测不出这一点——要 kill -9 才看得见，而那正是 #4946
  报告的失败模式。**这里的"更快"是拿正确性换的。**
- 两侧写盘总字节相同，差别只在同步点。本报告测的是"每次事务的同步成本"，
  不是长期总吞吐。
- S3 每侧仅 5 个样本。20~29% 远超噪声，但样本量小，#4944 的回归矩阵里应补
  更多轮次与更大批量。
- S1/S2 的 400 / 1600 事务规模偏小。要更确定地排除单行场景的回归，应把事务数
  拉到 10k 量级重测（本机 8GB 内存、单次 400 事务约 1.7s，10k 可行）。
- 与 #4910 记录的 8 线程 sysbench oltp_read_write 164 TPS 不可直接比较:工作负载
  不同（sysbench 有 SELECT + 显式事务，本测量是纯单行 autocommit 写）。
  本次 S2 的 ~223~230 TPS 仅在同口径 A/B 内有效。
- 未覆盖崩溃恢复路径（before 的数据丢失窗口）。

--------------------------------------------------------------------------------
6. 建议（归入 #4944 回归矩阵）
--------------------------------------------------------------------------------
- 不需要为单行 OLTP 性能回退 #4956：本次没有测到回退。
- 为批量路径留一条优化选项：在 commit_transaction 里把 flush 保留（正确性），
  但对已显式开启大事务的写做合并/延迟落盘，即按"是否已经在显式事务内"分流。
  这需要新的设计讨论，本次未做。
- #4944 的回归矩阵应新增两行：单行 autocommit 提交延迟、批量事务提交延迟，
  两者分开盯，因为它们的 flush 成本模型不同。
