## 0. 结论摘要

Issue #5379 的标题「TPC-H fixture 悬空符号链接导致 CI `test` job 恒红」只描述了表层症状。实测证明真实问题面是**三层叠加**，
且三层互相掩护，使 CI 长期显示"接近全绿"的假象：

| 层 | 问题 | 实测证据 |
|---|---|---|
| 1 | fixture 是指向仓库外 `/tmp` 的符号链接，任何机器都解析不了 | `git ls-files -s tests/data/` → mode `120000` |
| 2 | fail-fast 让 **446 个声明目标只跑了 64 个**，摘要却打 `passed=70 failed=1` | CI run 7613 完整日志 |
| 3 | 13 个文件**零断言**，只有 `eprintln!` 打印期望值 | 逐文件统计 |

**本变更做了什么**：让 fixture 在 CI 内**运行时生成**（零入库）、给 13 个零断言文件装上**独立预言机**（进程内 SQLite）
与**数据无关不变量**断言、把 CI 改成 `--no-fail-fast` 并加**目标执行核对门禁**、把缺数据从 panic 改成**显式 not-run 披露**。

**明确没做什么**：不 vendor dbgen；不把任何 `.tbl` 提交进仓库；不改任何参考期望值来求绿；不给测试加 `#[ignore]` 冒充通过；
不把 not_run 计入 passed；规模层（SF=1）本轮不接入（见 issue #5387）。

### 1.6 fixture 到位后才暴露的第三层：数据现实度缺陷

第一层是"数据不可达"，第二层是"382 个目标静默不执行"。把 fixture 接上之后，第三层才浮出水面：
**生成器产出的数据与仓库自带的规范查询集不匹配**，导致 22 个 TPC-H 查询里有 9 个是结构性空转。

实测（同一份 fixture，SQLite 独立预言机逐条测）：

| 查询 | 过滤条件 | 旧 fixture | 新 fixture |
|---|---|---|---|
| Q7/Q8/Q9 | `EXTRACT(YEAR FROM …)` / `p_name LIKE '%green%'` | 0 行 | 2 / 7 / 81 行 |
| Q13 | `o_comment LIKE '%special%requests%'` | 1 组（塌成一组） | 20 组 |
| Q16 | `s_comment LIKE '%Customer%Complaints%'` | 0 行 | 288 行 |
| Q17/Q19 | `p_brand = 'Brand#23' AND p_container = 'LG CASE'` | NULL 聚合 | 有效数值 |
| Q18 | `HAVING SUM(l_quantity) > 300` | 0 行（每单固定 4 行项，最大 200） | 命中 |
| Q20 | `n_name = 'GERMANY'` + `p_name LIKE 'forest%'` | 0 行 | 2 行 |
| Q22 | `c_phone` 国家码 + 无订单客户 | 0 行 | 0 行（SF=0.01 规模层固有，见 §8） |

逐条根因（全部在 `scripts/gate/generate_tpch_sf.py`）：

1. **`n_regionkey` 分组错**：`NATION_NAMES` 是按区域分组的（1-5 AFRICA、6-10 AMERICA、11-15 ASIA、
   16-20 EUROPE、21-25 MIDDLE EAST），生成器却用 `(i % 5) + 1` 轮转 → 只有前 5 个 nation 落对区域，
   **GERMANY（17）被放进 AMERICA**，`r_name = 'EUROPE'` / `'ASIA'` 的查询全部落空。
2. **文本列不承载查询所过滤的字面值**：`o_comment` 恒为 `"Ord comment"`、`p_brand` 恒为
   `Brand#12323`、`c_phone` 恒为 `+1-…`、`o_orderpriority` 恒为 `O-PRIO-3` → 规范查询的
   `%special%requests%` / `Brand#23` / `SUBSTR(c_phone,1,2)` / `1-URGENT` 全部匹配 0 行。
3. **品牌×容器组合会落空**：随机分配下 78 个 `Brand#23` 的 part 里**没有一个**是 `LG CASE`。
4. **`l_suppkey` 不受 `partsupp` 约束**（第 2 次同类缺陷）、**`o_custkey` 轮转**（每客户订单数
   完全相同 → Q13 的 `GROUP BY c_count` 塌成一组）、**每单固定 4 行项**（Q18 的 300 阈值不可达）。

**"测试是绿的"与"测试有意义"是两件事**：旧 fixture 下引擎与预言机在 22 条查询上 22/22 一致——
因为其中 9 条两边都返回空。修好现实度后，同一套断言的**信息量**从 13/22 提升到 21/22。

为此在生成器里加了 **4 类生成时自检**（任一不过即 `exit 1`，不产出 fixture）：

| 自检 | 拦住的缺陷 |
|---|---|
| 键分布 | 外键"在范围内"但"不具代表性"（partsupp 只引用 4/100 供应商） |
| 谓词覆盖率 | 12 条规范过滤条件各自必须选中非平凡比例的行 |
| 复合过滤覆盖率 | 品牌×容器这类**组合**过滤不能为空 |
| nation→region 映射 | 逐个 nation 校验其区域符合规范分组（distinct 计数看不出这个错） |

### 1.7 共享 harness 的 `orders` schema 缺一列 → 静默列错位

`tests/common/tpch_wire_harness.rs` 的 `SCHEMA_DDL` 里，`orders` 只声明了 **8 列**——漏了
`o_totalprice`：

```text
实际声明：o_orderkey, o_custkey, o_orderstatus, o_orderdate, o_orderpriority, o_clerk, o_shippriority, o_comment
规范定义：o_orderkey, o_custkey, o_orderstatus, o_totalprice, o_orderdate, o_orderpriority, o_clerk, o_shippriority, o_comment
```

而 `.tbl` 的 orders 数据是 **9 个字段**。于是 `o_orderstatus` 之后**每一列都错位一格**：
`o_orderdate` 位置存的是价格、`o_clerk` 位置存的是日期、`o_comment` 掉出行外。

**这个错位是静默的**：过滤 `o_orderstatus` 仍然命中正确的行（它在错位之前），所以测试看起来健康；
而后面每一列拿到的都是别人的值。最先暴露症状的是一条 `LIKE` 过滤——`o_comment LIKE
'%special%requests%'` 选出 0 行，因为引擎实际比的是**价格列**：

| 查询（同一份数据） | SQLite 预言机 | 引擎（错位前） | 引擎（修正后） |
|---|---|---|---|
| `o_comment LIKE '%special%requests%'` | 747 | **0** | 747 |
| `o_comment LIKE 'Customer asked%'` | 747 | **0** | 747 |
| `o_clerk LIKE 'Clerk%'` | 15000 | **0** | 15000 |
| `o_orderpriority LIKE '1-URGENT'` | 2991 | **0** | 2991 |
| `o_orderdate LIKE '1994%'` | 2130 | **5**（价格以 1994 开头） | 2130 |

进程内路径（`storage.insert`）是**响亮**地失败："row width 9 does not match the 8 declared columns"；
线协议路径（`LOAD DATA LOCAL INFILE`）则静默错位。影响面：31 个文件引用该 harness，其中
**12 个直接使用它的 `SCHEMA_DDL` / `load_fixture` / `start_sf001` / `start_sf01`**。

`tests/common/tpch_cli_harness.rs` 的两处 DDL 本来就是对的——同一个仓库里两个 harness 的
`orders` schema 不一致，是这份不一致长期未被发现的直接原因。

### 4.5 `eval_22_vs_sf01` 的 SQLite 加载器整表丢行

该测试自带的 SQLite 加载器用 `cols_str.split(',')` 拆 DDL 列清单，而 `PRIMARY KEY (l_orderkey,
l_linenumber)` 里的逗号把列数算成 **17**（实际 16）、`PRIMARY KEY (ps_partkey, ps_suppkey)` 算成
**6**（实际 5）→ 每行都因 `cols.len() != n_cols` 被**跳过** → `lineitem` 与 `partsupp` 两张最大的表
在 SQLite 侧是**空的**。

实测证据（修正前的 SQLite 基线库）：

```console
$ for t in region nation supplier customer part partsupp orders lineitem; do
    printf '%s: %s\n' "$t" "$(sqlite3 /tmp/tpch_22_sf01_audit/tpch_sf01.sqlite "SELECT COUNT(*) FROM $t;")"; done
region: 5        nation: 25       supplier: 100    customer: 1500
part: 2000       partsupp: 0      orders: 15000    lineitem: 0
```

后果：Q1/Q3/Q4/Q12/Q15 报 `MISMATCHED`（引擎给出正确结果、SQLite 给出 0），而该测试唯一的断言
`assert!(total >= 22)` **构造上恒真**（四个类别计数之和按定义就是 22），于是 5 处失配全部被掩盖；
同一个循环还把 `SQLiteERR` 重复计数了一次（19+0+0+6=25≠22），也被这条恒真断言放过。

修正后：顶层逗号切分 + **掉行即失败**的守卫（`assert!(skipped == 0)`）+ 类别计数去重 + 断言改为
`mismatched == 0` / `total == 22` / `unsupported == 0` / `oracle_err == 0`，并把 SQLite 侧改走共享
oracle 的 `adapt_sql`（`EXTRACT(YEAR FROM x)` → `strftime`），使 Q7/Q8/Q9 也纳入对照。

**实测**：22/22 全部 MATCHED（改造前 19 MATCHED / 5 MISMATCHED / 3 无法解析）。

## 5. 变异测试（证明新断言能杀缺陷）

> 变异对象是**引擎实现**（`src/engine_select.rs`），不是测试代码——变异测试代码是自证。

| 变异 | 注入点 | 参照目标 | 预期被哪些断言抓住 |
|---|---|---|---|
| MUT-1 | HAVING 谓词取反（去掉 `!`） | `diag_q11` | 「HAVING > 0 必须保留全部分组」不变量 + SQLite 对照 |

### 5.1 写完脚本后实测发现的三个缺陷（脚本交付 ≠ 脚本有效）

变异脚本在交付时**从未运行过**。逐行复核 + 锚点实测后发现三个问题，均已修正：

**(a) MUT-3 原本是一个 no-op 突变。**
原写法把 `AggregateFunction::Count` 的 `COUNT(*)` 分支改成 `if false { unreachable!() } else if ...`。
但 `else if agg.distinct` 分支**依然可达**，引擎行为完全不变 → 突变"存活"的原因与断言能力无关。
现改为直接替换 DISTINCT 分支的取值逻辑，让 `COUNT(DISTINCT x)` 退化为 `COUNT(x)`，
且所有分支保持可达。

**(b) MUT-3 的参照目标原本选错。**
原设计让 `diag_q11` 承担三个变异。但在本 fixture 上实测：

```console
$ SELECT COUNT(ps_partkey), COUNT(DISTINCT ps_partkey)
  FROM partsupp, supplier, nation
  WHERE ps_suppkey = s_suppkey AND s_nationkey = n_nationkey AND n_name = 'GERMANY';
320|320
```

GERMANY 联接后每个 `ps_partkey` 恰好出现一次 → `COUNT` 与 `COUNT(DISTINCT)` **完全相等** →
去重失效在这个数据上**不可观测**。MUT-3 改用 `diag_q12`：它用 `count_with_oracle` 对照
`COUNT(DISTINCT l_shipmode)`（去重后约 7 个），而不去重是行数量级 → 突变无可遁形。

**(c) 缺基线运行会让门禁假绿。**
原脚本直接注入变异并运行目标。若目标**本来**就因别的原因失败（fixture 变了、期望值过期），
每个变异都会"失败"→ 全部报 CAUGHT → 门禁报绿，但什么都没证明。
现增加前置基线：每个参照目标在**未变异**状态下必须先通过，否则退出码 2（harness 自身失败），
**不计入 CAUGHT**。另加引擎文件 SHA-256 校验，证明每个变异后文件被逐字节还原。

#### 7.12.1 对上一版记录的一处**如实更正**（exit 2 那一条当时是夸大的）

上一版本文档写的是「`exit 0 / exit 1 / exit 2` 三条路径全部实测」。**这一条对
exit 2 是夸大的**，本轮复核发现并更正：

| 当时宣称 | 实际情况 |
|---|---|
| 「运行超时 → exit 2」已实测 | ❌ **超时路径从未真正触发**。桩 `timeout` 的安装条件是"仅当文件不存在时才创建"，而 PATH 桩循环早已把 homebrew 的**真** `timeout` 软链进了桩目录 ⇒ 强制超时的桩**从未安装成功** ⇒ 那次跑的是正常路径 |
| 「3 个退出码路径全部实测」 | ✅ 但其中 exit 2 那一格的**证据来源是错的**（结论对，过程假） |

复核过程顺带查出**桩测试自身**的两个坑——它们和被测脚本的缺陷是同一类问题
（"看起来测了，其实没测"）：

1. **`cp` 写穿符号链接**：`cp fail.mktemp "$STUBBIN/mktemp"` 会**穿过** `$STUBBIN/mktemp`
   这个指向 `/usr/bin/mktemp` 的软链，直接去写**系统二进制**。macOS 的 SIP 拒绝了这次
   写入，`cp` 失败，而桩脚本**没有 `set -e`** ⇒ 失败桩**从未生效** ⇒ CASE 3 一度
   "通过"得毫无意义。（系统 `mktemp` 最终未被改动，已用校验和前后对比证明，见上表第 7 行。）
2. **本机 agent shell 里的 `rm` 是"可恢复删除 shim"**：它把删除转交给 Finder 的
   `osascript`，在**非交互 shell**里**会挂起**（本轮实测卡死在 `osascript -e tell
   application "Finder" to delete …`）。桩脚本里任何 `rm` 都会把整个 harness 拖死。

⇒ 修正后的桩测试：所有桩一律装在**独立目录**并**前置到 `PATH`**（不覆盖、不删除
任何文件），每个用例**先断言桩确实生效**再执行断言；整个 harness **零删除动作**
（一次性目录用 `$$` 后缀，天然不与上一轮冲突）。

**顺带发现并修掉一个真缺陷（CI 会红的那种）**：原脚本只用 `shasum` 计算引擎文件的
SHA-256。`shasum` 是 Perl 脚本，**精简版 CI 镜像不保证有**；`sha256sum` 来自 GNU
coreutils，CI runner 上已被 `scripts/gate/check_evidence_binding.sh`（evidence-graph-gate

`g13` 是 G13-OLTP-1「SELECT 取读锁」的回归守卫。本机实测（空闲机器）：

| 状态 | 吞吐比（contended/alone） | 判定 |
|---|---|---|
| 无 bug | 0.75 / 0.67 / 1.00 | 3 次里 1 次挂在 0.7 阈值下 |
| 有 bug（把 `engine.read()` 变回 `engine.write()`，即修复前的行为） | 0.67 / 0.83 / 0.83 | 3 次里 1 次挂在 0.7 阈值下 |

**两个分布完全重叠 → 该测试对「有没有 bug」判别力为零**，且无论有没有 bug 都约 50%
概率误报。可分离出三个缺陷：

1. **测量是量化的**：「2 秒窗口里跑了多少条重查询」是计数，窗口内只有 3–6 条重查询，
   一条跨窗口边界的查询就能把比值挪动三分之一。
2. **探针与文件自己的测试计划不一致**：文件头与步骤 4 的注释共 5 处都写
   「thread B hammers with `SELECT 1`」，代码却传 `HEAVY_SELECT`（同一条重查询）。
   自该测试诞生（`8423e465a8`）起就不一致。重探针会**烧 CPU** —— 即使锁行为完全正确，
   contended 阶段也要多花约 39% 的墙钟时间，于是「无回归」基线掉到 ≈ 0.72，
   正骑在 0.7 阈值上。
3. **0.7 这个阈值从来没有被测量支撑过**，且对机器负载高度敏感。

**为什么本机复现不出那个 bug**：`engine` 是 `Arc<parking_lot::RwLock<…>>`，
`parking_lot` 的 RwLock 允许刚释放锁的持有者插队重新获取，探针并不能真正饿死重查询；
重查询又由并行执行器执行，多核机器上的 CPU 争用进一步盖住信号。该测试文件自己的头注
就写了这一点：这个现象出现在 **Z6G4**，而「**macmini (M4) was unaffected**」。

**本 PR 的处置**：**不改这个测试的语义**。在无法代表目标运行环境（Z6G4）的机器上
重新标定一个并发回归测试的阈值，是没有依据的改动 —— 那正是本轮反复警惕的
「凭不可复现的推断改判定口径」。因此：

- 本 PR 只**如实披露**该测试的实测状态；
- 已新立 **#5398** 跟踪它的重做（验收标准：无 bug 连续 10 次全过、有 bug 连续 10 次
  全红，且间隔不依赖核数 / 负载 / 并发 job 数）；
- 若它在 CI（Z6G4）上仍然失败，按 #5388 的失败归因流程处理，不在本 PR 内改它的判定口径。

> 补充实测（本机）：用轻探针（`SELECT 1`）+ 连续量测量（固定查询数 + 计时）时，
> 无 bug 的比值稳定在 **0.91–0.95**（6 次全过），但**有 bug 时同样是 0.90–0.93** ——
> 因为本机上那个 bug 本来就几乎不产生吞吐差。**换句话说：把测量改「准」并不能让这个
> 测试在本机变得有判别力**；缺的是一台能复现该 bug 的机器，或一个不依赖吞吐的判据。
> 这也是 #5398 写明的方向。

```rust
let _ = s.insert(table, batch.clone());   // ← 错误被丢弃
count += batch.len();                     // ← 计数照样加
```

若这批 insert 失败（表不存在、列数不匹配……），表会是空的，而返回的
`count` 仍然是 10 000。**13 个 `diag_*` 目标**用
`assert!(loaded > 0, ...)` 来防这个 —— 但那个断言防不住"批量失败但计数为正"。
⇒ 失败时断言会对着空表空转通过。

本 PR 改为把 insert 错误向上传播（`Result` 本来就有，只是被 `let _ =` 丢掉），
并把 4 个 `load_rows_into_storage` 调用点从 `let _ =` 改成显式 `panic!`。
⇒ 装载失败现在**响亮**地失败，而不是安静地通过。

#### (f) `timeout 9000 | tee` **杀不掉**挂死的测试二进制

run 8031 的 `test` job 在 `timeout 9000` 到期后**没有结束**：

| 观测点 | 事实 |
|---|---|
| cargo test 起点 | ~04:58Z ⇒ 9000 s 到期 ≈ 07:28Z |
| 08:45Z 查询 job 状态 | `in_progress`（`GET /actions/jobs/16330`） |
| 08:45Z 日志字节数 | 281 854 B，与 06:35Z 完全相同，最后一行仍是 05:59:01Z |
| 处置 | 手动 `POST /actions/runs/8031/cancel` → job 变 `completed / cancelled` |

原因：原来的写法是

```bash
timeout 9000 cargo test --all-features --no-fail-fast 2>&1 | tee test_report.log
```

`timeout` 把信号发给 **cargo 所在的进程组**，但 `tee` 在这个进程组**之外**，
它持有 step 的 stdout 管道；挂死的测试二进制被杀掉（或没被杀掉）之后，
`tee` 仍然等着一个不会关闭的管道 ⇒ **step 永不结束**，runner 一直占着容器。

改法：把**重定向**放在 `timeout` 里面，去掉管道：

```bash
timeout -k 30 9000 cargo test --all-features --no-fail-fast > test_report.log 2>&1
status=$?
tail -n 200 test_report.log || true
exit ${status}
```

`timeout` 默认向子进程的**整个进程组**发信号，管道去掉后挂死的测试二进制
也会被杀，step 随即返回；`tail` 保留最后 200 行到 job 日志（超时时正是
"卡住的那个目标"）。后续的 summary 与 accounting 门禁本来就直接读
`test_report.log`，不受影响。

#### (l) CI 实锤：变异门禁的 `mktemp` 缺陷（3 个变异片段**从未被生成**）

run 8081 的 `mutation` job 16475 于 08:02:55Z 以 **failure / exit 2** 结束。
把它拆开看，链路是完整的：

```
mktemp: : Invalid argument          ← ×3
scripts/gate/mutate_tpch_oracle_tests.sh: line 245: : No such file or directory
scripts/gate/mutate_tpch_oracle_tests.sh: line 266: : No such file or directory
scripts/gate/mutate_tpch_oracle_tests.sh: line 286: : No such file or directory
...
== MUT-1: HAVING predicate inverted  (target: diag_q11)
/usr/bin/python3: can't find '__main__' module in '/workspace/openclaw/sqlrustgo'
ERROR: MUT-1: the mutation anchor was not found exactly once — the mutation was NOT applied
...
=== mutation summary ===
CAUGHT   : 0
SURVIVED : 0
ERRORS   : 3
FAIL: the mutation harness itself failed (3 error(s)) — the result is not trustworthy
exitcode '2': failure
```

**根因**：脚本原来用 `mktemp -t mutate_tpch_mut1.XXXXXX.py` 这类**带后缀的模板**。
CI runner 镜像的 `mktemp` 不接受 `X` 之后还带后缀的模板，直接报
`Invalid argument`；而脚本**没有 `set -e`** ⇒ 命令替换得到**空路径** ⇒
`cat > ""` 报 `No such file or directory`（脚本继续跑）⇒ 三个 Python 片段
**一个都没写出来** ⇒ `python3 ""` 报 `can't find '__main__' module` ⇒
三个变异**从未被应用**。

**注意结论的方向**：门禁**没有**因此报出假绿 —— `ERRORS=3` ⇒ `exit 2` ⇒
job 变红并明说"the result is not trustworthy"。这是脚本里 `ERRORS` 兜底逻辑
的功劳。但**这个 job 永远不可能变绿**，而它属于本 PR ⇒ 必须修。

**为什么只有 3 处失败、另外 3 处没事**：HEAD 版本共 6 处 `mktemp` 调用，
其中 3 处的模板**没有**额外后缀（`mutate_tpch_base.XXXXXX` 等）⇒ 镜像能接受；
失败的恰好是 3 处带 `.py` 后缀的（`mutate_tpch_mut1.XXXXXX.py` 等）⇒
只有**三个变异片段文件**受影响。CI 日志里的 3 次报错与这 3 处**一一对应**。

**修复**：抽出 `make_temp_file()` 辅助函数 —— 用**不带模板**的裸 `mktemp`
（本仓库 `scripts/gate/*.sh` 里 20+ 处都是这个用法，已被同一 runner 证明可用），
并且**在拿不到路径时大声失败**（stderr 报错 + 返回非 0），让"建不出临时文件"
的 harness **停下来**，而不是继续用一个空路径编造结论。6 处调用点全部替换。
该修复的机械逻辑已用桩测试实测（§7.12 第 3 行：exit 2 + `refusing to continue
with an empty path`）。

**同时更正一个与代码不一致的注释**：脚本头部的用法说明写着
`bash scripts/gate/mutate_tpch_oracle_tests.sh [--keep-fixture]`，但脚本**从不解析**
这个参数，fixture 目录**也从不被删除**。⇒ 用法说明已改成与代码一致
（明说 fixture 目录一律保留、根本没有这个开关）。

**这一节的元教训**：§7.12.1 记录的"桩测试自己也会骗人"（`cp` 写穿符号链接 +
本机 `rm` 是会挂起的可恢复删除 shim）与这里被测脚本的缺陷是**同一种病**：
**失败没有被看见，于是"测过了"就成了误会**。两处都必须显式断言"这一步真的生效了"。

#### (c) 本轮新暴露的两个成本：逐行 INSERT 的两个新目标

本 PR 已经为 4 个 TPC-H 目标做过"逐行 INSERT → 批量装载"的降本（#5399）。
本轮把 446 个目标第一次全部跑起来，**又暴露出两个同类目标**——它们的逐行 INSERT
此前从未在 CI 上执行过（run 8031 日志里 0 次），所以一直"便宜"。

| 目标 | 逐行 INSERT 条数 | 表有主键？ | 代价模型 | CI 实测 |
|---|---:|---|---|---|
| `tests/integration/sql/int2_substance_parallel_test.rs` | **200 000**（`PARALLEL_MIN_ROWS / 10`） | **是**（`id INTEGER PRIMARY KEY`） | **O(N²)** | **> 50 min 仍未结束**，进程 CPU 100%、累计 1977 s CPU |
| `tests/integration/sql/parallel_main_path_test.rs` | **600 000 × 8 次 = 480 万条**（`populate()` 被调用 8 遍：6 个调用点，其中一个在 `for parallel in [1,2,4]` 循环里 ⇒ 3 次） | 否（`t (k INTEGER, v INTEGER)`） | O(N) 但语句数巨大 | 尚未执行到（排在第 ~150 个之后） |

**为什么带主键的逐行 INSERT 是 O(N²)**（引擎侧，**本 PR 不改**，见 **#5412**）：
重复键检查走 `pk_lookup_cache`，但该缓存**只在表的 change stamp 未变时**才可用
（`src/engine_dml.rs:429-440`），而 `crates/storage/src/engine.rs:2855-2859` 的
`bump_change_stamp()` **在每一次行变更时递增** ⇒ **用来加速 INSERT 的缓存，恰好被
INSERT 自己作废** ⇒ 每条语句都退回全表扫描。引擎自己的注释记着这个形状：
「measured 44s for 15000 rows」。

两个实测点落在同一条二次曲线上：

| 逐行 INSERT 条数 | 目标 | 实测墙钟 |
|---:|---|---:|
| 10 000 | `cbo_integration_test` | **40.21 s**（CI run 8081 / job 16520） |
| 200 000 | `int2_substance_parallel_test` | **> 50 min 仍在跑**（O(N²) 外推 ≈ 130 min） |

**`for i in 0..rows` 的参数化上界**形态（§7.19(c-2) 扫描器的盲点），

⇒ 按 §7.19(c) 实测的逐行 INSERT 速率外推 ≈ 45 min，**与观测的 51 min 吻合**
⇒ **卡在装载，不是被测查询**。

**行数（600 000）与断言语义一个都没改**；并新增一条"插入行数 == 期望行数"的断言。

**为什么不影响被测对象**：该文件是**性能基线**测试，但它测的窗口是**查询**
（`median_ms` 只包住 `SELECT k, v FROM t WHERE k < 100`），
**装载从不进入计时** ⇒ 降本只改装载路径，**不改变任何被测的量**。

**该文件还带着一个判别力问题**（与 #5413 同源，**只披露不改**）：
`test_above_500k_rows_parallel_engages` 的注释说"At 500K+ rows, the parallel filter
guard should engage"，但实际阈值是 `PARALLEL_MIN_ROWS = 2_000_000`
⇒ **600 000 < 2M ⇒ 并行路径根本不会 engage**，
该测试实际只验证了"seq 与 par 结果一致"。

> 上一轮"全仓扫描无漏网"的结论，**恰恰因为扫描器口径只覆盖了字面量上界**而漏掉了这一处
> —— **如果第 7 处不补，446 个目标在预算内依然跑不完，而我们会以为已经扫干净了。**
> 这比漏掉一个巨兽更危险：**它给出了一个假的"已收口"信号**。
> ⇒ 补扫（§7.19(c-3)）后确认：**除已降本的 3 处外，其余全部可接受**。

#### (c) MUT-1 存活的根因：**锚点选错了路径，不是断言不力**

`src/engine_select.rs` 里 **HAVING 有两条实现路径**：

| 路径 | 位置 | 形态 | 语义 |
|---|---|---|---|
| (a) **无 GROUP BY**（全表聚合） | `src/engine_select.rs:1958` | `if !eval_predicate_with_subq(having_expr, …)` —— 该 `!` 守卫的是「谓词为假 ⇒ 返回零行」的分支 | 标准语义 ✔ |
| (b) **有 GROUP BY** | `src/engine_select.rs:2206` | `agg_result_rows.retain(\|row\| eval_predicate_with_subq(having_expr, …))` —— 保留谓词为**真**的组 | 标准语义 ✔ |

**MUT-1 原本只锚在路径 (a) 上**（把 `!` 去掉），
而 `diag_q11` 的查询是 `SELECT ps_partkey, SUM(…) … GROUP BY ps_partkey HAVING SUM(…) > 0`
⇒ **走的是路径 (b)** ⇒ **变异根本没有作用到被测代码** ⇒ 测试结果不变 ⇒ SURVIVED。

⇒ **断言没有过错**（`diag_q11` 的 Step 3 断言「`HAVING > 0` 必须保留全部组」、
Step 4 断言「不可能阈值必须保留 0 组」，在路径 (b) 被反转后**两者都会失败**），
**是门禁的锚点选错了路径**。

#### (d) 修法：MUT-1 **同时反转两条路径**

```
REPLACEMENTS = [
    # (a) no GROUP BY — drop the `!`
    ("if !crate::engine_utils::eval_predicate_with_subq(", "if crate::engine_utils::…"),
    # (b) with GROUP BY — add the `!`
    ("agg_result_rows.retain(|row| {\n    crate::engine_utils::…",
     "agg_result_rows.retain(|row| {\n    !crate::engine_utils::…"),
]
```

**只改一个 `!`，就等于只反转一条路径** ⇒ 任何只走另一条路径的测试都杀不掉它。
**两个锚点一起改**，一次变异同时覆盖两条路径 ⇒ 无论被测代码走哪条都会被杀掉。
（脚本顶部的说明注释也一并更正为如实描述：原文声称 `diag_q11` "can kill MUT-1"，
而实测它杀不掉 —— 那句话当时是**未经验证的断言**。）

|---|---|
| `bash -n scripts/gate/mutate_tpch_oracle_tests.sh` | ✅ 通过 |
| MUT-1 片段对 `src/engine_select.rs` **副本**的应用 | ✅ 退出码 0，`MUT-1 applied: HAVING predicate inverted on BOTH implementation paths` |

#### 7.25.5 D5-10 那个"1 个失败"的真实身份（同时是一个 CI 判读陷阱）

`cargo test --lib -p sqlrustgo --quiet` 在 PR 分支 5 次复跑失败 2 次、基线 3 次复跑失败 1 次，
失败用例固定为：

```
---- execution_engine_tests::test_v410_atomic_parallel_degree_getter_clamps_to_one stdout ----
panicked at src/execution_engine_tests.rs:1361:5:
assertion `left == right` failed
  left: 4
 right: 1
```

根因：`ExecutionEngine::base_with`（`src/execution_engine.rs:349`）**每次构造引擎都读进程级**
`SQLRUSTGO_EXECUTOR_PARALLELISM`；而 `src/execution_engine_tests.rs` 的多个用例
（`:559`/`:618` 的 `set_var`、`:561`/`:586`/`:592`/`:620`/`:659` 的 `remove_var`）
**并发改写同一个进程的环境表** ⇒ 读取方偶尔读到 4 而不是 1。
`--test-threads=4` 时 6/6 通过，与并发度直接相关。

**⇒ CI 判读陷阱**：CI 的 `test` job 执行 `cargo test --all-features --no-fail-fast`，
根包 lib 测试就在其中 ⇒ **该 job 存在约 1/3 量级的随机红灯**。
所以「CI 红了」不必然是本 PR 的锅，「CI 绿了」也不必然是绿的 —— 必须用
「同命令复跑 + 基线对照」甄别（本次即如此定位，已立项 #5423）。

#### (e) 本轮**新暴露**的一个真缺陷：`setup_tpch_tables` 的单表探针 + 并发不安全

这一条是本轮改造过程中**由假绿变成真红、又定位到真根因**的完整链条，值得单独记录。

1. 把 `tpch_full_test` 的 5 个**零断言**查询测试（`test_mysql_tpch_q1`、`test_mysql_all_queries`、
   `test_postgres_tpch_q1`、`test_postgres_tpch_q6`、`test_postgres_all_queries`）
   从 `if let Ok(...) { println! }` 改成「服务不可达 ⇒ NOT-RUN；**可达但查询失败 ⇒ panic**」。
2. 改完后本地立刻**变红**：`test_postgres_all_queries` panic
   `PostgreSQL Q2 on a reachable server failed: ERROR: relation "part" does not exist`。
3. 定位：`setup_tpch_tables()` 的存在性探针**只问 `lineitem` 一张表**
   （`SELECT COUNT(*) FROM pg_tables WHERE tablename = 'lineitem'`），
   命中就**跳过整套建表** ⇒ **半初始化的 schema 永远不会被修复**。
   而本地这台 Postgres 上正是半初始化状态（`lineitem` 在、`part` 不在）。
4. 再定位第二层：多个 postgres 用例**并行**调用 `setup_tpch_tables()`，
   各自 `DELETE` + `INSERT` 同一批表 ⇒ **主键冲突** ⇒ `test_postgres_setup` 随机红。
5. 两处一起修：
   - 探针改为**一次性核对全部 8 张表**，缺任一张就修复（`INSERT … ON CONFLICT` 语义由 `DELETE`+`INSERT` 保证）；
   - 建表脚本首尾加 **PostgreSQL advisory lock**（`SELECT pg_advisory_lock(5379001)` /
     `pg_advisory_unlock(5379001)`）⇒ 并行调用被数据库层串行化（跨进程也有效）。

```
$ for i in 1 2 3; do cargo test --test tpch_full_test; done
test result: ok. 40 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out   ×3
```

同时修掉了 NOT-RUN 披露的 2 个瑕疵：客户端把**整页帮助文本**打进 `detail`（现在截断到 200 字符、
只留第一行），以及客户端 stderr 为空时 `detail=` 为**空**（现在回退到 stdout / 退出码）。

> **方法学**：这次「假绿 → 真红」的转换本身就是结论 ——
> **一个只 `println!` 的测试，它报告 "ok" 时不代表它执行过任何东西。**
> 本 PR 把「环境阻塞 ⇒ NOT-RUN」与「能跑 ⇒ 报错就红」两条规则同时落到这 5 个用例上，
> 假绿才得以消失。

#### (h) 对「GA 全绿」这句话的结论

**当前仓库状态下，「GA 全绿」是一个不可声称的结论**，理由是上面 14 条中至少 5 条各自独立地使它失真：

1. **清单不唯一**（#5437 / #5438）—— 不知道该数几个；
2. **执行点不存在**（#5440）—— SSOT 无人消费，20 项里只有 6 项被 CI 触及；
3. **被判据本身恒绿**（#5417 / #5419 / #5445）—— 20 项里至少 4 项不会失败；
4. **CI 的判读不可靠**（#5443 / #5444 / #5447）—— 失败可以被吞、被错配、被自己写进去；
5. **证据链不成立**（#5439 / #5441）—— 产物缺失不可见、连日志都进不了版本控制。

⇒ **本 PR 不勾选任何 GA 门禁项**（`AGENT_PROMPT_TEMPLATE.md:35`「不得自批 Gate」），
并且**本 PR 的交付物是 GA 流程的取证与差距清单，不是「GA 已通过」的结论**。

> **方法学上的一致性**：本 PR 一贯的口径是「恒绿与恒红是同一种病 ——
> 门禁不再对代码的真实状态作出区分」（判据：改一处代码，这个门禁的结论会不会变）。
> 本节把同一条判据用到了**发布链路本身**：
> 把 `check_architecture_freeze.sh` 的 `:130` 改成 `exit 1`，结论会不会变？⇒ 不会 ⇒ 它恒绿。
> 把 `ci.yml:620` 的 `❌` 改成 `✗`，postcheck 的结论会不会变？⇒ 会 ⇒ 它有判别力。
