### 2.2 真正卡住 CI 的是另外 11 个测试目标（issue 未记录）

`cargo test` / `cargo check` **默认遇错即停**：第一个目标失败后就不再编译
其余目标。因此：

- issue 记录的「编译失败的测试目标数 = 1」只是**第一个**失败目标

全工作区实测（`cargo check --workspace --all-features --tests --keep-going`，
基线 `7a73c42397`）共 **12 个目标**编译不过：`sqlrustgo-storage` 的 11 个
+ `sqlrustgo-wal-verification` 的 1 个。

**根因单一**：`set_current_db` / `current_db` 已随 #5057 step 3 从
`StorageEngine` trait **彻底移除**（`crates/storage/src/engine.rs:1268`），
但这 11 个集成测试仍在调用它：

| 错误 | 次数 |
|---|---|
| `no method named 'set_current_db' found for struct 'FileStorage'` | 30 |
| `no method named 'set_current_db' found for struct 'MemoryStorage'` | 8 |
| `no method named 'current_db' found for struct 'FileStorage'` | 3 |
| `… for struct 'parking_lot::…RwLockWriteGuard<'_, FileStorage>'` | 3 |
| `… for mutable reference '&mut FileStorage'` | 1 |
| `E0061: this method takes 2 arguments but 1 argument was supplied`（`has_view`） | 1 |
| **合计** | **46** |

迁移原则（见 §3.2）：**保意图、换契约**。数据库改为在调用点显式命名
（`*_in_db`），无库调用一律解析到 `DEFAULT_DATABASE`；原「切到非当前库再
操作」的鉴别力，通过给 `default` 也建同名表来恢复。

### 2.2.1 第 12 个目标：`sqlrustgo-wal-verification`

```
error: could not compile `sqlrustgo-wal-verification` (test "wal_real_verification_test") due to 14 previous errors
error[E0063]: missing field `database_name` in initializer of `WalEntry`
```

`WalEntry` 在 #5192 新增了 `database_name: Option<String>`
（`crates/storage/src/wal_legacy.rs:126`，用于点时间恢复时知道行属于哪个
库），`wal_real_verification_test.rs` 的 14 处字面量没跟上。

**修法**：14 处补 `database_name: None`——与该文件既有的
`table_name: None` 对称（这些是 LSN 单调性等场景的合成条目，不参与回放；
`WalEntry` 的文档明确「`None` for entries written before #5192 and for
non-row entries」）。顺带清掉 `wal_verification_test.rs` 里一个未使用的导入。

修复后：`cargo test -p sqlrustgo-wal-verification --all-features` →
**71 passed / 0 failed**。

### 2.3 编译修复暴露出的 2 个真实产品缺陷

编译错误掩盖了 2 条**真实缺陷**（与本次改动无关，8 个源文件的改动全部在
`#[cfg(test)]` 之后）：

#### 缺陷 A：`pages_visited` 冷路径双计

`BufferPool::get_or_load` 的冷路径把同一页数了两次：
`get()` 的 miss 分支 +1，`insert()` 再 +1。

```
crates/storage/src/buffer_pool.rs:149   stats.pages_visited += 1;   // get() miss 分支
crates/storage/src/buffer_pool.rs:211   stats.pages_visited += 1;   // insert()
```

既有测试 `buffer_pool_bumps_pages_visited_on_get_or_load` 断言
`pages_visited() == 1`，实测得 **2**。

`pages_visited` 是 EXPLAIN 的「页流量」信号，必须数**页**而不是**事件**：
miss 意味着这页**不在**池里，本次没有访问任何池内页。

**修法**：删掉 `get()` miss 分支的那一行。这同时符合 `file_storage.rs:4768-4771`
注释里作者自己的模型（「loader runs → `pool.insert` bumps `pages_visited`」）。

#### 缺陷 B：扫描路径把空白页插回池里 → 级联淘汰

`scan_via_bufferpool` 冷路径用 `get_or_load` 加载一个**空白页**，
而 `get_or_load` 会把空白页**插入**池中。于是每个已被淘汰的 page-id
都以空白页的身份重新入池，**反过来淘汰一个还活着的页**——级联。

定量（临时探针，已删除）：

| 记录数 | 池容量 | 扫描回读行数（修复前） |
|---|---|---|
| 1 | 64 | 1 |
| 10 | 64 | 10 |
| 64 | 64 | 64 |
| **100** | **64** | **0** ← 不是淘汰 36 条，是**全部行丢失** |

**修法**：扫描路径改为纯查表 `pool.get(page_id)`，miss 即「这页已被淘汰」，
丢行但**不惊动还活着的页**。修复后同样的 100/64 场景回读 **64 行**
（= 池容量，即真正存活的那 64 页），且扫描本身零淘汰。

这正是旧文档注释自己声称的行为（「this page was evicted and we have
nowhere to read it back from」）——实现方式与声称不符。

### 2.4 一条与设计契约自相矛盾的测试

`file_storage_concurrent_inserts_via_bufferpool_do_not_corrupt`：
64 页容量的池装 100 条记录，断言回读 **100 行**。

这在任何实现下都不可达：`insert_at` 在配置了 BufferPool 时**提前返回**，
数据只存在于池中，64 槽 LRU 池在插入时就淘汰掉 36 页，且**没有恢复路径**。

它的 MemoryStorage 姊妹测试（`engine.rs`）已被改成 256 页池 +
`pages_visited >= 100` 断言——**两个同名姊妹测试互相矛盾**。本 PR 把
FileStorage 版对齐到姊妹版，并把淘汰行为单独用一条新测试钉住
（不变量：超配池扫描必须回读**全部存活页**，且扫描零淘汰）。

## 5. 新暴露的缺陷（已立项，不在本 PR 修）

### 5.1 崩溃测试的 server 二进制路径永远解析不到 —— 已在本 PR 修

`fault_coordination.rs::server_bin()` 返回**相对**路径
`target/release/sqlrustgo-mysql-server`，而 cargo 跑集成测试时的工作目录
是**包目录** `crates/storage/`，于是实际查找的是
`crates/storage/target/release/…` —— 该目录从不存在。

后果：4 条崩溃测试全部以 `spawn server: No such file or directory (os error 2)`
**瞬间失败**，从未真正执行过。

**修法**：从 `CARGO_MANIFEST_DIR` 推导工作区根，`debug` 优先于 `release`；
`SQLRUSTGO_SERVER_BIN` 仍可覆盖；找不到时给出可操作的报错（原本的
`spawn server: No such file` 没说清缺的是哪个文件、怎么编）。

**效果（实测）**：`committed_transaction_survives_sigkill_at_commit_fsync`
**首次真正执行并通过**：

```
B1 point=after_commit_fsync sync=every run_id=commit_fsync_28442 pid=28500 reached=true expected=10 actual=10 outcome=PASS
```

### 5.2 崩溃测试的 SIGKILL 落在边界**之后** —— 已立项

`fault_injection::reach()` 写完信号后**自旋 120 秒**
（`crates/storage/src/fault_injection.rs:166-169`）；而 harness 是
**先同步调用 `sql()`**（客户端阻塞等响应）、**再** `await_signal()`
（`crates/storage/tests/fault_coordination.rs:287` / `:258`）。

于是 SIGKILL 至少晚 120 秒才发出，落在服务**已恢复服务之后**。
实测两个测试目标耗时 **121.45s** ≈ `reach()` 的 120s 自旋。

也就是说：`committed_transaction_survives_sigkill_at_commit_fsync`
证明的是「进程在空闲时被 SIGKILL 后数据仍在」，**不是**它文档里声称的
「在 COMMIT 的 fsync 边界崩溃后数据仍在」。这是假证据，属于
#5228（故障注入真实性审计）的范围。

### 5.3 control 测试的前提是错的 —— 已在本 PR 修

`crash_without_new_commit_preserves_exactly_the_seeded_rows` 断言
「hook 不应触发，因为本场景不发 COMMIT」。**前提不成立**：
autocommit INSERT 本身就是 COMMIT，hook 在 seed 上触发是**产品行为正确**。

原断言的错误方向是「让一个从未到达边界的 harness 看起来健康」——正是
control 要防的事。已改为直接断言 control 真正的职责：信号文件必须存在，
且必须写明**本次 run 的 run_id、本次 server 的 pid、被 arm 的故障点**。

**修复后实测**（`--test-threads=1`）：

```
test committed_transaction_survives_sigkill_at_commit_fsync ... ok
test crash_without_new_commit_preserves_exactly_the_seeded_rows ... ok
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 240.53s
```

**240.53s ≈ 2 × `reach()` 的 120 秒自旋**——这正是 §5.2 那条缺陷的量化
证据：两个测试各被自旋拖了 120 秒，SIGKILL 落在这之后。

### 5.4 索引更新边界崩溃后，扫描与索引路径不一致 —— 已立项 #5376

`index_update_crash_does_not_serve_dangling_rows` FAILED。该测试要求
「全表扫描」与「走索引的查询」结果一致（悬垂索引会让两者不一致）。
`--test-threads=1` 单独跑时它**超过 10 分钟未结束**被 `timeout 900` 杀掉
（`AfterIndexUpdate` 在一条 SQL 内被多次触发，每次一段 120 秒自旋）。

**在 §5.2 的 kill 落点被修正之前，无法判定这是恢复逻辑缺陷还是 harness
缺陷**——已并入 #5376 一并处理，不在本 PR 内下结论。

### 5.5 `create_index` 没有 `_in_db` 变体 —— 已立项 #5377

`MemoryStorage::create_index` 经 `self.tbl(...)` 恒定注册到
`DEFAULT_DATABASE`，而 `scan_with_index_in_db` 按**命名库**的 scoped key
查找索引。于是**命名库（`default` 之外）的索引永远查不到**，
`create_index` 的写侧也无法按库寻址。

FileStorage 侧同样只有 `save_index`（硬编码 `DEFAULT_DATABASE`）而读侧
按库加载。已在 `memory_in_db_full_5057.rs` 中把这一事实钉住并说明。

## 6. 结论

- #5375 正文记录的两处编译错误已修复，且**实际损坏面（12 个目标 / 60 个错误）
  比 issue 记录的更大**，一并修复：storage 的 11 个目标 / 46 个错误，加上
  `sqlrustgo-wal-verification` 的 1 个目标 / 14 个错误。
- 编译修复暴露的 2 个真实产品缺陷（`pages_visited` 双计、扫描路径级联淘汰）
  已修复并各有专门的回归测试。
- 崩溃测试的 server 二进制路径 bug 已修复，4 条「从未真正执行」的测试因此
  开始真实执行；其中 `crash_commit_fsync_b1` 的 2 条**首次真正执行并全部
  通过**（120.35s）。
- 剩余的崩溃/恢复语义缺陷（§5.2、§5.4）属于 #5228 的范围，已单独立项，
  **不在本 PR 内自批**。
