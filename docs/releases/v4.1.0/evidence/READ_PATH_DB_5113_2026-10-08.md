## 缺口的三种形态

14 处不是同一种遗漏，按后果分：

### 1. 同一 tuple 里一半有一半没有（`execute_single_join`）

```rust
(
    self.scan_for_reader_with(storage, &right_table_name)?,          // 无 db
    storage.get_table_info_in(&current_db, &right_table_name)?,      // 有 db
)
```

右表的**列**来自正确的库，**行**来自另一个库。两张表列数相同时 JOIN 不会报错，
只会返回另一个库的值 —— 无错、错答案。这条被基线测试抓住（见下）。

### 2. 同一函数的两个分支只有一半接线（`table_status_row`）

#5025 给它加了 `db: Option<&str>` 参数，`Some(db)` 分支用 `*_in_db` 解析，
`None` 分支什么也不解析。#5111 刚碰过这个函数，仍只修了前者。

### 3. 纯读路径（其余 12 处）

都在 `&self` 方法或带 `engine` 参数的函数里，可以直接 `session_db()`。此前预估
「需逐个改签名」过于悲观 —— 实际无一需要改签名。

### 哪几条测试真的有鉴别力

用两种变异分别判定，而不是数断言：

1. `src/` 回退基线
2. 把全树 `session_db()` 强制换成不存在的库 `__nonexistent_db`

| 测试 | 基线 | 强制错库 | 判定 |
|------|------|----------|------|
| `join_reads_rows_and_schema_from_the_same_database` | **FAIL** | pass | **有鉴别力** |
| `exists_subquery_reads_the_connections_table` | pass | **FAIL** | **有鉴别力** |
| `show_table_status_counts_the_connections_table` | pass | pass | 无效 |
| `insert_pk_cache_is_built_from_the_connections_table` | pass | pass | 无效 |
| `ordinary_statements_work_in_a_single_database` | pass | pass | 对照组 |

后两条标 `#[ignore]`，原因写在测试里。它们**不是断言写错了**，而是这两条语句根本没
走到刚修的代码路径 —— 强制数据库指向一个不存在的库也照样通过，说明路径没被触达。

按「空断言必须修正而非迁就」，宁可标 `#[ignore]` 并写明，也不留一条「看起来在测
其实测不到」的断言。修复本身保留：形态 2 与形态 3 是同一套参数传递，不存在
「改一半更安全」。
