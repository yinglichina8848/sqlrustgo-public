## 0. 一句话

这一批处理的不是「代码算错了」，而是**「判定结果怎么变成 CI 结论」那根线**。
线一断，脚本判得再对，CI 也看不见；线一接错，CI 恒绿。
本批次修好了 8 个既有断点，并**在真跑工作流步骤体时发现了一个此前未被记录的新断点**（#5483）。

## 1. 为什么要做这一批

迭代 5 的前三个批次（#5470 / #5475 / #5479）合并后，`develop/v4.1.0` 上仍然有 3 个 PR 的 CI
**永远拿不到绿灯**，原因被记录为「结构性阻塞」：

| 阻塞 | 现象 | 本批次处理 |
|---|---|---|
| `legacy-gate` 挂死 2.5 h | 单 runner `hp-z6g4` 被占满，其余 job 全排队 | #5447 / #5416 |
| `test` job 从未成功 | 400+ 次零次成功 | #5420（A2 维度编译失败）+ #5484（陈旧断言） |
| `postcheck` 从未执行 | 18 个发布前判据 0 次运行 | #5455 / #5443 / #5444 / #5456 / #5424 / #5483 |

三者互为因果：`postcheck` 的 `needs: [test]` 让它 0 次执行 ⇒ 它的判据**从未被检验过**
⇒ 里面的缺陷（缺 `fi`、计数解析错误、字符集漂移）全部潜伏至今。

⇒ 本批次的核心命题：**让这些判据第一次真正跑起来，并让它们的失败能被看见。**

## 2. 缺陷清单与归因

### 2.1 #5420 —— `fault_injection.rs` 的 cfg 写反（真实 Rust 缺陷）

`crates/storage/src/fault_injection.rs`：

| 行 | 定义 | cfg |
|---|---|---|
| 156 | `pub fn reach(point: FaultPoint)` | **无** |
| 188 | `pub fn reach(_point: FaultPoint)` | `#[cfg(not(feature = "fault-injection"))]` |

而 `crates/storage/src/lib.rs:29` 是：

```rust
#[cfg(any(test, feature = "fault-injection"))]
pub mod fault_injection;
```

⇒ 模块在 **lib-test 构建（feature 关）** 下被编译，两个 `reach` 同时存在 ⇒ E0428：

```
error[E0428]: the name `reach` is defined multiple times
   --> crates/storage/src/fault_injection.rs:188:1
    |
156 | pub fn reach(point: FaultPoint) {
    | ------------------------------- previous definition of the value `reach` here
error: could not compile `sqlrustgo-storage` (lib test) due to 1 previous error
```

⇒ RC/GA 门禁的 **D1-A2 维度**（`cargo test --lib -p …`）**恒红**，且从未跑到任何断言。

**修法**：给真实现加 `#[cfg(feature = "fault-injection")]`（空实现保持 `not(feature)`），
两个定义在任何 feature 组合下都恰好活一个；`write_signal` 同步加门控，避免非 feature 构建出现
dead_code 警告。

**实测**：

```
$ cargo test --lib -p sqlrustgo-storage --no-run
    Finished `test` profile [unoptimized + debuginfo] target(s) in 18.85s
  Executable unittests src/lib.rs (.../sqlrustgo_storage-36265d2c6f766ec4)
EXIT=0

$ cargo build -p sqlrustgo-storage --features fault-injection
    Finished `dev` profile ... EXIT=0
```

### 2.2 #5416 —— legacy 门禁把 `--quiet` 传给了 rustc

`scripts/gate/legacy/check_alpha.sh:20`：

```bash
check "R7: clippy zero warnings" "cargo clippy --all-features -- -D warnings --quiet"
```

`--` 之后的一切都是 **rustc** 的参数 ⇒ rustc 报 `Unrecognized option: 'quiet'` ⇒
**每个 crate 都编译失败** ⇒ 这条检查无论代码写成什么样都必然 FAIL。

同时 `check()` 把被检查命令的输出整个丢掉（`>/dev/null 2>&1`）⇒ 失败行只有一个词
`FAIL`，没有任何可诊断信息 —— 这正是「连着三个 FAIL 却看不出所以然」的原因。

**修法**：`cargo clippy --all-features --quiet -- -D warnings`；`check()` 改为把输出
捕获到临时文件、失败时打印前 20 行。

### 2.3 #5447 —— `gate.yml` 的两个 job 都不做真检查

**(1) `evidence-graph-gate`**：把 `PASS` **写进**证据图，再从证据图里**读出** `PASS`；
artifact 的哈希是字面量 `"sha256-placeholder"`。

**修法**：CI 结果改为来自一次**真实检查**（`check_path_casefold_conflict.sh`，纯 shell、
毫秒级、检测仅大小写不同的被跟踪路径），artifact 哈希改为真实二进制�� sha256。

**(2) `legacy-gate`**：跑 `scripts/gate/legacy/check_alpha.sh`（v2.9.0 时代的脚本）并以
`|| true` 收尾 ⇒ 恒绿；且该脚本的 R4 检查是**无界的全量 `cargo test --all-features`**
⇒ 这就是 CI 挂死 2.5 h、占死单 runner 的直接原因。

`docs/governance/STAGE_CONFIG.yaml` 的 ALPHA 段本身已经写明该怎么做：

> v2.9.0's check_alpha.sh is hardcoded with v2.9.0 paths and references crates that no
> longer exist … **Each version provides its own check_alpha_v{VER}.sh** that references
> the version's own worktree paths and gate set.

**修法**：CI job 改为跑 `scripts/gate/check_alpha_v410.sh`（v4.1.0 专属、有界的真实门禁），
去掉 `|| true`，加 `timeout-minutes: 45`；legacy 脚本的 R4 检查用 `run_bounded 1200 …`
包住（同时兼容 Linux 的 `timeout` 与 macOS 的 `gtimeout`）。

### 2.4 #5455 —— `postcheck` 被 `needs: [test]` 完全遮蔽

50 个 CI 周期的 job×结论统计：`test` 0 success / 8 fail / 16 cancel / 1 skip。
⇒ `postcheck` 的 18 个步骤**一次都没跑过**。`mutation` job 同样被遮蔽。

**修法**：`postcheck` 与 `mutation` 的 `needs` 改为 `[]`（无依赖 ⇒ 不会被跳过）。

### 2.5 #5443 —— 门禁步骤没有 `pipefail`；失败标记字符集漂移

**(1) pipefail**：`bash scripts/gate/check_rc_ga_gate.sh ga 2>&1 | tee rc_ga_gate.log`
在没有 `pipefail` 时，步骤退出码取自 `tee`（恒 0）⇒ 步骤恒绿。

同一形态在别处是**对的**：「6 Meta-Gate Hard Block」步骤也用了 `| tail -10`，
但它带着 `set -euo pipefail` ⇒ 管道退出码取自门禁而非 `tail`。
⇒ 判据必须是通用的「**凡是把门禁脚本管道出去的步骤都要开 pipefail**」，
而不是逐行点名。

**修法**：为 3 个缺 `pipefail` 的步骤补上 `set -euo pipefail` ——
`Gate L1 — Code Quality`、`RC/GA Gate — Unified 6-Dim`、
`test` job 的 `Gate G1 — TPC-H 22/22 baseline`（后者原本的注释还宣称
「this step fails hard …」，与实际行为相反）。

**(2) 字符集漂移**：CI 的兜底 grep 用 `❌`(U+274C)，而 RC/GA 脚本实际输出 `✗`(U+2717)：

```
$ sed -n '93p' scripts/gate/check_rc_ga_gate.sh | hexdump -C | head -2
  ... e2 9c 97 ...        ← ✗  U+2717  BALLOT X
$ grep -c '❌ FAIL' <rc_ga_gate.log>   → 0
$ grep -c '✗ FAIL' <rc_ga_gate.log>   → 3
```

**修法**：把失败标记**收敛成一个常量** `[FAIL]`（ASCII）—— `gate/gate.sh` 本来就在用它；
`check_rc_ga_gate.sh`、`check_alpha_v380.sh`、`check_full_gate_verification.sh`
的失败输出统一带上 `[FAIL]`，CI 的三个计数器统一 grep `\[FAIL\]`。

### 2.6 #5444 —— CI 调的是废弃的覆盖率桩

```bash
$ head -8 scripts/gate/check_coverage.sh
#!/usr/bin/env bash
# ...deprecated stub...
exit 2
```

CI 调的是它（`ci.yml:455`），而真门禁 `check_coverage_v312.sh`
（`STAGE_CONFIG.yaml` 的 GA `required_gates` 列的正是它）**CI 从不调用**。

**修法**：改调真门禁；真门禁需要 `cargo-llvm-cov`，runner 上没有该子命令时按治理规范
记 **NOT-RUN + 受控原因码**（`COVERAGE_TOOL_MISSING`），而不是静默通过。

**顺带修正**：postcheck 的「Version detection」步骤原本只在
`origin/develop/v3.8.0` 与 `origin/develop/v3.7.0` 之间二选一，而 checkout 是
`fetch-depth: 1` ⇒ 那些远端分支根本不存在 ⇒ **任何分支上都恒为 v3.7.0**，v4.1.0 也不例外。
改为按分支名 → `STAGE.yaml` 的 `version:` → `VERSION` 文件依次回退。

### 2.7 #5456 —— Gate summary 的 10 个计数在零计数时被解析错误跳过

`grep -c` 在零匹配时**打印 0 并以退出码 1 结束**；`|| echo "0"` 于是追加第二个 0
⇒ 变量变成多行的 `0\n0` ⇒ `[ "0\n0" -gt 0 ]` 报 `integer expression expected`
并返回 2（假）⇒ **零失败这一唯一常态下，10 个判据全部以解析错误被跳过**。

**修法**：引入 `count_matches()`，把「零匹配 / 文件不存在 / N 个匹配」三种情况
归一成**恰好一个整数**。

### 2.8 #5424 —— Security 门禁在 v4.x 上从未执行

`ga3-security-scan` 的 `if:` 只匹配 `develop/v3.12.0` / `ci/v3.12.0-` ⇒ 在 v4.x 上一律 skipped。

**修法**：`if:` 放宽到 `develop/v4.` / `release/v4.`（并保留 v3.12.0 口径）。

### 2.9 #5483（本批次新发现）—— Gate summary 步骤缺收尾 `fi`

`.gitea/workflows/ci.yml` 的最后一个 step 的 `if` 块**没有 `fi`**（文件止于该行）：

```
$ bash -n -c "<Gate summary 的 run 体>"
bash: -c: line 17: syntax error: unexpected end of file
```

⇒ 该步骤体整体是 bash 语法错误、**恒 exit 2** ⇒ 这一汇总判据**从未真正判定过任何门禁**。
它之所以从未暴露，正是因为 #5455 让 `postcheck` 一次都没跑过。

**修法**：补上 `fi`；并补一条**通用**回归断言 —— 用 `bash -n` 校验**每一个** step 的
`run` 体都是合法 shell（对所有工作流、所有 step 成立，成本近乎为零）。

### 2.10 #5484（本批次新发现）—— 取模除零的陈旧断言
#5420 修好、A2 维度**第一次真正跑起来**后，立刻暴露一个此前从未被执行过的红灯：

```
---- expr::tests::test_eval_arithmetic_modulo_by_zero_returns_null stdout ----
assertion `left == right` failed
  left: Null
 right: Integer(0)
```

归因：`#5326`（`f73c20fd01`）把「整数除零返回 0」改成「返回 Null」以对齐
MySQL/SQLite 语义，**只改了实现**，测试断言与两处文档注释都留在旧行为上。
⇒ **实现是对的，测试是陈旧的**：测试名 `..._returns_null` 与它自己的断言
`Value::Integer(0)` 互相矛盾。

**修法**：断言改为 `Value::Null`；修正 `eval_arithmetic` 的函数文档与模块文档里
「`Integer` → 0」的陈旧描述；并在断言旁注明与 #5326 的对应关系。

### 2.11 #5444 的第二处 —— `"${version}"` 是**未定义变量**

postcheck 里两处把步骤输出当成 bash 变量读：

```yaml
bash gate/gate.sh "${version}" 2>&1 | tee gate_report.log
bash scripts/gate/check_evidence_binding.sh "${version}" "gate/evidence_binding_out/" 2>&1 | tee evidence_binding.log
```

`version` 是上一步（`id: version`）的**输出**，Actions 的读法是
`${{ steps.version.outputs.version }}` —— `"${version}"` 是一个**从未被赋值的
bash 变量**：

- 「Evidence Binding Check」步骤本来就有 `set -euo pipefail`
  ⇒ `set -u` 直接让它以 `version: unbound variable` 失败
  ⇒ **该步骤一直在失败**，只因 postcheck 从未执行（#5455）而无人发现；
- 「Gate L1 — Code Quality」步骤没有 `set -u` ⇒ 变量被当成空串
  ⇒ `gate/gate.sh ""` 落到脚本自己的默认版本 `v3.7.0`。

**修法**：两处都改成 `"${{ steps.version.outputs.version }}"`；
并补一条**通用**回归断言 —— 一个 step 里用 `${VAR}` 引用的每个 shell 变量，
必须 (a) 在本 step 内被赋值、(b) 由本 job **更早**的 step 通过 `$GITHUB_ENV` 导出、
或 (c) 属于 runner/CI 提供的已知变量。

### 2.12 #5485（本批次新发现）—— P13 / P15 的基线文件不在版本控制里

`check_test_count_monotonic.sh` 与 `check_oracle_present.sh` 都读
`tests/baseline/*.json`；两者在基线缺失时都走「首次运行：建立基线」并 **exit 0**
⇒ 恒绿。而这两个文件**都不在仓库里**（同目录的 `drift_baseline.json` 是提交了的，
`.gitignore` 第 192 行 `!tests/baseline/*.json` 本来就是否定规则）。

⇒ 在任何 fresh checkout 上，P13 与 P15 每次都「第一次运行」然后通过：
P13 本该在测试数**下降**时失败、P15 本该在**新增**无 oracle 门禁时失败 —— 都不可能。

**修法**：提交两个基线文件（内容是仓库属性快照，与机器无关），
P13 随即能在测试数下降时失败、P15 能在新增无 oracle 门禁时失败；
顺带修 P13 脚本里硬编码的 `"version": "v3.9.0-rc7"`
（它从写下那天起就一直在给每一个版本记同一个版本号），
改为从 `docs/releases/v*/STAGE.yaml` 的 `version:` 依次回退；
并补一条**通用**回归断言：任何引用 `tests/baseline/*.json` 的门禁脚本，
其基线文件都必须存在于仓库里。

## 5. 诚实的边界

1. **CI 仍然不会立刻全绿。** 本批次让判据**第一次真正被执行**，
   它们第一次执行就会暴露仓库里既有的红灯 —— 那是真相，不是本批次引入的。
   `develop/v4.1.0` 的分支保护 `enable_status_check: False`，
   所以 CI 红不阻塞合并；本 PR 的合并依据是**本地等价证据**（见 §3），
   不是 CI 绿灯。
2. **覆盖率维度可能记为 NOT-RUN。** 真门禁需要 `cargo-llvm-cov`；
   runner 上没有该子命令时按受控原因码 `COVERAGE_TOOL_MISSING` 记 NOT-RUN。
   ⇒ 「覆盖率已测量」目前**不可声称**。
3. **`legacy/check_alpha.sh` 不再在 CI 发布路径上**（它仍是 v2.9.0 的历史回归件）。
   它的 R0 检查引用 `verification_report.json`（仓库根目录不存在该文件），

## 6. LEARN（知识沉淀）

1. **「门禁恒绿」有两个位置**：判定逻辑内部（批次 2 的 #5417/#5418/#5419），
   以及**判定结果接到 CI 结论的那根线**（本批次）。
   只修前者不够 —— 后者可以让前者修得再对也白修。
2. **未执行过的判据等于不存在的判据。** `postcheck` 的 18 个步骤、其中的
   「缺 `fi`」「计数解析错误」「字符集漂移」三个缺陷，**同时存在了很久**，
   因为它们从未被执行。⇒ 任何新门禁，接线后必须**先确认它真的跑过一次**。
3. **字符集漂移是 Unicode 层面的静默不匹配。** `❌`(U+274C) 与 `✗`(U+2717)
   肉眼几乎一样，但 grep 不一样。⇒ 跨脚本的判定标记必须是**单一常量**，
   且最好选 ASCII。
4. **「注释在宣称什么」与「代码在做什么」必须对账。** 本批次遇到两处
   注释与行为相反（`legacy-gate` 的 `|| true`、TPC-H 步骤的「fails hard」）。
5. **修好一个恒红门禁，会立刻露出它掩盖的东西。** #5420 修好后，
   A2 维度第一次跑起来就抓到 #5484。⇒ 恒红门禁的修复是**发现**的起点，
   不是终点。
6. **判据要写成不变量，而不是点名。** 「任何把门禁管道出去的步骤都要开 pipefail」
   比「第 571 行要改」更能防回归；`bash -n` 校验所有 step 的 run 体
   则一次性挡住了「写漏一个 `fi`」整类缺陷。
