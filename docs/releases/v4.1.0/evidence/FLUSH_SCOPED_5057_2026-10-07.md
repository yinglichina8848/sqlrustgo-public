## 缺陷：`flush()` 静默丢弃非活动库的行

`WriteState::dirty_tables` 是 `HashSet<String>`，存**裸表名**；flush 落盘时用
`current_db` 解析每个名字决定写哪个目录。裸名无法表明所属库，于是两个库里的
同名表在集合里**合并成一个条目**，那唯一一次写入落到当前库目录。

探针 `probe_5057_flush_cross_db.rs`（修复前实跑）：

```
d1.t <- 3 行, d2.t <- 3 行, current_db = d1
flush() -> Ok(())                      <- 无任何报错
d1/t.json  485B   3 行                 <- 正确
d2/t.json  330B   "rows": []          <- 3 行彻底消失
after reopen, scan_in_db("d2","t") = 0 rows
```

`SESSION_CONTEXT_5057_RECON_2026-10-07.md` §8 早已记录此处「被 `dirty_tables`
的混合 key 阻塞，刻意不半修」。本批把前置条件补齐后即可修复。

## 缺口的完整链条

三处独立缺陷叠加，**修任何一处都不够**：

| # | 位置 | 问题 |
|---|------|------|
| 1 | `dirty_tables: HashSet<String>` | 存裸名，两库同名表合并成一条 |
| 2 | `drain_dirty_windowed` 消费点 | `let db = self.current_db_name()` 对循环里每个条目用同一个库 |
| 3 | `flush_all_buffers` | 只遍历当前库的 buffer 前缀，其他库的行一直卡在 `insert_buffer`，`tables.rows` 为空 |

第 3 点是关键：即使 1、2 修好，drain 拿到的仍是**空表**（`last_saved == total == 0`）
而跳过。实测证明了这一点 —— 只做 1、2 后 `d2/t.json` 仍是 `rows: []`。

另有两处同源问题：

- `last_saved_row_count` 的 key 也是裸表名 → `d1.t` 与 `d2.t` 共享一个「已落盘
  行数」计数，第二个表看起来已经持久化而跳过写入。
- `append_table_delta` / `delta_path` 全部经 `current_db` 解析 → 两个库的增量行
  写进**同一个** `<table>.delta`，加载时被重放进另一张同名表。

## 改动

**`dirty_tables` 改为 `HashSet<(String, String)>`（库, 表）。**

没有采用「`scoped_key` 字符串 + 拆回」：`scoped_key` 会把两半都小写化，拆回来的
表名是��写的，而 `save_table_window` 用它拼 `<table>.json` —— 大写表名 `T` 会被
持久化成 `t.json`。元组不需要分隔符往返，保留原始大小写。

`engine.rs` 新增 `split_scoped_key`，与 `scoped_key` 同处，令 `DB_SEP` 保持模块私有
—— 两处手写分隔符必然漂移。

具体：

- 12 个写入点全部改为元组（6 处裸名 → `(db, table)`；6 处已是 `scoped_key` →
  `(current_db, table)`）
- `drain_dirty_windowed` 返回 `(db, table, window, total)`，查缓存与
  `last_saved_row_count` 都用条目自己的库
- 两个消费点（`flush`、`flush_parallel` 的串行与并行分支）改用条目携带的库
- `last_saved_row_count` 的 key 作用域化
- `append_table_delta(db, table, rows)` 新增 `db` 参数；三个 `delta_path` 调用点
  改 `delta_path_in(db, …)`
- `flush_all_buffers` 改为遍历**所有**库的 buffer，按 key 分组去重
- 删除 `delta_path`（不带 db 的版本）：改完后已无调用者。留着它等于留一个无法
  表明所属库的入口 —— 本批缺陷正是这种入口造成的

## 变异验证

### M-F：`flush_all_buffers` 退回只处理当前库（CAUGHT）

```
test issue_5057_cross_db_flush_survives_reopen ... FAILED
test issue_5057_cross_db_delete_is_persisted ... FAILED
test issue_5057_delta_files_are_per_database ... FAILED
test issue_5057_flush_persists_rows_of_every_database ... FAILED
test issue_5057_unnamed_family_still_follows_current_db ... ok
test issue_5057_second_flush_does_not_duplicate_rows ... ok

issue_5057_flush_persists_rows_of_every_database:
  d2/t.json holds the wrong rows
  left: []
 right: [21, 22, 23]
```

4/6 失败，报错文本与修复前探针的现象逐字一致。两条通过的都是只涉及单个
`current_db` 的用例（对照组与重复 flush 用例），不是漏网。

### M-E：`drain` 忽略条目自带的库（存活，且暴露了断言不足）

把 drain 里的 `db` 覆写为 `current_db`（即第 2 条缺陷的精确还原），6/6 仍通过。

原因：`flush_buffer` 自己就会把 buffer 里的行持久化到条目指定的库，之后 drain 看到
`last_saved == total` 便跳过。于是这条变异在当前调用顺序下不可观测。

结论与处置：**M-F 本身就是「丢弃条目所带库信息」的变异，且 CAUGHT** —— 二者等价，
M-E 没有提供额外信号，不重复报告。M-E 的价值在于坐实了一件事：`drain` 的库传递与
`flush_all_buffers` 是两条独立的正确性保证，不能互相顶替，也因此不能只修一条。

## 测试

新增 `file_storage_flush_scoped_5057.rs`，6 个用例：

1. `flush_persists_rows_of_every_database` —— 直接读两个 json 文件比对行值
   （不用 `scan_in_db`，它会合并写缓冲，证明不了持久化）
2. `cross_db_flush_survives_reopen` —— 重开 storage 后两库行都在
3. `cross_db_delete_is_persisted` —— 非活动库的删除被持久化，且没泄漏到活动库
4. `second_flush_does_not_duplicate_rows` —— 反复 flush 不重复不丢行
5. `unnamed_family_still_follows_current_db` —— **对照组**：不带库的方法仍跟随
   `current_db`。若两族被合并，先挂的是这一条
6. `delta_files_are_per_database` —— delta 不跨库污染

探针 `probe_5057_flush_cross_db.rs` 保留：只打印不断言，用来观察落盘去向。

## 影响面

改动全部落在 `crates/storage/src/file_storage.rs` 与 `engine.rs`。相关字段与方法
（`dirty_tables`、`last_saved_row_count`、`save_table*`、`delta_path*`）均为
`FileStorage` 私有成员，跨 crate 无调用点。

注意 `crates/storage/src/file_table.rs` 有同名但无关的 `dirty_tables`（属于
`TableEngine` trait），本次未触碰。

## 已知遗留

`split_scoped_key` 返回的两半是小写形式，`flush_all_buffers` 传给 `flush_buffer`
的表名因此是小写。这与改动前一致（旧的 `strip_prefix` 路径同样得到小写名），
未引入新行为；但它意味着「表名含大写字母」的落盘文件名是小写。属独立问题，
未在本 PR 处理。
