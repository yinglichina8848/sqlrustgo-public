## 1. 问题陈述

`scripts/sync/5remotes_sync.sh` 在本机**无限挂起**，实测 900s 超时仍未返回：

```
Step 3: SSH container update-ref for gitea250 / gitea252
<此处挂死 900s，被 timeout 杀掉>
```

此前会话据挂起现象得出结论：**「github / gitee / gitcode 三个远端在本机 SSH 不可达」**，
并把该结论写进了 lessons。

**本迭代用实测证明该结论是错的。** 三个远端认证完全正常。

---

## 2. 根因（实测隔离，非推测）

不是网络不可达，是 **ssh-agent 失效导致 ssh 在公钥认证阶段阻塞**。

### 2.1 本机状态

```
$ ssh-add -l
（空 —— agent 已死）
$ echo $SSH_AUTH_SOCK
/var/run/com.apple.launchd.mngm6DFt8Q/Listeners
（socket 文件仍在 → connect() 不立即失败 → ssh 阻塞在 agent 往返上，且无任何输出）
```

### 2.2 对照实验（同一台机器 / 同一网络 / 同一密钥）

| 命令 | 结果 |
|---|---|
| `ssh -T git@github.com` | **挂起，无输出** |
| `ssh -o IdentityAgent=none -T git@github.com` | `Hi yinglichina8848! You've successfully authenticated` |
| `ssh -o IdentitiesOnly=yes -o IdentityAgent=none -T git@github.com` | 认证成功 |
| `ssh -o IdentitiesOnly=yes -o IdentityAgent=none -T git@gitee.com` | 认证成功（`Hi 李莹(@yinglichina)`） |
| `ssh -o IdentitiesOnly=yes -o IdentityAgent=none -T git@gitcode.com` | 认证成功（`Welcome to GitCode, BreavHeart`） |
| `ssh -o IdentitiesOnly=yes -o IdentityAgent=none liying@192.168.0.250 true` | 成功 |
| `ssh -o IdentitiesOnly=yes -o IdentityAgent=none liying@192.168.0.252 true` | 成功 |

排除项：

- TCP 22 端口对 github / gitee / gitcode **全部 OPEN**
- 主机密钥与 `known_hosts` **一致**（`ssh-keyscan` 比对 ed25519 完全相同）
- 密钥本身有效（`IdentityAgent=none` 下 5/5 认证通过）

### 2.3 关键选项辨析

| 选项 | 作用 | 能否切断失效 agent 阻塞 |
|---|---|---|
| `BatchMode=yes` | 禁止交互式口令/口令短语提示 | **否** |
| `IdentitiesOnly=yes` | 只提供指定的身份 | **否**（仍会与 agent 往返） |
| `IdentityAgent=none` | 完全不接触 agent | **是** |

### 2.4 次生缺陷

**容器仓库发现使用 `find / -maxdepth 6`**——250 容器上实测 **9 分钟未完成**，
单这一条就吃光脚本 900s 预算。而两台机器的仓库布局是**已知且互不相同**的：

- 250：`/git/<owner>/<repo>.git`
- 252：`/data/git/repositories/<owner>/<repo>.git`

## 3. 变更清单

### 3.1 `scripts/sync/5remotes_sync.sh`

| 变更 | 说明 |
|---|---|
| 新增 `SSH_OPTS` 数组 | 唯一选项来源；`IdentityAgent=none` + `IdentitiesOnly=yes` + `BatchMode=yes` + `ConnectTimeout` + `ServerAliveInterval/CountMax`（把「连上但不应答」封顶 ~45s） |
| 全部 3 处 ssh 调用改用 `SSH_OPTS` | 消除「漏一处就复现」的隐患 |
| 新增 `GIT_SSH_COMMAND` 自动设置 | git 的 SSH 通道（push/fetch）不继承调用方失效的 agent |
| `StrictHostKeyChecking` 由 `no` 改为 `accept-new` | `no` 静默接受任何变更过的主机密钥；`accept-new` 只自动接受首次见到的密钥，对已变更的拒绝。5 个主机在 `known_hosts` 中均已存在，实测全部通过 |
| 容器发现改为**定向探测** | 已知布局优先（O(1)）；`find` 收窄为 `/git` `/data/git` 且 `maxdepth 4` 的兜底 |
| 移除硬编码明文凭据 | 改由 `GITEA_USER` / `GITEA_TOKEN` 提供，缺失即**明确报错并跳过该主机**；凭据改走 `http.extraheader`（Basic），不再嵌在 URL 里 |
| 新增 `GITEA_HOSTS` / `GITEA_PUSH_URL` 覆盖开关 | 既是可测试性 seam，也是「只同步部分主机 / 推到镜像仓库」的真实需求 |
| `cd "$REPO_ROOT" \|\| exit 1` | `set -e` 未开启时，cd 失败会让脚本在错误目录继续跑 |
| 空 `GITEA_HOSTS` 显式拒绝 | bash 3.2（macOS 系统 bash）下空数组展开在 `set -u` 下是未绑定变量 |

> 这正是变异测试的价值——它暴露了测试自身的鉴别力缺口。

### 4.4 凭据门禁的自检

门禁本身也必须证明不是空过。注入 4 种泄露形态：

| 注入形态 | 捕获 |
|---|---|
| `GITEA_TOKEN = "<40位hex>"` | ✅ 扫描 1 |
| `echo "details8488" \| sudo -S true` | ✅ 扫描 2 |
| `curl -s -u "openclaw:details8848"` | ✅ 扫描 3 |
| `URL="http://user:<token>@host/repo.git"` | ✅ 扫描 4 |

移除探针后仓库恢复 `✅ 硬编码凭据检查通过`。

> 扫描 1 曾在首轮**漏报**：关键词匹配区分大小写（`TOKEN` vs `token`）。
> BSD grep 的 `-E` 不支持 `(?i)` 修饰符，改为 `-i` 开关后修复。
> 误报（git SHA、`PASS:` 状态词）通过「要求同行出现凭据关键词 + 至少 16 位十六进制
> + 至少一个非零字符」三重收窄消除。
