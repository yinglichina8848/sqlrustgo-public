§1  #4982 合并后独立复测
--------------------------------------------------------------------------------

实测输出：

    P0 before anything: []
    P1 A 自己的事务内看到: [1]
    P1 B 看到 A 未提交的写: [1]                  <- 与修复前一致
    P2 A 看到 B 未提交的写: [1, 2]              <- 与修复前一致
    P5 B 看到 A 的未提交 UPDATE: [["1","A-DIRTY"], ["2","A-DIRTY"]]
    P6 A 回滚后 B 看到: [["2","b-uncommitted"]]
    R1 A 事务内第一次读: [2]
    R2 A 事务内第二次读: [2, 99]
    R2 一致? false

逐项对比：

  探针  修复前(c4d6d5a420)                      #4982 后(95880f76cc)                判定
  ----  ------------------------------------  ------------------------------------  ------
  P1    [1]                                    [1]                                 未修
  P2    [1, 2]                                [1, 2]                              未修
  P5    [["1","A-DIRTY"], ["2","A-DIRTY"]]    [["1","A-DIRTY"], ["2","A-DIRTY"]]  未修
  P6    [["1","a-uncommitted"],               [["2","b-uncommitted"]]             已修
        ["2","b-uncommitted"]]
  R2    [1] vs [1, 2]                         [2] vs [2, 99]                      未修

结论：#4982 修的是「回滚后脏值残留」，不是「跨连接脏读」。这两件事容易混。

  P6 变干净的原因是 committed 标记让 rollback_tx 的丢弃真正生效 ——
  版本被 drop，所以没人再读得到。这是真实修复。

  P1/P2/P5 未变的原因在 find_visible（crates/storage/src/mvcc.rs:289）：

      if v.committed {
          v.visible_from_ts <= snapshot_ts
      } else {
          reader_tx != 0 && v.created_by_tx == reader_tx
      }

  未提交版本对读者可见的条件是 reader_tx == created_by_tx。而 reader_tx
  来自存储级单值 FileStorage.current_tx_id —— A 设了它，B 读时拿到的还是
  A 的值。**读的人无法被区分于写的人**，「只对作者可见」退化为「对所有人
  可见」。

  剩下的不是隔离机制问题，是跨连接身份问题。created_by_tx 字段本来就在
  版本链里，数据模型不缺东西，缺的是把每连接的真实事务身份传进存储层。
  该项由 #4983 承接。

§2  决策点 3 实测：GC 回收未提交版本 → COMMIT 静默丢数据
--------------------------------------------------------------------------------

设计文档 §3.3 提出的第三个决策点「GC 如何处理未提交版本」，此前标注
「尚无人验证」。本次验证发现缺陷，已立 #4986。

机制
----

#4982 让未提交版本在写入时带 visible_from_ts = <写入时刻>，只有 commit_tx
才把它改写为提交时刻。于是 pending 版本的 visible_from_ts 是一个**已经变老**
的值。

而 gc（crates/storage/src/mvcc.rs:223）有两处回收判断：

    // Step 1: trim multi-version chains
    if chain[i].visible_from_ts < cutoff { chain.remove(i); dropped += 1; }

    // Step 2: evict single-version chains
    if chain.len() == 1 && chain[0].visible_from_ts < cutoff { to_evict.push(pk.clone()); }

两处都只看 visible_from_ts，**没有任何一处检查 committed**。

实测
----

场景：事务 7 在 ts=10 写入一行（未提交）→ 快照推进到 1000（cutoff=900）
→ gc(1000, 100) → 事务 7 提交。

    PROBE before_gc visible_to_own_tx=1
    PROBE gc_dropped=1 after_gc_visible_to_own_tx=0
    CONFIRMED: GC 回收了未提交版本 —— 该事务 COMMIT 时写会丢
    PROBE after_commit visible_to_public=0

写入 → 提交，数据没了。全程 errors = 0，无任何报错。

为什么现有测试没抓到
--------------------

tx_isolation_and_escape_hatch_test.rs 的用例都在毫秒内完成，事务持续时间
远小于 gc_lag（默认 256~1000），pending 版本来不及变老就被提交或回滚。
要复现需要「事务写入 → 停顿超过 gc_lag → GC 跑过 → 再提交」。

复核：#4983（08afba8cf6）虽在 mvcc.rs 中使用了 committed，但改的是
pending 主键集合的收集，**未改 gc 的 cutoff 判断**。本缺陷在 a6ed136dd2
上仍然成立。

修复方向（记录在 #4986）
-----------------------

最小修复是给两处判断加 `v.committed &&`。但这不够 —— 跳过后长事务的
pending 版本会永久滞留，版本链无限膨胀，正是决策点 3 原本担心的方向。
完整修法需要 pending 版本的生命周期策略：记录创建时刻（而非借用会被
commit_tx 改写的 visible_from_ts）、以「事务已不在活跃表中」为回收前提、
配合 MvccGCRunner 的活跃事务跟踪。

§3  性能测量：绝对 TPS 不可用，改为只做 A/B
--------------------------------------------------------------------------------

开发机 12 人共享（load average 14.64 / 10 核）。同一配置下实测：

  point_select  17532 / 14496 / 15870 TPS     （无编译并行时）
  read_write      8 / 20112 / 54580 TPS       （冷启动 + 负载波动）
  read_write    1184 / 316 / 995 TPS         （有 cargo test 争 CPU 时）
  point_select   595 / 459 / 515 TPS         （同上）

波动达 10 倍以上，且编译任务并行会把吞吐打到 1/30。**这些数字不能作为
定隔离级别的依据。**

已按用户决定停止绝对 TPS 测量，改为 before/after 交替的 A/B 比值
（PERF_4956_COMMIT_FLUSH_AB_2026-10-04.md 即此法），且只在无编译任务
并行的时段跑。

测量方法上修掉的两个自身缺陷（如实记录，避免复用脚本时重蹈）：

  1. 缺预热 —— 每个场景首轮恒为个位数 TPS（表刚 prepare 完，页缓存冷、
     WAL 刚建），次轮立刻跳到数万。已加 warmup 轮并丢弃。
  2. p95 解析错 —— 用 head -1 取值取到的是字段名行，所有轮次都报
     p95_ms=95。已改为按字段末列提取。
