## 2. 缺陷逐条剖析

### 2.1 #5417 — 聚合门禁的 `|| true` 吞掉退出码

**位置**：`scripts/gate/check_full_gate_verification.sh:69`（修复前）

```bash
run_gate() {
    local name="$1" script="$2" expect_code="${3:-0}"
    ...
    local output
    output=$(bash "$script" 2>&1 || true)   # ← 强制退出码为 0
    local code=$?                          # ← 因此恒为 0
    ...
    if [ "$code" -eq "$expect_code" ]; then
        echo "  ✅ PASS (exit $code)"        # ← 永远走这一支
```

**为什么必然恒绿**：`|| true` 是命令替换的最后一个命令，bash 会把整个 `$( ... )` 的退出状态
设为 `|| true` 的退出状态（0）。因此 `code` **永远是 0**，`[ "$code" -eq 0 ]` 永远为真。

**影响面**：这个 `run_gate()` 是 D9 聚合门禁的**唯一**判定入口，8 个维度
（D1-D5 RC/GA、D6b 测试清单、D7 INT 债、D8 架构/语义债、跨版本债、测试计划一致性、
PR 模板、证据生成）**全部**经过它。因此**整个 8 维聚合门禁没有任何一条路径能返回失败**。

**实测复现**（修复前的脚本，桩 cargo 加速子门禁）：

```
$ bash -c 'source scripts/gate/check_full_gate_verification.sh
           STUB=$(mktemp); printf "#!/usr/bin/env bash\nexit 1\n" > "$STUB"; chmod +x "$STUB"
           run_gate "StubFailingGate" "$STUB" 0; echo "FAIL_COUNT=$FAIL_COUNT PASS_COUNT=$PASS_COUNT"'
  --- [StubFailingGate] ---
  ❌ FAIL (exit 1, expected 0)      ← 修复后的正确行为
```

> 修复前的同一命令输出为：
> ```
>   --- [StubFailingGate] ---
>   ✅ PASS (exit 0)
>   FAIL_COUNT=0 PASS_COUNT=1
> ```

**同时存在的第二个缺陷**（同一函数族）：

```bash
run_gate "D1-D5 RC/GA (--skip-a5)" "$SCRIPT_DIR/check_rc_ga_gate.sh --skip-a5" 0
```

`--skip-a5` 被拼进了**脚本路径**里，而该路径不存在 ⇒ `[ ! -f "$script" ]` 命中 ⇒
该维度被记为 `NOT_FOUND`（一个 FAIL），而不是「带 `--skip-a5` 参数运行 RC/GA 门禁」。
调用方是 `scripts/gate/check_r2_invariants.sh`（R2 证据刷新驱动，60 秒预算）。

### 2.3 #5419 — `${ARRAY}` 在 bash 下只展开第 1 个元素

**位置**：`scripts/gate/check_rc_ga_gate.sh` 的 `run_d6_integration_tests()`（修复前）

```bash
for t in ${D6_INTEGRATION_TESTS}; do        # ← 没有下标
    if [[ ! -f "tests/${test_name}.rs" ]]; then
        log_info "D6: skip $test_name (file not found)"
        continue
    fi
    ...
```

**bash 语义**：`${ARRAY}`（不带下标）等价于 `${ARRAY[0]}`。因此
**51 条策展清单只有第 1 条 `wal_integration_test` 被迭代到**，
而它不在 `tests/wal_integration_test.rs`（实际在 `tests/integration/migration/`）⇒
被当作「文件不存在」跳过 ⇒ `D6_TOTAL` 保持 0 ⇒ 摘要打印：

```
    ℹ D6: skip wal_integration_test (file not found)
    ✓ PASS D6 summary: 0/0 integration tests PASS
```

**并且**：即使循环跑起来了，旧的「文件存在性探针」`tests/${test_name}.rs`
也只能命中**位于 `tests/` 根目录的 4 条**清单项 —— 其余 44 条在子目录里
（`tests/integration/...`、`tests/e2e/...`、`tests/ci/...`），探针永远看不到。

**实测复现**（修复前的脚本，`ga` 模式，桩 cargo）：

```
$ PATH=/tmp/gatestub:$PATH bash scripts/gate/_old_rc_ga_gate.sh ga
    ℹ D6: skip wal_integration_test (file not found)
    ✓ PASS D6 summary: 0/0 integration tests PASS
$ echo $?
0
```

**清单本身的陈旧**：策展清单里的 `ci/buffer_pool_test` 与 `e2e/observability_test`
两条对应的文件在 v3.12.0 已被**有意退休**（commit `c3c6bc675d`
「v3.12.0(retire): remove dead tests + unregister from Cargo.toml」删除文件并从
`Cargo.toml` 注销），但清单从未同步 ⇒ 这两条**永远无法解析**。
处置：从清单移除并写明理由（见 §4.2）。

**裁决遗漏**：`D6_FAIL` / `D7_BLOCKERS` 两个计数器**从未进入 verdict**，
verdict 只看 D1/D2/D8/D9 的 blockers 与 D3 的失败 ⇒ **D6 或 D7 红了，门禁照样报 PASS**。

### 2.5 附带发现：固定日志路径导致证据互相覆盖

在实测 D6 期间发现的**第 5 个缺陷**（本 PR 一并修复）：


### 2.6 D6 第一次真跑，暴露出一个从未被测到的引擎缺陷

D6 门禁在本 PR 之前**从未真正执行过任何测试**（§2.3）。把它修好后跑第一次真实全量，
得到的结果是 **46/47 PASS，1 FAIL**，失败目标是 `regression_test`：

```
thread 'test_regression_suite' panicked at tests/integration/sql/regression_test.rs:673:5:
assertion `left == right` failed:  回归测试有 1 个测试失败
  - null_handling_test: test tests::green_4154_alter_table_drop_default_accepted ... FAILED
```

顺着失败子用例往下追，得到一个**范围比用例本身大得多**的结论：

```
PROBE A_SET_DEFAULT_ON_ORIGINAL_COLUMN                      => ERR Execution error: Table not found: t
PROBE B_AFTER_ADD_COLUMN_SET_DEFAULT_ON_ORIGINAL            => ERR Execution error: Table not found: t
PROBE C_AFTER_ADD_COLUMN_SET_DEFAULT_ON_NEW_COLUMN          => ERR Execution error: Table not found: t
PROBE D_AFTER_ADD_COLUMN_SELECT                             => OK
PROBE E_SECOND_ADD_COLUMN                                   => OK
PROBE F_AFTER_ADD_COLUMN_DROP_DEFAULT_ON_ORIGINAL           => ERR Execution error: Table not found: t
PROBE G_NO_ADD_COLUMN_DROP_DEFAULT                          => ERR Execution error: Table not found: t
```

即：**`ALTER TABLE ... ALTER COLUMN ... SET DEFAULT` 与 `... DROP DEFAULT` 在
`MemoryStorage` 上完全不可用**（与有没有 `ADD COLUMN` 无关），
而同一张表上的 `SELECT` / `ADD COLUMN` 正常。

**根因**（`crates/storage/src/engine.rs:3944`，修复前）：

```rust
fn set_column_default(&mut self, table: &str, column: &str, default_value: Option<String>) -> SqlResult<()> {
    let info = self
        .table_infos
        .get_mut(&table.to_lowercase())          // ← 裸表名
        .ok_or_else(|| SqlError::ExecutionError(format!("Table not found: {}", table)))?;
```

`MemoryStorage::create_table` 把表存在**数据库作用域 key** `db\u{1}table`
（`scoped_key` / `tbl`）下，而 `set_column_default` 用**裸表名**去查 ——
两者**永远不可能相等** ⇒ 查找必然落空。

它的三个兄弟方法都是对的：

| 方法 | 查找方式 |
|------|---------|
| `drop_column` | `self.tbl(table)` ✅ |
| `modify_column` | `self.tbl(table)` ✅ |
| `rename_column` | `self.tbl(table)` ✅ |
| **`set_column_default`** | **`&table.to_lowercase()` ❌** |

**这为什么一直没被发现**：
1. D6 门禁从未跑过任何测试（§2.3）⇒ 这条路径**从不被执行**；
2. 唯一覆盖它的用例在 `tests/anomaly/null_handling_test.rs`，由 `regression_test` 聚合，
   而 `regression_test` 目标从未在 CI 里被真正跑到（#5407：test job 在全部 400 次 run 里零次成功）；
3. 落盘后端**根本没有实现**这个方法（trait 默认返回 “not supported”）⇒
   生产路径上同样不可用，且**没有任何落盘后端用例覆盖**（见新立 issue #5471）。

**归因**：`git diff HEAD --stat -- '*.rs' 'src/' 'crates/'` 在修复前为**空** ——
本 PR 未触碰任何 Rust 源码，故该失败**与本 PR 无因果关系**，
是 D6 门禁第一次真跑才暴露出来的既有缺陷。

**处置**：本 PR 内修复 `MemoryStorage` 的查找（1 行，与三个兄弟方法对齐）+ 新增存储层
回归用例（4 例，RED 双向验证通过）。其余后端未实现的问题、以及列名大小写敏感的问题，
分别立案 #5471 / #5472。

## 3. 修复设计

### 3.1 可测性改造：把决策逻辑抽成无副作用的纯函数

三个门禁脚本此前是「一坨线性 shell」，**无法在不跑完整门禁的前提下测试其判定逻辑** ——
这正是它们能长期保持恒绿而无人察觉的结构性原因。

本次改造在 `check_rc_ga_gate.sh` 中引入三个纯函数：

| 函数 | 职责 | 返回 |
|------|------|------|
| `gate_parse_args <args...>` | 解析 CLI：区分**维度选择器**与**flag** | 0=OK / 2=未知参数 / 3=请求帮助 |
| `gate_expected_dims <mode>` | 给出该模式下**必须执行**的维度清单 | 空格分隔的维度串 |
| `gate_verdict_for <mode> <executed> <10 个计数器>` | 由「实际执行了哪些维度」+ 各维度计数器算出裁决 | 设置 `GATE_VERDICT` / `GATE_EXIT_CODE` / `GATE_MISSING_DIMS` |

同时在两个脚本末尾加了 **source 守卫**：

```bash
if [[ "${BASH_SOURCE[0]}" == "${0}" ]]; then
    main "$GATE_TYPE"
fi
```

使得回归用例可以 `source` 门禁脚本后**直接驱动其判定逻辑**，
而不必付出跑完整门禁（分钟级 + 依赖真实 cargo）的代价。

`check_full_gate_verification.sh` 的执行体同样被包进 `main()` 并加 source 守卫。

### 3.2 参数解析：flag 与维度选择器分离

```bash
gate_parse_args() {
    local arg
```
