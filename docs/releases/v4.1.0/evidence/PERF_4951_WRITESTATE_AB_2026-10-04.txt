## 4. 结论：回退是确定性的，不是噪声

三侧 CV 仅 2.4%~3.2%，远低于 29% 的组间差距。
**mine 的最高值 2809.3 仍低于 base 的最低值 3632.6，也低于 mid 的最低值 3815.1** ——
两组区间零重叠，任何顺序检验都判定为显著差异。

`mid/base = 1.044` 说明三个隔离修复（#4960/#4981/#4986）本身是中性的、
甚至略有正收益。**全部回退来自 PR #4990 的 WriteState 重构**。

## 5. 根因（已定位到具体代码）

#4951 AC2 把 4 个受保护字段打包进 `RwLock<WriteState>` 后，`&TableData`
无法再从读守卫借出，于是 `get_table` 的签名被改：

```diff
- pub fn get_table(&self, name: &str) -> Option<&TableData>   // 借用，零成本
+ pub fn get_table(&self, name: &str) -> Option<TableData>    // 全表深拷贝
```

而 `get_table_info` 一直就是这一行：

```rust
self.get_table(table).map(|t| t.info.clone())
```

同一行代码在旧签名下只克隆 `TableInfo`（几个字段），在新签名下**先把整张表
的所有 `Record` 深拷贝一遍，再把 rows 全部丢掉**。

致命之处在调用点 —— `crates/storage/src/file_storage.rs` 的 `scan_pk` 在
**每一次主键点查的开头**都调用 `get_table_info`：

```rust

    if let Ok(info) = self.get_table_info(table) {   // <-- 每次点查都全表克隆
        if info.columns.iter().any(|c| c.primary_key) {
```

而 `oltp_read_only` 的负载几乎全是 `point_select`（60%）。于是「读列名列表」
这个本该 O(列数) 的操作变成了 O(表行数) 的全表深克隆。5000 行 × 8 线程 ×
~2700 QPS，即每秒数 GB 级别的无谓分配。-30% 完全对得上。

## 6. 同 PR 的第二处（次要）

`partition_rows` 同样用了克隆版 `get_table`，随后又 `table_data.rows.clone()`
第二次 —— 每次调用两份全表拷贝；且 rows 与 insert_buffer 分两次取样，
可能来自两个不同的瞬间。已一并修复。
