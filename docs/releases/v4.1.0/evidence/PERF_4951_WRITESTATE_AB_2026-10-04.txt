## 5. 根因（已定位到具体代码）

#4951 AC2 把 4 个受保护字段打包进 `RwLock<WriteState>` 后，`&TableData`
无法再从读守卫借出，于是 `get_table` 的签名被改：

```diff
- pub fn get_table(&self, name: &str) -> Option<&TableData>   // 借用，零成本
+ pub fn get_table(&self, name: &str) -> Option<TableData>    // 全表深拷贝
```

而 `get_table_info` 一直就是这一行：

```rust
self.get_table(table).map(|t| t.info.clone())
```

同一行代码在旧签名下只克隆 `TableInfo`（几个字段），在新签名下**先把整张表
的所有 `Record` 深拷贝一遍，再把 rows 全部丢掉**。

致命之处在调用点 —— `crates/storage/src/file_storage.rs` 的 `scan_pk` 在
**每一次主键点查的开头**都调用 `get_table_info`：

```rust
fn scan_pk(&self, table: &str, pk_column: &str, pk: &Value) -> SqlResult<Option<Record>> {
    if let Ok(info) = self.get_table_info(table) {   // <-- 每次点查都全表克隆
        if info.columns.iter().any(|c| c.primary_key) {
```

而 `oltp_read_only` 的负载几乎全是 `point_select`（60%）。于是「读列名列表」
这个本该 O(列数) 的操作变成了 O(表行数) 的全表深克隆。5000 行 × 8 线程 ×
~2700 QPS，即每秒数 GB 级别的无谓分配。-30% 完全对得上。

## 6. 同 PR 的第二处（次要）

`partition_rows` 同样用了克隆版 `get_table`，随后又 `table_data.rows.clone()`
第二次 —— 每次调用两份全表拷贝；且 rows 与 insert_buffer 分两次取样，
可能来自两个不同的瞬间。已一并修复。

## 4. 本次 A/B 未能覆盖的（诚实边界）

- 只测了**并发只读**一种负载。写路径（oltp_read_write）没有重测，
  `get_table_info` 同样在写路径的点查/更新中被调用，理论上收益相同，
  但**没有实测数据，不做断言**。
- 只测了 5000 行/表这一个规模。全表克隆的代价与行数成正比，
  行数越大回退越严重 —— 但**这个外推没有实测支撑**。
- `partition_rows` 的修复路径需要 >500k 行才走分区分支，本次负载
  （20000 行）**根本没进入该分支**，等于未测。其修复依据是代码审读
  （每次调用两份全表拷贝 + 两次取样可能撕裂），不是实测。
- 绝对 QPS 受本机 12 用户共享影响，只用同机同协议下的**相对比值**。

## 5. 顺带发现：#4986 遗留的失效测试

全量回归时 `mvcc::tests::test_gc_drops_old_versions` 红（left: 2, right: 6）。
逐层定位：

1. 在**未修改的 a38931dc5c** 上失败方式完全相同 → 与本次改动无关
2. 换回 #4986 修复提交 `4b89f976d2` 之前的 mvcc.rs → 通过
   → **由 4b89f976d2 引入**
3. 该测试 `put(..., created_by_tx = i as u64)` 用 tx 0..=9，却一律
   `commit_tx(1, ts)`；10 个版本里只有 created_by_tx==1 的被标 committed。
   #4986 之前 gc 不看该标志，掩盖了不一致；#4986 让两处回收判断都要求
   `committed`，不一致就变成真失败

生产改动是对的（有变异自证），测试才是缺陷方。已改为
`commit_tx(i as u64, ts)`，与同文件姊妹测试写法一致。
