### 0.1 最重要的一个发现：release 构建下是**静默错值**，不是 panic

#5432 的行宽不一致在 debug 构建里表现为 `ResultSet::with_columns` 的 `debug_assert!` panic
（`crates/executor/src/executor.rs:70`）。该断言是 **`debug_assert!`** —— release 构建里被编译掉，
而 `with_columns` **不做任何修复**（不截断、不补齐），行原样存下：

```rust
// crates/executor/src/executor.rs:65-81
pub fn with_columns(columns: Vec<ResultColumn>, rows: Vec<Vec<Value>>, affected_rows: usize) -> Self {
    debug_assert!(
        columns.is_empty() || rows.iter().all(|r| r.len() == columns.len()),
        "row width {} does not match the {} declared columns", ...,
    );
    Self { rows, affected_rows, columns }     // ← 行宽原样保留
}
```

**release 构建实测**（基线 `005b6c18f3`，`cargo build --release`，见 §1.3.1 的完整输出）：

```
$ ./target/release/sqlrustgo-mysql-server exec "… SELECT count(*) FROM orders GROUP BY cust; …"
col_1 | col_2 | col_3 | col_4
Text("bob")   | Integer(1) | Text("bob")   | Integer(200)
Text("alice") | Integer(2) | Text("alice") | Integer(100)
Text("carol") | Integer(1) | Text("carol") | Integer(300)
(3 rows)
```

⇒ **声明 1 列，打印 4 个 cell；第一个 cell 是分组键，计数被挤到第 2 位。**
**不 panic。读第一列拿到的是分组值，不是计数。**

**这比 panic 更危险**：panic 至少会让 CI 变红；静默错值会让 CI 变绿并把错答案写进证据。
debug 测试**看不见**这个形态 —— 而生产构建是 release。
本轮实测已确认这一形态（§1.3.1）。

### 0.2 本变更做了什么

1. 去掉 GROUP BY 路径的「单列 SELECT 跳过重投影」快捷分支，单列与多列走同一条重投影路径；
2. `SELECT *` 分支改为取聚合行的**尾部**（表自身列在 `[group_key..., aggregate..., fd...]` 布局的最后一段）；
3. `MemoryStorage::list_views` 改用 `split_scoped_key` 拆分真实分隔符（与 #5350 在 `FileStorage` 的修法一致）；
4. 新增 `system_tables::is_virtual_schema()`，`information_schema` / `mysql` 作为**虚拟 catalog**
   跳过「库是否已知」校验；
5. `replace_test` 从根包迁到 `crates/mysql-server/tests/replace_exec_test.rs`，用编译期
   `CARGO_BIN_EXE_*` 定位二进制，**去掉 `SQLRUSTGO_REPO_ROOT` 依赖**，并把「跑不起来」从静默变 loud；
6. 新增 3 组回归用例（10 个断言组）锁住「行宽契约」与「`list_views` 契约」。

### 0.3 明确没做什么

- 没有改任何参考期望值来求绿；
- 没有给任何测试加 `#[ignore]` / `skip` 冒充通过；
- 没有把 not_run 计入 passed；
- **没有改动任何已入库的 GA 证据文件**（全量回归会改写 81 个 A04 证据文件 —— 已立 **#5389** ——
  本轮已用 `git checkout -- docs/` 全部还原，见 §6.3）；
- 没有把 #5433 的两个根因混进一个提交：它们分别是存储层与执行层，测试各自独立。

`run_sql` 的取环境变量处：

        .map_err(|_| "SQLRUSTGO_REPO_ROOT env var must be set to repo root".to_string())?,

⇒ `REPLACE INTO` 引擎实现**没有问题**：`src/engine_dml.rs:230` 的实现完好，

### 1.3 #5432 的真因：GROUP BY 投影宽度不匹配（与 HAVING 无关）

`src/engine_select.rs:2596`（改造前）：

```rust
let agg_result_rows = if is_star_agg || select.columns.len() <= 1 {
    // Star / single column: no re-projection needed
    agg_result_rows
} else {
    /* ... 重投影 ... */
};
```

聚合行的实际布局（`src/engine_select.rs:2150-2181`）：

```
[group_key..., aggregate..., fd_per_col...]
```

⇒ 走快捷分支时，**行宽 = 布局宽度**，而**声明宽度 = SELECT 列表宽度**。两者只在
「SELECT 列表宽度 == 布局宽度」时才碰巧相等 —— 而这正是 `select.columns.len() <= 1`
永远做不到的情况。

实测（改造前）：

| 语句 | 行宽（实际） | 行宽（声明） | debug 后果 | release 后果 |
|---|---|---|---|---|
| `SELECT cust FROM orders GROUP BY cust` | 3 | 1 | panic @ `executor.rs:70` | 行原样输出，**声明 1 列却打出 3 个 cell** |
| `SELECT count(*) FROM orders GROUP BY cust` | 4 | 1 | panic @ `executor.rs:70` | 打出 4 个 cell，**第一个是分组键** ⇒ 读作「分组值」而非「计数」 |
| `SELECT * FROM orders GROUP BY cust` | 3 | 2 | panic @ `executor.rs:70` | 声明 2 列却打出 3 个 cell |
| `SELECT UPPER(cust) FROM orders GROUP BY cust` | 3 | 1 | panic @ `executor.rs:70` | 声明 1 列却打出 3 个 cell |

⇒ **与 HAVING、与 AND、与子查询都无关**。#5432 的两个失败用例之所以报在 HAVING 上，
是因为它们恰好是「单列 SELECT + GROUP BY + HAVING」的组合。

### 1.4 #5433 的真因：两个互相独立的缺陷

**(a) 视图不可见 —— 键分隔符漂移**

`crates/storage/src/engine.rs`：

```rust
const DB_SEP: char = '\u{1}';                                  // 行 968
pub(crate) fn scoped_key(db: &str, table: &str) -> String {
    format!("{}{}{}", db.to_lowercase(), DB_SEP, table.to_lowercase())   // 行 972-974
}
```

`MemoryStorage::list_views`（改造前，行 3756）：

```rust
fn list_views(&self, db: &str) -> Vec<String> {
    let prefix = format!("{}\0", db);          // ← NUL，不是 DB_SEP ⇒ 永远匹配不上
    ...
}
```

⇒ 列表**恒空** ⇒ `sqlite_master`（`src/system_tables.rs:132` 正是用 `storage.list_views(db)` 造行）
**看不到任何视图**。

**这不是新缺陷，是 #5350 的漏网孪生。** `FileStorage::list_views` 里已经写着修复与原因：

```rust
// crates/storage/src/file_storage.rs:6894-6897
// #5350: this stripped a hard-coded `"{db}\0"` prefix while
// `scoped_key` joins with `DB_SEP` (`\u{1}`), so the strip never
// matched and `list_views` always returned an empty list. Split on
// the real separator instead of hand-spelling it.
```

⇒ **#5350 修了 `FileStorage`，漏了 `MemoryStorage`。** 失败模式是**静默**的：
`CREATE VIEW` 成功、`has_view` / `get_view` 都找得到视图，只有 introspection 列表是空的。

**(b) `Unknown database: mysql` —— 校验顺序错了**

`src/engine_select.rs:843`（改造前）：

```rust
if let Some(schema) = &select.schema {
    if !schema.eq_ignore_ascii_case("information_schema") {
        self.ensure_database_known(schema)?;          // ← 在这里就报错返回
    }
}
```

而真正能处理 `mysql.user` / `mysql.db` 的拦截在**后面**（`src/engine_select.rs:886`）：

```rust
if let Some(result) = self.try_system_table_select(select) {
    return result;                                   // ← 永远到不了
}
```

`ensure_database_known` 回答的是「storage 里有没有这个目录」，而 `mysql` 是**虚拟 catalog**
（`mysql.user` / `mysql.db` 由 `catalog::AuthManager` 合成，`src/system_tables.rs:42-43`），
storage 里当然没有它的目录 ⇒ `Unknown database: mysql`。

### 3.1 #5431 的修法：为什么不是「给 CI 补一个环境变量」

补 `SQLRUSTGO_REPO_ROOT` 只能让 CI 变绿，**三个问题一个都不解决**：

1. **依赖仍然是外部的** —— 换一个 checkout 位置、换一种运行方式（IDE / `cargo nextest` /
   直接跑二进制）就又红了；
2. **测试仍然是嵌套 cargo** —— 在 `cargo test` 里 `cargo run` 一次要 35.72 s（4 个用例），
   而 CI 的 `test` job 有 9000 s 的总预算，被这种「测试里再编译一次」吃掉的每一秒都是净损失；
3. **错误仍然是静默的** —— `unwrap_or_default()` 把「跑不起来」变成「断言失败」，
   失败信息指向症状（`should have apple: `）而不是原因。

新做法沿用本仓库**已有**的模式（`crates/mysql-server/tests/` 下 6 个文件都这么写，
`alter_table_test.rs:9-17` 有专门的说明）：

```rust
let mut child = Command::new(env!("CARGO_BIN_EXE_sqlrustgo-mysql-server"))
```

⇒ 编译期保证二进制位置、无环境变量、无嵌套 cargo、spawn 失败直接 panic 带真实原因。

**代价**：CLI `exec` 子命令的覆盖从根包搬到了 `crates/mysql-server/tests/`。
**收益**：同一批断言从 35.72 s 降到 **0.80 s**，且断言从「子串包含」升级为「整行精确匹配」。

```diff
- assert!(out.contains("100"), "should have value 100: {}", out);
+ assert_has_row(&out, "Integer(1) | Text(\"apple\") | Integer(100)");
```

> 子串断言会把 `Integer(1000)` 也算作 `Integer(100)` 的证据 —— 这在 #5431 的
> `COUNT(*) = 1` 断言上尤其危险（原断言是 `out.contains(" 1\n") || ...`）。

### 3.2 #5432 的修法：宽度是引擎的硬不变量

改造后 `src/engine_select.rs:2596`：

```rust
let agg_result_rows = if is_star_agg {
    // Star projection: the table's own columns. They are the **tail** of the
    // aggregate row — after the group keys and the aggregates:
    //   [group_key..., aggregate..., table_column...]
    let fd_start = group_exprs.len() + select.aggregates.len();
    agg_result_rows
        .into_iter()
        .map(|row| row.iter().skip(fd_start).cloned().collect::<Vec<Value>>())
        .collect::<Vec<Vec<Value>>>()
} else {
    /* ... 单列与多列走同一条重投影路径 ... */
};
```

**为什么 star 分支也要改**：改造前 star 分支返回**整行**（含 group key 与 aggregate），
而 `SELECT *` 的声明列是**表自身的列**。修好单列捷径后，star 分支会独自把行弄宽 ——
所以两条分支必须一起改。

### 7.1 `base_db` 的处理（刻意不改）

`src/engine_select.rs:858-862` 的 `base_db` 计算**刻意保留** `information_schema` 的过滤、
**不**把 `mysql` 过滤掉：

```rust
let base_db = select
    .schema
    .clone()
    .filter(|s| !s.eq_ignore_ascii_case("information_schema"))
    .unwrap_or_else(|| current_db.clone());
```

理由：`mysql` 是**真实的** MySQL schema。若把它折叠成「无 schema 限定」，`FROM mysql.foo`
会退化成「在当前库里找 `foo`」⇒ **静默读到错误的表**。保留 `base_db = "mysql"` 后，
`FROM mysql.foo` 会去找 `mysql.foo` 并报「表不存在」—— 与 MySQL 的
`Table 'mysql.foo' doesn't exist` 语义一致。
