## 结论

PR #5105（另一 agent，`4fbdd280d6`）把当前库改成连接级，解除了我上一批留的 4 条
`#[ignore]`。方向对，但**引入了一处脏读回归**：连接能读到另一连接未提交的写入。

## 缺陷

`scan_for_reader_in_db` 计算了 `reader_tx` 却丢弃：

```rust
pub(crate) fn scan_for_reader_in_db(&self, storage, db, table) -> ... {
    let reader_tx = self.reader_tx();     // 算了
    storage.scan_in_db(db, table)         // 没用
}
```

`scan_in_db` 不接受事务，默认实现是 `self.scan(table)`，而 `FileStorage::scan` 经
`tbl()` 解析到 `inner.current_tx_id()` —— **一个存储级共享值**。

`MvccStorage` 覆写 `scan_in` 正是为了让读不经过这个值（#4983/#4974 的原话：未提交的
写入不得对没有它的读者可见）。把 SELECT 路径绕开该覆写，等于把生产读放回共享值。

server 把 `FileStorage` 包在 `MvccStorage` 里（`mysql-server/src/lib.rs`，
`V400-MVCC-ENABLE`），所以这是生产路径。

### 实证（`tests/mvcc_reader_tx_5105.rs`）

生产栈 `MvccStorage<FileStorage>` + 两个 `ExecutionEngine`：

| 基线 | 结果 |
|------|------|
| #5105 的父提交 `d853cb7690` | **4 passed / 0 failed** |
| #5105 之后 `077588b0e9` | **2 passed / 2 failed** |

```
connection B saw A's UNCOMMITTED row
  left: 2
 right: 1
```

### 为什么 storage 层测试没抓到

`crates/storage/tests/tx_isolation_and_escape_hatch_test.rs` 有 8 条隔离测试，
**全部通过**。因为它们直接调 trait 的 `scan_in`，绕开了被改的那一层。

这就是它容易被漏过的原因：隔离契约仍在一层之下被验证，而坏掉的代码在其之上。
所以新测试走 `ExecutionEngine`。

## 修复

`scan_in_tx_db(db, table, reader_tx)` 这个签名早已存在（#5025 加的），注释写着
「`MvccStorage` needs both」，但**零调用点**，且默认实现 `let _ = db` 会丢库。
两半都没接上。

接上全链：

1. `ExecutionEngine::scan_for_reader_in_db` → `scan_in_tx_db(db, table, reader_tx)`
2. **`MvccStorage`** 新增 `mvcc_table_in(db, table)` 与 `pending_keys_in(db, …)`；
   `mvcc_table(table)` 降为转调 `mvcc_table_in(inner.current_db(), …)`；
   覆写 `scan_in_tx_db`，版本存储、pending 集合、内层扫描**三者都用传入的 db**
3. **`FileStorage`** 覆写 `scan_in_tx_db` → `scan_in_db`（无 MVCC，tx 无意义）
4. **3 层包装层转发** `scan_in_tx_db`：`WalStorage`、`ParallelWalStorage`、
   `BinaryStorage`（`BoxStorageEngine`）。它们都转发了 `scan_in`，唯独缺这一条，
   于是 trait 默认在最外层把 `db` 丢了

第 3 步是必须补的，不是我顺手加的：漏掉它时 `session_db_isolation_5057.rs` 的
**4 条测试立刻失败** —— 那 4 条用 `FileStorage`，走 trait 默认的 `let _ = db`
退回到 `current_db`。这正好证明了包装层转发的必要性。

## 变异验证

### M-G：`scan_for_reader_in_db` 退回 `scan_in_db`（#5105 的状态）— CAUGHT

```
isolation_holds_inside_a_non_default_database ... FAILED
uncommitted_write_is_invisible_to_another_connection ... FAILED
committed_write_is_visible_to_another_connection ... ok
autocommit_reader_sees_committed_rows ... ok
```

精确复现脏读。

### M-H：`scan_in_tx_db` 的内层读取退回 `inner.scan(table)` — 首轮存活，补测试后 CAUGHT

**首轮 5 条全部存活。** 原因是前 4 条测试都在 `d1` 里，而 `inner.current_db()`
恰好也是 `d1` —— 巧合让它看不出 `db` 被忽略了。

这是本次唯一一处「变异存活后怀疑测试」的地方，处理方式是加一条**专门针对 db 半边**
的用例，而不是放宽既有断言：

```
same_table_name_in_two_databases_does_not_mix
  A (in d1) did not see exactly d1.t
  left: 3
 right: 1
```

`left: 3` 只可能来自合并：`d1.t` 的 1 行（MVCC 侧正确）+ `d2.t` 的 2 行（内层侧
按共享 `current_db` 取错）。M-H **CAUGHT**。

### 修正了我自己测试里的一个错误假设

接线后 `committed_write_is_visible_to_another_connection` 反而失败
（`left: 0`），一度看起来是修复过头。实为**测试写错**：B 从未 `USE d1`，本就读不到
`d1.t`。

之前它「通过」是因为内层按 `inner.current_db()`（A 选的 d1）取数 —— 读对了但是
**碰巧**，测试并没有在测隔离。补 `join()` 让 B 显式选库，并在注释里写明这个坑。

## 仍未覆盖（不是本次遗漏，是明确剩余）

engine 侧还有 **19 处** `scan_for_reader_with` / `scan_for_reader_dyn` 未接线
（#5105 自述 3 处，实测更多）：

```
src/cbo_estimator.rs:176      src/engine_cte.rs:399        src/engine_ddl.rs:1339
src/engine_dml.rs:445/463/558/949/1660/1837                src/engine_select.rs:627
src/engine_select.rs:4695/6832/6870/6946/7133/7346/8420    src/engine_utils.rs:184
```

它们**保留了 `reader_tx`**（走 `scan_in`），丢的是 `db`。所以事务隔离在这些点仍
成立，跨库定位仍走共享 `current_db`。后果比 #5105 修掉的那个轻：不产生脏读，只
是这些点上的表解析跨库会错。

接线需要每个调用点都有 db 在手。`engine_dml.rs` 的 6 处最容易 —— `execute_insert`
/ `_update` / `_delete` 开头已经取了 `stmt_db`，只是没往下传。其余散落在没有 db
上下文的 helper 里（CTE、DDL、子查询），需要逐个改签名。

逐条处理还是整批推进，取决于是否值得为「不产生脏读」的路径扩大变更面。建议按
`engine_dml` 先做（低风险、紧邻已有变量），其余单列一批。
