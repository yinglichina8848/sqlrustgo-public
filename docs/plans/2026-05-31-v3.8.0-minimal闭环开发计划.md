# Issue #2625: v3.8.0 开发与集成测试计划 — 最小闭环路径

## 问题背景

当前 `develop/v3.8.0` 分支存在 **双路径执行问题**：

```
路径A (正确):  Client → ExecutionEngine.execute() → Storage
路径B (错误):  Direct storage access bypass ExecutionEngine
```

PR-800 的目标是消除路径B，使 ExecutionEngine 成为唯一写入口。但当前代码本身无法编译，无法验证这个目标。

## 解决方案：最小闭环优先

从可执行的最小系统开始，逐步扩展，每个阶段都是可测试的闭环。

## 阶段 1: 单执行路径验证 (P0)

**目标:** 消除路径B，所有DML经过 ExecutionEngine.execute()

### 1.1 定义单一执行入口

- [ ] `ExecutionEngine` trait 是唯一 DML 入口
- [ ] `TransactionalFacade` trait 作为单一写控制面
- [ ] 禁止直接 storage write 调用

### 1.2 WalTransactionalFacade 参考实现

- [ ] 实现 `TransactionalFacade` trait
- [ ] begin() / commit() / rollback() / execute_write()
- [ ] 内部调用 DriftGate.validate()

### 1.3 集成测试

```
Test: INSERT via Facade → Storage
Test: UPDATE via Facade → Storage  
Test: DELETE via Facade → Storage
Test: 直接 storage 写操作 → REJECTED
```

**验收标准:** 所有写操作通过 Facade，绕过路径被静态分析或运行时拒绝

---

## 阶段 2: WAL 合约强制 (P1)

**目标:** WAL 顺序强制执行，无 WAL 就不允许 mutation

### 2.1 DriftGate 强制

- [ ] `DriftGate.validate_mutation()` — WAL begin 必须在 mutation 之前
- [ ] `DriftGate.validate_commit()` — commit 时 WAL segment 必须 open
- [ ] Critical violation → panic (VtuGuard)

### 2.2 集成测试

```
Test: 无 WAL begin → INSERT → PANIC
Test: WAL begin → INSERT → OK
Test: WAL begin → INSERT → COMMIT → OK
Test: WAL begin → INSERT → ROLLBACK → WAL abort
```

**验收标准:** 没有 WAL 的 mutation 触发 panic 或错误

---

## 阶段 3: 事务边界强制 (P1)

**目标:** 事务边界完整性，所有 mutation 在事务内

### 3.1 TxnBoundary Gate

- [ ] TransactionContext 跟踪 active txn
- [ ] mutation 必须在 active txn 内
- [ ] commit/rollback 必须匹配 begin

### 3.2 集成测试

```
Test: 无 TxnBegin → Mutation → REJECTED
Test: TxnBegin → Mutation → COMMIT → OK
Test: TxnBegin → Mutation → ROLLBACK → OK
Test: TxnBegin (id=1) → COMMIT (id=2) → REJECTED
```

## 关键约束

1. **单 DML 入口:** ExecutionEngine.execute() 是唯一写路径
2. **VtuGuard 是硬约束:** Critical violation = panic
3. **渐进式:** 每个阶段完成后可运行测试
4. **无破坏:** 不降低现有覆盖率
