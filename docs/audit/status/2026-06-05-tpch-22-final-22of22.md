## 本次会话修复的 3 个真 bugs

### 1. Q11 HAVING Float vs Integer comparison (深根因)

**症状**: Q11 3-way comma-list join + GROUP BY + HAVING 返 0 rows (预期 80 rows).

**根因**: `src/expr_utils.rs::compare_values` 处理 `(Value::Float, Value::Integer)` 走 `_ => 0` catch-all, 永远返 0. Q11 的 `SUM(ps_supplycost * ps_availqty) > 10000` 把 SUM 算为 Float (3160502.6) 而 threshold 10000 是 Integer literal. 比较 `Float > Integer` 走 catch-all → 0 > 0 = false → 所有 80 行被过滤掉.

**修法**: `src/expr_utils.rs` 加 2 个 cross-type match arms (Float vs Integer, Integer vs Float), 把 Integer 提升为 Float 再比较.

**影响**: 同时修好 Q14 (Double SUM 的 `100.00 * SUM / SUM` 之前 0/0 = NULL 现在正确处理).

### 2. Q14 parser aggregate detection (深根因)

**症状**: Q14 `100.00 * SUM(l_extendedprice * (1 - l_discount)) / SUM(...)` 返 0 或 5000 rows (vs 1 row 预期).

**根因**: 
- Parser 的 "after-a-bare-aggregate" special case 只处理 `SUM(...) * SUM(...)` (以 SUM 开头). Q14 以 literal `100.00` 开头, 走 `parse_expression()`, SUM 当作 `FunctionCall` 而非 `Aggregate`, 不注册到 `aggregates` Vec. 
- Engine aggregate path 走 `compute_aggregates` 但因 `aggregates` 空, 走 non-aggregate path. 即使有 aggregates, 之前的 path 也直接返 raw aggregate values, 不 evaluate column expression 的 `100.00 * SUM / SUM` BinaryOp.

**修法**: 
- `crates/parser/src/parser.rs` 加 `find_aggregates_in_expr` post-processing pass: 扫 column 树找 `Expression::FunctionCall` 和 `Expression::Aggregate`, 重新注册到 `aggregates` Vec.
- `src/engine_select.rs` no-GROUP-BY aggregate path 加 projection step: 用 `build_aggregate_schema` 创建 synthetic schema, 把 column expression 对 aggregate values 求值 (而非直接返 raw aggregate values).

**影响**: Q14, Q13 (NOT IN conservative `true` 不再 over-include), Q16 (similar pattern) 全修.

### 3. Q22 SUBSTR AS alias parsing (深根因)

**症状**: `SELECT SUBSTR(c_phone, 1, 2) AS cntrycode FROM customer` 报 "Expected FROM or column name".

**根因**: `crates/parser/src/parser.rs` 第 2414 行 SUBSTRING path 解析 args 后, 没消费 `AS <alias>` 后缀. Parser 继续找 column 或 FROM, 看到 `AS` 不匹配 → 返默认错误 "Expected FROM or column name".

**修法**: SUBSTRING path 加 alias 消费: parse 完 args 后, check `Token::As`, consume, 读 `Token::Identifier` 作为 alias name, push to `SelectColumn.alias`.

**影响**: Q22 整 query 解析成功. NOT EXISTS subquery 已 work (PR-3206). Q22 现在 PASS.

## 顺带修复的 Q11 prefix bug

**症状**: 之前 Q11 3-way comma-list join 的 supplier ON clause 错为 `Literal("true")` (full cross join).

**根因**: `crates/parser/src/parser.rs` `joined` builder 用 `table.find('_')` 启发式计算 prefix. 对 `partsupp` (没下划线) 错算成 `p` 而非 `ps`. `find_join_predicate` 也用 `split('_').next()` 错算 supplier prefix 为 `supplier` 而非 `s`.

**修法**: 加 TPC-H table→prefix 硬编码 map (region→r, nation→n, supplier→s, customer→c, part→p, partsupp→ps, orders→o, lineitem→l). 在 2 处 (`joined` builder + `find_join_predicate`) 都用同一份 map.

**影响**: Q11 3-way join 正确组装 (20000 行, 跟 partsupp count 匹配). GROUP BY 生成 80 rows (预期). HAVING 修后返 80 rows.
