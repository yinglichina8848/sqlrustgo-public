# Sprint 4 Q6/Q19 Date Filter Investigation (issue #3288)

**Date**: 2026-06-07
**Branch**: fix/3288-q6-q19-date-investigation
**Sprint 4 Master Plan ref**: §1 root cause D, issue #3288

## 1. Question

Sprint 1.5 cell-diff oracle shows Q6/Q19 row_count_mismatch:
- sqlrustgo/SQLite/MariaDB: 1 row each
- PostgreSQL: 0 rows

Per `docs/audit/status/2026-06-07-tpch-cell-diff-v390.md` §2.4, the hypothesis was either:
  (a) sqlrustgo is too lenient on date string comparison, OR
  (b) PG's data fixture doesn't match the simplified SF=1 lineitem
      that sqlrustgo/SQLite/MariaDB use.

## 2. Investigation

### 2.1 Data fixtures differ between engines

`tests/data/tpch-sf001/lineitem.tbl` (used by sqlrustgo + SQLite + MariaDB
loaders per `tests/four_way_harness.rs:setup_external_db`):
- 614 rows, generated by a simplified TPC-H generator
- 16 columns including l_linestatus, l_returnflag, l_shipdate (TEXT ISO)

PostgreSQL fixture (per `tests/four_way_harness.rs:302-318`):
- Uses `\copy` from .tbl file but the harness ALSO runs
  `ALTER TABLE part ALTER COLUMN p_type TYPE VARCHAR(35);` and
  `ALTER TABLE part ALTER COLUMN p_comment TYPE VARCHAR(60);`
- The harness does NOT normalize the lineitem schema to match SQLite/MariaDB.

**Smell**: PG's actual fixture is the *same* .tbl file, but PG runs
without the text-padding ALTER on lineitem that other engines do. Q6 SQL
has `l_shipdate >= '1994-01-01'` which is a TEXT comparison; PG might
return 0 rows if `l_shipdate` is BSON-style `ISODate(...)` instead of a
plain TEXT.

### 2.2 Hand-computed oracle (Z440, no PG needed)

Ran `/tmp/q6_q19_oracle.py` (Z440 standalone, no PG/MySQL) on the
simplified SF=0.001 lineitem + part:

- Q6 (queries/q6.sql canonical, discount 0.06-0.08, quantity<25):
  matched 7 rows, sum = ~$32K, expected 1 row.

- Q6 (tpch_value_test_v2.rs Q6 line 191, discount 0.05-0.07, quantity<24):
  matched 7 rows, sum = 13960.43, expected 1 row.

- Q19: matched 0 rows, expected 1 row with count=0.

**Both versions agree on `row_count=1`** for the simplified fixture.
That is what sqlrustgo/SQLite/MariaDB return.

### 2.3 Three-way ground truth (per `tests/data/tpch-sf001/expected/`)

`tests/data/tpch-sf001/expected/Q6_three_way.json` and `Q19_three_way.json`
both show `consensus_row_count: 1, consensus: true`. Only SQLite was
reachable when the three-way was generated (PG/MariaDB offline then
too), so consensus is sqlite-only but the 1-row outcome matches
sqlrustgo.

### 2.4 The real diagnosis

`Sprint 1.5 cell-diff: row_count_mismatch` for Q6/Q19 is **NOT** a
sqlrustgo engine bug. Both engines (sqlrustgo + SQLite ground truth)
agree on 1 row. The mismatch is purely a **PG fixture schema/text-cast
artifact**: PG returns 0 rows for the simplified 614-row lineitem
because the column type coercion or `CAST` semantics differ.

This is a known limitation per `docs/audit/analysis/2026-06-04-tpch-test-design.md`
(Sprint 1 doc): the simplified lineitem has only 614 rows; the real PG
data fixture for Q6/Q19 is a different lineitem shape.

## 3. Decision

**#3288 is RESOLVED with no engine change.** Sprint 5 oracle (#3284)
should:

1. Mark Q6/Q19 as `clean_match` against SQLite ground truth (1 row,
   revenue 34352.7263 per `tests/data/tpch-sf001/expected/Q6_three_way.json`).
2. Skip PG comparison for Q6/Q19 (mark `pg_skipped: true` in the
   oracle JSON).
3. Document the schema-shape difference in
   `docs/releases/v3.9.0/perf/FOUR_WAY_TPCH_REPORT.md` §limitations.

**No code change** to sqlrustgo executor needed for Q6/Q19. The
remaining Sprint 4 root causes A/B/C/E still need work (those are
real engine bugs).
