## TL;DR (the truth nobody wanted to hear)

**The 5-PR TPC-H 22 thread (3086 / 3089 / 3093 / 3095 / 3098 / 3114)
delivered "in-process engine doesn't crash on 22 queries" — not
"in-process engine produces correct results for 22 queries."**

Concrete numbers from `tests/eval_22_vs_sqlite` (sf001 fixture,
in-process engine, row_count vs SQLite baseline JSON):

| Category | Count | Queries |
|---|---|---|
| **MATCHED** (row_count == SQLite) | **10** | Q1, Q6, Q7, Q11, Q17, Q18, Q19, Q20, Q21, Q22 |
| **MISMATCHED** (row_count wrong) | **8** | Q3, Q4, Q5, Q10, Q12, Q13, Q14, Q16 |
| **ERROR** (engine crash / executor error) | **4** | Q2, Q8, Q9, Q15 |
| **Total** | **22** | — |

Of the 10 "matched", only **Q1, Q6, Q17, Q19** actually return
non-trivial rows where matching ≠ "both return 0 by coincidence."
Q7, Q11, Q18, Q20, Q21, Q22 return 0 because:
- Q7/Q8/Q9 use `EXTRACT(YEAR FROM ...)` (PostgreSQL syntax,
  parser doesn't support — not even an engine bug, just not
  implemented)
- Q11/Q20/Q21 are 0 because sf001's 5-year date range and 614
  lineitem don't produce any matching groups
- Q18 returns 0 by design on sf001 (large-order threshold not met)

So the **real correct-result count is ~4/22** if you discount the
coincidental-zero matches. This is the bar Phase 1 / 1b / 3 / 4
should have been held to, but never was.

## Why we got here: the gap between "test gate" and "correctness gate"

The thread's 4 functional PRs each introduced a `#[test]` that asserts
"doesn't crash and returns the right answer for one specific case":

| PR | Test | What it actually proves |
|---|---|---|
| #3086 | (no test — Phase 0 is just generator script + JSON) | 22 baseline row counts were generated by SQLite against sf001 |
| #3089 | `tpch_bug_regression_test.rs` (4 ignored, 2 pass) | 2 of 6 specific bug cases were fixed |
| #3093 | same 6 tests, un-`#[ignore]` | Bug #4/#5 root cause was test fixture, not engine |
| #3095 | (Macmini — no new test added) | 18/22 in-process "not crash" — but didn't check row_count |
| #3098 | (Macmini — no new test added) | Q15 derived-table predicate isolation — didn't check row_count |

The "in-process 22/22 PASS" line that kept showing up in
`tpch_full_22_test` is **a "didn't crash" gate, not a "correct
result" gate.** The test asserts:
- `tpch_full_22_test` (1 test, 478s on SF=0.01): does the engine
  return *some* result for each query, on a 1-char prefix of the
  SQL text. (It explicitly uses `q1_prefix`, `q2_prefix`, etc. —
  truncated to 1-character TPC-H prefix — so it only checks the
  parser doesn't panic on the first character of each query name.)
- `tpch_value_correctness_test` (4 tests): 4 hand-picked Q1 / Q3
  correctness cases (row_count > 0 for Q3 join, sum > 0 for Q1).
- `tpch_bug_regression_test` (6 tests): 6 hand-picked bug cases
  from the "5 bugs" report.

**None of these verify the full 22 queries' row_count matches the
SQLite baseline.** The thread's central deliverable — "22/22 row_count
matches SQLite" — was never gated by any test.

## The 12 actual problems (sorted by user-visible cost)

### Tier 1 — Q1 is correct, everything else is suspicious

The single query that absolutely matters for TPC-H is Q1 (the
pricing summary query). It is correct, by accident or by design.
Everything else in the 22 we shipped in this thread is somewhere
between "probably wrong" and "definitely wrong" — none of it has
been *verified correct* with the full 22-query round-trip.

### Tier 2 — Q2 / Q8 / Q9 / Q15 crash (4 of 22)

| Q | Error | Most likely cause |
|---|---|---|
| Q2 | "Column 'ps_suppkey' not found in either 'part' or 'supplier'" | 3-way hub-spoke join with partsupp: join chain doesn't propagate qualified aliases through comma-list + JOIN. (Q2 hub-spoke reordering deferred to v3.9.0 per `docs/audit/analysis/2026-06-04-tpch-test-design.md`.) |
| Q8 | "Unsupported join condition expression" | Q8's `WHERE` has an `OR` with `LIKE` and arithmetic; engine doesn't handle compound join conditions. (Macmini's Phase 3 aggregate-division fix only fixed the parse, not the executor side of Q8.) |
| Q9 | "Join condition must reference one column from each side" | Q9 has 6-table hub-spoke join. Same v3.9.0 deferred fix. |
| Q15 | "Unsupported join condition expression" | Q15 derived-table materialization landed (Macmini PR #3095) but predicate pushdown into derived table is broken (Macmini PR #3098 partially fixed it, but the Q15 ON clause still fails). |

### Tier 3 — Q3 / Q4 / Q5 / Q10 / Q12 / Q13 / Q14 / Q16 wrong row_count (8 of 22)

These are the **most damaging failures** because the engine returns
a number, the test thinks it passed (no error thrown), and the
result is silently wrong. Examples:

- Q3: returns 8 rows, should return 10. 80% of the result. Almost
  right, totally wrong.
- Q4: returns 0 rows, should return 4. 0% — total miss.
- Q13: returns 0 rows, should return 9. 0% — total miss.
- Q14: returns 9 rows, should return 1. 900% — overshooting.
- Q16: returns 0 rows, should return 7.

These mismatches fall into a few patterns:
- **GROUP BY with multiple joins and aggregations** (Q4, Q5, Q10,
  Q12, Q13, Q16): some intermediate join drops rows, or grouping
  key is lost in the join chain.
- **COUNT(DISTINCT) and edge aggregates** (Q14): engine's
  COUNT(DISTINCT) over multi-table joins is off by an order of
  magnitude.
- **Subquery correlated** (Q2, Q17, Q20, Q22): some work
  (Q17, Q20, Q22 thanks to Macmini Phase 3), some don't (Q2).

### Tier 4 — wire-protocol (0/22 — separate blocker)

See `docs/discovery/2026-06-05-orders-load-eagain.md` and PR #3114.
**Zero** of the 22 queries can be exercised over the wire because
`LOAD DATA LOCAL INFILE` EAGAINs on `orders.tbl` and `lineitem.tbl`.
TPC-H 22 wire round-trip is a P0 issue entirely blocked by one
unfixed server handler bug.

## What "done" actually looks like (the bar we missed)

For TPC-H 22 to be genuinely done, every one of these must be true
*and there must be a test that enforces it*:

1. **In-process row_count matches SQLite** for all 22 queries
   (currently 10/22 — need to fix Q3, Q4, Q5, Q10, Q12, Q13,
   Q14, Q16).
2. **In-process result values match SQLite** (or PG/MySQL) for at
   least the aggregation columns of Q1, Q3, Q10, Q12, Q13 — the
   queries that are measured in TPC-H scores.
3. **Wire-protocol 22/22 row_count matches SQLite** (currently
   0/22 — blocked by server LOAD DATA EAGAIN, need to fix the
   server handler first).
4. **EXTRACT(YEAR FROM ...)** parser support so Q7/Q8/Q9 stop
   silently returning 0 (currently parser error swallowed
   somewhere or returns 0).
5. **Q2/Q9 hub-spoke join reordering** for the 3-table and
   6-table joins (currently deferred to v3.9.0 per the v3.8.0
   RC1 closure report).
6. **Q15 ON clause validation** so the derived-table predicate
   pushdown actually works (Macmini's PR #3098 partially fixed
   this; the Q15 wire path still errors).

## Suggested next steps (ranked by user-visible value)

### Option A: Fix the 8 MISMATCHed queries (in-process row_count) — P0

- **Why first**: these are the silent killers. Engine returns a
  number, test passes, result is wrong.
- **Effort**: 3-5 days (one query at a time, root-cause per case,
  no shortcut).
- **Output**: 18/22 in-process row_count match SQLite (Q2/Q8/Q9/Q15
  still crash but at least they're not silently wrong).
- **PR shape**: 1-2 PRs per query (fix + regression test).

### Option B: Fix the server LOAD DATA EAGAIN bug — P0 (blocks wire)

- **Why**: this is the only thing standing between us and 22/22
  wire round-trip. The wire test prototype is already written
  (recoverable from session history, was deleted in the Phase 2
  closure commit).
- **Effort**: 2-3 hours (server handler is `crates/mysql-server/src/lib.rs::handle_load_local_infile`).
- **Output**: 8/8 tables loadable; wire test restores; 13-15/22
  wire PASS (everything except Q7/Q8/Q9 due to EXTRACT, plus Q2/Q15
  until their in-process fixes land).

### Option C: Add `EXTRACT(YEAR FROM ...)` parser support — P1

- **Why**: unblocks Q7/Q8/Q9 in-process and wire.
- **Effort**: 1-2 hours.
- **Output**: +3 to the in-process and wire tallies (assuming
  executor can handle the function call).

### Option D: Make the in-process "22/22 PASS" gate actually verify row_count — P0

- **Why**: the current gate is misleading. The 5-PR thread
  shipped "doesn't crash" as the success criterion. The
  `eval_22_vs_sqlite` test (this commit) makes the real bar
  enforceable.
- **Effort**: 30 min (rename, change assertion from "doesn't
  crash" to "row_count matches SQLite baseline JSON").
- **Output**: 1 new test that fails today (10/22) and forces
  every future fix to also fix row_count, not just crash-avoidance.

### Option E: Stop. The thread is "shipped" in the sense that
every PR is merged, no `#[ignore]`s are blocking CI, and the
in-process 22/22 number on the closing report is technically
true. The remaining 12 failures (4 crash + 8 wrong) are
separately trackable in the v3.8.0 RC1 closure report under
"Q2/Q9 hub-spoke (v3.9.0)" and "EXTRACT (v3.9.0)". Calling
the thread done and moving on to v3.9.0 is a legitimate
choice if the remaining work is explicitly out-of-scope for
v3.8.0.

## Recommended combination

**D (gate tightening) + A (8 mismatch fixes) + B (server LOAD
DATA fix)**, in that order, over 1-2 weeks.

D is 30 minutes and immediately prevents the next PR from
silently re-introducing wrong row_count. A is the bulk of the
work. B unblocks the wire-protocol story which is independently
valuable for non-TPC-H use cases (sf0.01 corpus, generic LOAD
DATA users).

C is nice-to-have. E is acceptable if v3.8.0 truly is "feature
complete" and v3.9.0 has the bandwidth for TPC-H continuation.

## Bottom line for 李哥

**The thread's stated goal — TPC-H 22 queries running end-to-end
over the wire and matching an external baseline — is currently
0% achieved (wire) and 10/22 = 45% achieved (in-process).** The
previous 5 PRs made the engine more robust and added 6 new
regression tests, but the **central deliverable was neither
written down as a test nor enforced as a gate.** This document
fixes the second half (we now have a test, `eval_22_vs_sqlite`,
that asserts row_count match); the first half (actually
matching for all 22) is the next session's work.
