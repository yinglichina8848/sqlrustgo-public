## TL;DR

The fixture checked in at `tests/data/tpch-sf001/` (15 customers / 150 orders /
614 lineitem rows) is **not a valid TPC-H .tbl file**. Every row has the wrong
number of pipe-separated fields (8 vs 9 vs 10), and the per-row column order
does not match the standard TPC-H schema. SQLite refuses to import it
silently:

```
sqlite> .import tests/data/tpch-sf001/customer.tbl customer
tests/data/tpch-sf001/customer.tbl:1: expected 8 columns but found 9 - extras ignored
tests/data/tpch-sf001/customer.tbl:2: expected 8 columns but found 10 - extras ignored
...
```

The canonical, TPC-H-spec-compliant fixture lives at
**`/home/openclaw/sqlrustgo-tpch/data/`** (1500 customers / 15000 orders /
60000 lineitem = SF=0.01). Macmini used this fixture in PR #3124
(`tpch_value_test_v2`) to report `6/22 PASS / 16/22 FAIL`.

## How the corruption was found

While digging into a suspected 2-table JOIN bug (Q3 actual=8 vs expected=10),
I wrote `tests/diag_parser_2t.rs` to compare `customer, orders WHERE c_custkey=o_custkey`
(comma-list) against `customer INNER JOIN orders ON c_custkey=o_custkey`
(explicit JOIN) at SF=0.001.

Result:
- `INNER JOIN` path: 150 rows ✓ (matches SQLite)
- comma-list path: 13 rows ✗ (looks like a 2-table join drop bug)

Deeper inspection of the 150 matched rows showed row[105..120] had the
`o_custkey` column populated with **Text("iously regular dependencies
nag blithely blithely quiet excuses. blithely pending ...")** — that is the
TPC-H `o_comment` field, not `o_custkey` (=11).

That sent me to look at the raw `.tbl` file. First row of `customer.tbl`:

```
1|1|Customer#000000001|IVhzIApeRb ot,c,E|15-869-611-5825|711.56|BUILDING|arefully...|
```

→ 8 real fields + trailing empty, which lines up with the standard
`c_custkey, c_name, c_address, c_nationkey, c_phone, c_acctbal, c_mktsegment, c_comment`
column order **only if** we use the standard TPC-H order (not the
sqlrustgo-internal `c_custkey, c_nationkey, c_name, ...` DDL).

Line 12 of the same file:

```
12|12|12|Customer#000000012|7A9Rdm6P9ea6Jj7AaY 4c,|21-199-311-4723|4218.16|AUTOMOBILE|usly pending p...|
```

→ 9 real fields + trailing empty. The first three are "12", "12", "12" — a
pattern that does not match either TPC-H standard or any sensible schema. The
canonical SF=0.01 fixture at `/home/openclaw/sqlrustgo-tpch/data/customer.tbl`
first row is:

```
1|Customer#0000001|0 Address|0|10-0000-0000|-500.00|AUTOMOBILE|Customer comment 0|
```

→ 8 real fields, **standard TPC-H order** `c_custkey, c_name, c_address, c_nationkey, c_phone, c_acctbal, c_mktsegment, c_comment`.
And the per-row `Customer#0000001` is in the second field (= c_name), exactly
where the schema says it should be.

## Why sf001 .tbl exists at all (best guess)

Looking at the row counts (15/25/10/20/80/150/614/5) and the fact that
`tpch_full_22_test.rs` reports 22/22 in-process PASS on this fixture (before
the canonical SF=0.01 audit replaces it), my best guess is that this fixture
was hand-rolled by an early TPC-H port (probably during Sprint 1) to fit in a
small git checkout. It worked for "22 queries don't crash" but it has never
been a real TPC-H dataset, and the per-row column count drift
(8/9/10 mixing) suggests it was patched across multiple sprints without ever
being re-generated by `dbgen`.
